Virtual Memory

Every process on your machine behaves as if it owns the entire address space, starting at address 0, with no other process in sight — even though dozens of processes are really sharing the same physical RAM at once. Virtual memory is the illusion that makes this work: an extra layer of address translation, invisible to the application programmer, that simultaneously protects processes from each other, simplifies memory management, and turns main memory into just another cache.

CS:APP reference: Chapter 9.1–9.5.  |  Tested on: This material comes after Game 2 and is tested only on the comprehensive Final.

Learning objectives

  • Explain the three problems virtual memory solves: efficient use of DRAM, memory management, and process isolation
  • Distinguish a virtual address from a physical address and describe the role of the MMU
  • Describe pages and page tables, and how a page table entry maps a virtual page to a physical page
  • Walk through address translation on a page hit and explain what happens on a page fault
  • Explain how virtual memory enables memory protection, memory-mapped files, and swapping

1. Why virtual memory exists

Processes in a running system share the CPU and main memory with every other process on the machine. Left unmanaged, that sharing creates real problems: if too many processes need too much memory at once, some simply can't run; and if one process is allowed to write directly into another process's memory (by accident or by malice), that other process can fail in ways that have nothing to do with its own logic. Modern systems solve both problems with an abstraction called virtual memory (VM), and it does three distinct jobs at once:

  • Uses main memory efficiently. DRAM acts as a cache for the parts of a much larger virtual address space, most of which lives on disk until it's actually needed.
  • Simplifies memory management. Every process gets an identical, private, linear address space starting at address 0, regardless of how physical memory is actually laid out or how many other processes are running.
  • Isolates address spaces. A process cannot read or write memory belonging to another process, and ordinary user code cannot touch privileged kernel memory at all.

All of this happens silently and automatically — the application programmer never manages it directly.

2. Virtual addresses vs. physical addresses

In a simple embedded system, the CPU issues physical addresses (PA) directly, and those addresses correspond one-to-one with locations in main memory. Servers, laptops, and phones don't work that way. Their CPUs issue virtual addresses (VA), and a piece of hardware called the MMU (Memory Management Unit), sitting on the CPU chip, translates every virtual address into a physical address before it ever reaches main memory. The application only ever sees and manipulates virtual addresses; it has no idea where its data actually lives in physical RAM, and it doesn't need to.

3. Virtual memory as a cache for disk

The first way to think about virtual memory is as a cache, exactly like the caches from the previous module — just one level further down the hierarchy. Conceptually, a process's entire virtual address space (all 2n bytes of it) is treated as if it lives on disk. It's divided into fixed-size chunks called pages (size 2p, typically 4–8 KB). Physical main memory (DRAM) holds copies of a subset of those pages at any given time, playing the same role for disk that a hardware cache plays for DRAM.

Each virtual page falls into one of three states:

  • Unallocated — not yet created by the VM system; takes up no disk space.
  • Cached — allocated, and currently resident in physical memory.
  • Uncached — allocated, but currently only on disk, not in physical memory.

Because the miss penalty here is enormous (DRAM is roughly 10× slower than the SRAM caches above it, and disk is roughly 10,000× slower than DRAM), the design choices look different from a hardware cache: pages are large (to amortize the huge cost of a disk access over more data), any virtual page may be placed in any physical page slot (fully associative, requiring a real mapping structure rather than a simple hardware calculation), and replacement decisions are made by sophisticated software algorithms rather than simple hardware logic.

4. Page tables and address translation

The OS tracks where every virtual page currently lives using a per-process data structure called the page table, stored in DRAM. Each virtual page has one page table entry (PTE) containing a valid bit and either a physical page number (if the page is cached) or a disk address / "not present" marker (if it isn't).

A virtual address splits into two pieces: a virtual page number (VPN), which selects a PTE, and a virtual page offset (VPO), which selects a byte within that page. Translation conceptually works like this:

  1. The CPU sends a virtual address to the MMU.
  2. The MMU uses the VPN to index into the page table (a "page table walk") and fetches the matching PTE.
  3. If the PTE's valid bit is 1 (page hit), the MMU combines the PTE's physical page number with the original page offset to form the physical address, and sends it on to the cache/memory system, which returns the data.
  4. If the valid bit is 0, the page isn't in physical memory at all — this triggers a page fault, described below.

5. Page faults

A page fault is what happens on a virtual-memory "miss": the CPU references a virtual page that is not currently resident in physical memory. Unlike a hardware cache miss, a page fault is handled by raising an exception and letting the OS's page fault handler take over:

  1. The MMU detects the invalid PTE and triggers a page fault exception.
  2. The kernel's fault handler picks a victim page to evict from physical memory (if physical memory is full), and if that victim has been modified, writes it back out to disk first.
  3. The handler reads the needed page in from disk, updates the victim's PTE to point at it, and marks it valid.
  4. The kernel resumes the original process, re-executing the instruction that faulted — which now hits, because the page is in memory.

Waiting until the exact moment of the miss to bring a page in from disk, rather than loading everything up front, is called demand paging. It means nothing is ever copied into physical memory until it's actually referenced.

This scheme only performs well because of locality: at any point in time a program tends to reference a fairly small set of pages, called its working set. If a process's working set fits in physical memory, it runs fast after its initial faults; if the combined working sets of every running process exceed physical memory, the system can fall into thrashing — pages get evicted and immediately faulted back in over and over, and performance collapses.

What actually happens when the CPU references a virtual page whose valid bit is 0 in the page table?
A page fault is an exception, not a crash — the kernel's fault handler brings the missing page in from disk (evicting a victim page if needed), fixes up the page table, and lets the faulting instruction run again, this time as a hit.

6. Memory management and protection

Beyond acting as a disk cache, the indirection of a page table buys two more big wins.

Simplifying memory management: because every process gets its own private, identical virtual address space, the OS is free to scatter a process's actual pages anywhere in physical memory — contiguity in the virtual address space says nothing about contiguity in physical memory. This also makes it trivial to share memory between processes (map two different virtual pages, in two different processes, to the same physical page — this is exactly how shared libraries avoid keeping duplicate copies of library code in RAM), and it keeps linking and loading simple, since code, stack, and shared libraries can always start at the same virtual addresses in every process.

Memory protection: each PTE can be augmented with permission bits (readable? writable? requires kernel/supervisor mode?), and the hardware checks these bits on every single memory access. A process that tries to write to a read-only page, or touch memory it was never granted, triggers a hardware exception, and the kernel responds by sending it a SIGSEGV ("segmentation fault") signal — the familiar crash any C programmer eventually sees from a bad pointer.

This same translation layer is also what makes memory-mapped files possible — mapping a file's contents directly into a process's virtual address space so that ordinary loads and stores read and write the file, with pages faulted in from disk on demand exactly like any other virtual page — and what makes swapping possible, where the OS evicts a rarely-used process's pages out to disk entirely to free physical memory for other processes, and pages them back in on demand if that process runs again.

Two different processes map their own distinct virtual pages to the exact same physical page in DRAM. What is this used for?
Because address translation is per-process and fully flexible, the OS can point multiple processes' page tables at one shared physical page — the standard way read-only library code is shared across every process that uses it, without wasting RAM on redundant copies.
