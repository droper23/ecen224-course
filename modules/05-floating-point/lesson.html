Floating Point

Integers can't represent fractions, and fixed-point numbers force an ugly trade-off between range and precision. Floating point solves this by letting the "binary point" move — and IEEE 754 is the standard that makes every computer on Earth agree on exactly how. This module covers the format, how to convert numbers by hand, and where it quietly breaks.

Learning objectives

  • Explain why fixed-point representations force a range/precision trade-off
  • Convert a normalized IEEE 754 number between decimal and its sign/exponent/fraction bit layout, by hand
  • Compute the exponent bias for a given number of exponent bits, and apply it in both directions
  • Identify the special encodings: normalized, denormalized, infinity, and NaN
  • Explain why floating point addition is not associative, and why that breaks real systems

1. Why integers aren't enough

Every representation you've used so far — unsigned, two's complement — encodes whole numbers. Nothing stops you from imagining a binary point in the middle of a bit pattern, the way 1011.101₂ has 3 bits before the point and 3 after. Each position right of the point is worth 2-1, 2-2, 2-3, ... — mirroring how 0.101₁₀ is 1/10 + 0/100 + 1/1000 in decimal.

That's a fixed-point number: you pick a spot for the binary point once, and it never moves. It works, but it forces a trade:

  • More fractional bits → better precision, but a smaller maximum magnitude
  • More whole-number bits → bigger range, but coarser precision

Worse, a fixed budget of fractional bits can't represent very small numbers (10-100) or very large ones (10+100) in the same format at all. Physics, graphics, and machine learning all need both — so we need the point to float.

A fixed-point format uses 8 bits: 4 for the whole part, 4 for the fraction. What happens if you shift 2 bits from the fractional side to the whole side?
Moving bits from the fraction to the whole-number side lets you represent bigger numbers (more range) but the smallest representable step between two fractional values gets coarser (less precision). This exact trade-off is what floating point is designed to avoid.

2. The floating-point idea: mantissa × 2exponent

Scientific notation writes -123.45 as -1.2345 × 102: a sign, a mantissa (the significant digits), and an exponent that says how far to shift the decimal point. Floating point does the same thing in base 2: 

sign × mantissa × 2^exponent

The mantissa controls precision (how many significant bits you keep); the exponent controls range (how far the point can shift). Critically, in binary, any nonzero number can always be normalized so its leading bit is exactly 1 — so that leading 1 never has to be stored. It's implied "for free," which is why the fraction field is one bit shorter than you'd expect.

3. IEEE 754: the standard everyone agreed on

Before 1985, every vendor's floating point behaved slightly differently — same bits, different answers on different machines. IEEE Standard 754 fixed that by defining an exact bit layout and exact rounding rules that every conforming CPU must follow. Two sizes matter for this course:

SignExponentFractionC typeBias
Single precision1 bit8 bits23 bitsfloat127
Double precision1 bit11 bits52 bitsdouble1023

The value a normalized encoding represents is:

value = (-1)^sign × 1.fraction × 2^(exp - bias)

Three things to notice, because they're exactly what homework and exam problems test:

  • The exponent field stores a biased value, not the real exponent. The stored field is exp = E + bias. To recover the true exponent E, subtract the bias back out. The bias itself is 2k-1 - 1 where k is the number of exponent bits — that's 127 for 8 bits, 1023 for 11 bits.
  • The fraction field is only the part after the implied leading 1. If M = 1.101, the fraction field stores just 101 (padded with zeros to fill the field width).
  • Bigger numbers get sparser. Because the exponent scales the whole mantissa, the gap between two adjacent representable floats doubles every time the exponent increments. Near 224, single-precision floats can only represent every other integer — which is why the classic C snippet below prints something surprising.
float fp = 16777216;  // 2^24
fp += 1;
printf("val: %f\n", fp);
// val: 16777216.000000  -- the +1 was silently absorbed

4. Worked conversion: decimal → IEEE 754

Convert 15213.0 to single-precision IEEE 754.

  1. Convert to binary: 1521310 = 111011011011012
  2. Normalize so exactly one bit sits before the point: 1.11011011011012 × 213
  3. Fraction field is everything after the implied leading 1, right-padded with zeros to 23 bits: 11011011011010000000000
  4. Exponent field: E = 13, so exp = E + bias = 13 + 127 = 140 = 100011002
  5. Sign bit: 0 (positive)
0 | 10001100 | 11011011011010000000000
sign  exponent         fraction
A single-precision float has exponent field exp = 130. What is the true (unbiased) exponent E?
Single precision bias is 127, so E = exp - bias = 130 - 127 = 3.

5. Special cases: zero, denormals, infinity, NaN

The "normalized" rule above assumes a nonzero number with an implied leading 1 — but that can't represent zero, and it leaves a gap near zero too large to be useful. IEEE 754 reserves the two extreme exponent field values (all 0s and all 1s) to encode special cases instead:

Exponent fieldFraction fieldMeaning
not all 0s and not all 1sanythingNormalized: (-1)s × 1.frac × 2exp-bias
all 0sanythingDenormalized: represents 0 and numbers very close to it, using 0.frac instead of an implied 1
all 1sall 0s±Infinity (e.g. from overflow, or 1.0 / 0.0)
all 1snonzeroNaN — "Not a Number" (e.g. from 0.0 / 0.0 or sqrt(-1))
Why denormalized numbers exist: without them, there would be a "hole" between zero and the smallest normalized number — and worse, two very small numbers that are actually different could subtract to exactly zero. Denormals fill that gap by giving up the implied leading 1 (0.frac instead of 1.frac) so numbers near zero degrade gracefully instead of jumping straight to 0.

6. Where floating point bites you

Floating point cannot represent most real numbers exactly — including numbers that look perfectly simple in decimal, like 0.1. That's not a bug; it's the same reason 1/3 has no exact finite decimal representation. The consequences show up in two places you'll see again in this course and in real systems:

  • Floating point addition is not associative. (a + b) + c can give a different result than a + (b + c) once rounding is involved. This matters for compilers (which can't freely reorder floating-point sums the way they reorder integer sums) and for parallel/GPU code (where reduction order affects the answer).
  • Small per-operation errors accumulate. The Patriot missile system tracked "time since boot" in single-precision floating point, counted in 0.1-second ticks — a value that floating point can't represent exactly. After 100 hours of continuous operation the drift reached a third of a second, a targeting error of 687 meters. On February 25, 1991, that error contributed to a Patriot battery failing to intercept a Scud missile that killed 28 soldiers. The fix that was already known — reboot periodically to reset the accumulated error — hadn't reached that battery's crew in time.
Rule of thumb for this course and beyond: never compare floats with ==. Compare fabs(a - b) < epsilon instead, and be deliberate about the order you sum a long list of floating-point values in.
Why can floating point addition give a different result for (a + b) + c versus a + (b + c)?
Every intermediate floating-point result gets rounded to fit back into the fixed-width mantissa. Which pair you add first changes what gets rounded away, so the two orders can land on different final bit patterns.
