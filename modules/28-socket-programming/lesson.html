Socket Programming

Every browser tab, chat app, and database connection eventually comes down to the same handful of OS calls: socket, bind, listen, accept, connect, send, recv. This module walks through the client/server socket API using real client and server programs, byte order, and the read/write loop you need to move data reliably over a connection.

CS:APP reference: Chapter 11.4.  |  This material comes after Game 2 and is tested only on the comprehensive Final.

Learning objectives

  • Name the socket API calls a TCP server uses, in order, and what each one does
  • Name the socket API calls a TCP client uses, in order, and what each one does
  • Explain why network data needs a fixed byte order and what htons/htonl do about it
  • Read and write a loop that reliably sends or receives all the bytes of a message over a socket

1. A socket is just a file descriptor for the network

Everything in this module builds on one idea you already know: in Unix, "open a communication channel, get back an integer file descriptor, then read/write on it" is the same pattern for files, pipes, and now network connections. A socket is an endpoint for network communication, and the OS hands you back an int — a socket descriptor — that you use the same way you'd use a file descriptor from open().

The socket API sits below the application-layer protocols you've heard of (HTTP, DNS, SSH) and rides on top of the transport layer — almost always TCP for this course. In the OSI model's terms, everything above sockets (the message format, the meaning of the bytes) is up to your application; sockets just get bytes from one process to another reliably, in order.

FunctionSidePurpose
socket()bothCreate a new socket descriptor of a given type
bind()serverAssociate the socket with a local address/port
listen()serverPut a bound TCP socket into a state where it accepts incoming connections
accept()serverBlock until a client connects; return a new socket for that one connection
connect()clientEstablish a TCP connection to a server's address/port
send() / recv()bothWrite/read bytes on an established connection
close()bothTear down the connection and release the descriptor

2. The client: socket → connect → send/recv

A client's job is simple: build a socket, tell the OS where to connect it, then read and write. Here is the real client.c distributed for this course, connecting to a server on localhost: 

int sock = socket(AF_INET, SOCK_STREAM, 0);
if (sock == -1) {
    fprintf(stderr, "Could not create socket");
    exit(EXIT_FAILURE);
}

struct sockaddr_in server;
server.sin_family = AF_INET;
server.sin_port = htons(8080);
server.sin_addr.s_addr = inet_addr("127.0.0.1");

if (connect(sock, (struct sockaddr *)&server, sizeof(server)) < 0) {
    fprintf(stderr, "Could not connect to server");
    exit(EXIT_FAILURE);
}

AF_INET says "IPv4 address family"; SOCK_STREAM says "reliable, connection-oriented byte stream" — i.e. TCP. (The alternative, SOCK_DGRAM, gives you connectionless UDP datagrams instead — out of scope here, but it's why socket() takes a type argument at all.)

struct sockaddr_in is the address structure: an address family, a port, and an IPv4 address packed into a 32-bit field. connect() takes a generic struct sockaddr * — that's why the call casts &server — because the socket API is address-family agnostic; the same functions work for IPv4, IPv6, and Unix domain sockets, all of which lay out their address struct differently but the same size-prefixed way.

3. The server: socket → bind → listen → accept

A server needs two extra steps before it can talk to anyone: it has to claim a port (bind) and announce that it's ready for connections (listen). Then it loops, and each call to accept() blocks until a client shows up. Here's the real server.c: 

int server_fd, client_socket, read_len;
struct sockaddr_in address;
char buffer[BUFFER_SIZE];

// create server socket
server_fd = socket(AF_INET, SOCK_STREAM, 0);

// configure server address
address.sin_family = AF_INET;
address.sin_addr.s_addr = INADDR_ANY;
address.sin_port = htons(8080);

// bind socket to address
bind(server_fd, (struct sockaddr *)&address, sizeof(address));

// listen for incoming connections
listen(server_fd, 3);

// accept incoming connections
while (1) {
    client_socket = accept(server_fd, (struct sockaddr *)&address,
                            (socklen_t *)&address);

    // read data from client and echo back
    while ((read_len = recv(client_socket, buffer, BUFFER_SIZE - 1, 0)) > 0) {
        buffer[read_len] = '\0';
        send(client_socket, buffer, strlen(buffer), 0);
    }

    close(client_socket);
}

Three details worth noticing because they trip people up:

  • INADDR_ANY vs a specific IP. The client had to name a specific address (127.0.0.1) to connect to. The server binds to INADDR_ANY — "any interface on this machine" — so it accepts connections arriving on any of the machine's network interfaces, not just one.
  • accept() returns a new descriptor. server_fd stays open the whole time, listening for the next client. client_socket, the return value of accept(), is a separate descriptor dedicated to that one connection. This is the same shape as a file: the listening socket is like a directory handle, the accepted socket is like the file you actually read and write.
  • The 3 in listen(server_fd, 3) is the backlog — how many pending connections the OS will queue up before the server calls accept() on them.
Why does the server keep server_fd open in a loop instead of closing it after the first client connects?
server_fd only ever listens — the actual conversation with each client happens on the separate descriptor accept() returns. Closing the listening socket would mean no future client could ever connect.

4. Byte order: why htons exists

htons(8080) shows up in both programs, wrapping a plain integer literal. That's not decoration — it's converting the port number from your machine's native byte order to network byte order.

Different CPU architectures disagree about which byte of a multi-byte integer comes first in memory (x86 is little-endian; you saw this back in the integer representations module). If a little-endian machine sent the two bytes of 0x1F90 (8080 decimal) in its native order, and a big-endian machine on the other end interpreted those same bytes in its native order, they'd disagree on the value. The network protocol has to pick one order and enforce it — that's network byte order, which is big-endian.

FunctionDirectionSize
htons()host → networkshort (16-bit) — ports
htonl()host → networklong (32-bit) — IPv4 addresses
ntohs()network → hostshort (16-bit)
ntohl()network → hostlong (32-bit)

On a big-endian machine these functions are actually no-ops; on a little-endian machine (essentially everything you've used) they swap the byte order. Either way, calling them is what makes the code portable: you write the same source and it produces the correct on-the-wire bytes regardless of the CPU it's compiled for. This is exactly why server.sin_port = htons(8080) appears in both client.c and server.c — the port field of sockaddr_in is defined to hold a value in network byte order, full stop.

Both client.c and server.c call htons(8080) before storing the port in sockaddr_in. What would go wrong if they stored 8080 directly instead?
The sin_port field is specified to always hold its value in network (big-endian) byte order. On a little-endian CPU, skipping htons would store the bytes reversed, so the OS would bind/connect using a completely different 16-bit value than the one you intended.

5. The read/write loop: why one send() isn't enough

send() and recv() are allowed to transfer fewer bytes than you asked for — a "short count" — and still return successfully. A busy network, a full kernel buffer, or a large payload can all cause this. That's why client.c sends its message inside a loop rather than trusting a single call to deliver everything: 

char message[] = "hello world";
int num_bytes_sent = 0;
int result = 0;
int payload_size = strlen(message);

while (num_bytes_sent < payload_size) {
    result = send(sock, message + num_bytes_sent,
                   payload_size - num_bytes_sent, 0);

    if (result < 0) {
        fprintf(stderr, "Could not send data");
        exit(EXIT_FAILURE);
    }

    num_bytes_sent += result;
}

Each iteration advances the pointer (message + num_bytes_sent) and shrinks the remaining count by however many bytes actually went out (result), and the loop doesn't stop until everything has been sent. This is the same "don't assume the whole transfer happens in one call" discipline you should already have from buffered file I/O.

The server's receive loop follows the mirror-image pattern, reading until recv() returns 0 (the peer closed the connection) or a negative value (an error): 

while ((read_len = recv(client_socket, buffer, BUFFER_SIZE - 1, 0)) > 0) {
    buffer[read_len] = '\0';
    printf("Received: %s\n", buffer);
    send(client_socket, buffer, strlen(buffer), 0);
}

Notice buffer[read_len] = '\0': recv() gives you back raw bytes, not a C string, so the code has to manually null-terminate before treating it like one — and it sizes the buffer read as BUFFER_SIZE - 1 precisely so there's always room for that terminator without overflowing.

The pattern to remember: never treat a single send()/recv() call as "the whole message." Loop on the byte count until you've moved everything you expect, and check for 0 (peer closed) and negative (error) return values explicitly.
