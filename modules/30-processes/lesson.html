Processes

A process is the OS's unit of isolation: an independent, running instance of a program with its own private memory. The strangest — and most tested — idea in this module is fork(), a function that returns twice, once in each of two now-separate processes. We'll walk through real fork-based programs line by line to build the right mental model, then cover reaping children and replacing a process image with exec.

CS:APP reference: Chapter 12.1.  |  This material comes after Game 2 and is tested only on the comprehensive Final.

Learning objectives

  • Define a process and list what it owns (stack, heap, text, virtual memory, PID)
  • Explain fork()'s "returns twice" semantic and what each return value means
  • Trace the actual output of a real fork-based C program, including ordering caveats
  • Use wait()/waitpid() to reap a child and explain what a zombie process is
  • Explain what the exec family does and how it differs from fork()

1. What is a process?

A process is an instance of an executing program: the OS allocates it system resources — a stack, a heap, its program text (code), its own virtual address space, access to shared libraries — and tracks it as one independent, isolated unit. "Isolated" is the key word from the concurrency preview last module: unless a process goes out of its way to share memory through a file or a socket, nothing it does to its own memory is visible to any other process.

Every process has an ID, its PID, and every process (except the very first one the OS boots) has a parent — the process that created it. You can inspect this from the shell with ps (list process info) or pstree (view the parent/child hierarchy), or from inside a running C program with two functions: 

pid_t getpid(void);   // this process's own PID
pid_t getppid(void);  // this process's parent's PID

2. fork(): one call, two returns

The only way to create a new process is to clone an existing one. fork() does exactly that: it makes a near-exact copy of the calling process — same code, same data, same open files, same program counter position — and that copy becomes a new, independent child process. 

pid_t fork(void);  // function prototype

What makes fork() genuinely strange the first time you see it: it is called once, but it returns twice — once in the original (parent) process, and once in the brand-new (child) process, both resuming execution at the exact same point right after the call. The two calls are told apart purely by the return value:

  • In the child, fork() returns 0.
  • In the parent, fork() returns the child's PID (a positive number).
  • On failure, fork() returns -1 and no child is created.
child_pid = fork();
if (child_pid == 0) {
    printf("Child: Hi!\n");
} else {
    printf("Parent: Hi!\n");
}

Each process now has its own independent copy of the stack, data, and heap — from this point on, a variable the child modifies has no effect on the parent's copy, and vice versa. Under the hood, the OS doesn't actually duplicate all that memory up front (that would be the "relatively slow and heavy operation" mentioned in the Concurrency module) — it uses copy-on-write: parent and child initially share the same physical pages, marked read-only, and the OS only makes a private copy of a page at the moment either process tries to write to it. From the programmer's point of view you can and should just reason about it as "each process gets its own full copy" — the copy-on-write trick is a performance optimization, not a change in the semantics.

What does fork() return inside the newly created child process?
The child always gets 0 back from its call to fork(). The parent gets back a positive number — the new child's PID — which is how the parent process can later refer to that specific child (e.g. in waitpid()).

3. Tracing a real fork program

Here is example2.c, distributed for this course, in full: 

int main() {
    pid_t my_pid = getpid();
    pid_t parent_pid = getppid();

    printf("---- Start of main ----\n");
    printf("My PID is %d.\n", my_pid);
    printf("My parent's PID is %d.\n", parent_pid);

    printf("---- Calling fork ----\n");
    pid_t child_pid = fork();

    if (child_pid == 0) {
        printf("---- From child ----\n");
        my_pid = getpid();
        parent_pid = getppid();
        printf("My PID is %d.\n", my_pid);
        printf("My parent's PID is %d.\n", parent_pid);
    } else {
        int child_status;
        wait(&child_status);
        printf("---- From parent ----\n");
        printf("My child's PID is %d.\n", child_pid);
    }

    return 0;
}

Walk through it in order: the first three printfs run once, before fork() is ever called — there's only one process alive at that point, so there's only one copy of that output. The moment fork() returns, there are two processes both sitting right after that line, each about to evaluate the same if.

The child takes the child_pid == 0 branch and re-reads its own PID and parent PID — and it must re-read them, because the copies of my_pid/parent_pid it inherited from before the fork are stale: they held the parent's PID, not its own. The parent takes the else branch, calls wait() (more on this below), and then prints the child's PID — which it already knew, because fork() handed it back directly as the return value.

So the full output has the three "Start of main" lines exactly once, followed by the "From child" block and the "From parent" block — in that relative order here, because the parent's explicit wait() call forces it to pause until the child has finished and printed its own lines first. Without that wait(), the two blocks could interleave in either order, or even mix line-by-line, because the OS scheduler decides how the parent and child's execution actually interleaves — this is the same "don't assume an order" lesson from the Concurrency module.

In example2.c, why must the child re-call getpid()/getppid() after fork() instead of reusing my_pid/parent_pid computed before the fork?
fork() duplicates memory as it existed at the moment of the call — including whatever values were already stored in my_pid and parent_pid. Those held the original process's own PID/parent PID, which is now wrong from the child's perspective, so the child must query the OS again to get its own correct values.

4. Copy-on-write in action: example8.c

The isolation guarantee — "each process gets its own copy of memory" — is easy to state and easy to doubt until you see it demonstrated. example8.c uses a global variable, data_variable, that the child repeatedly increments in a loop: 

int data_variable = 1;

int main() {
    pid_t child_pid;

    switch (child_pid = fork()) {
    case -1:
        printf("An error occurred while creating process.\n");
        return -1;

    case 0:
        // This means I am the child
        printf("Child: Hi!\n");
        for (int i = 0; i < 10; i++) {
            printf("Child: Doing work... (%d)\n", data_variable++);
            sleep(1);
        }
        return 2;

    default:
        // This means I am the parent
        printf("Parent: Hi! Waiting for child to do some work.\n");
        int child_status;
        wait(&child_status);
        printf("Parent: Exit status from child = %d\n", WEXITSTATUS(child_status));
        printf("Parent: data_variable = %d\n", data_variable);
        break;
    }

    return 0;
}

The child increments data_variable ten times (1, 2, 3, ... 10) inside its loop. But when the parent finally prints data_variable after the child has exited, it prints 1 — completely unaffected by everything the child did. That's copy-on-write isolation made visible: the moment the child's first increment touched data_variable, the OS gave the child its own private physical copy of that page, and every further increment happened only in the child's copy. The parent's own copy of data_variable was never touched.

Notice also the switch here is just a different, equally valid way to branch on fork()'s return value compared to the if/else in example2.c: case -1 is the error path, case 0 is the child, and default (any positive PID) is the parent. And notice return 2; in the child — that becomes the child's exit status, which is exactly what the parent reads back out on the next line.

5. Reaping children: wait() and zombies

When a child process finishes, it doesn't just vanish — the OS keeps its exit status around until the parent collects it. A child that has terminated but hasn't yet been collected by its parent is called a zombie: it's no longer running, but it still occupies an entry in the OS's process table. 

pid_t wait(int *status);  // function prototype

Calling wait() from the parent blocks until some child terminates, reaps it (removing its zombie entry), and — if status is non-null — writes back information about how it exited, which macros like WEXITSTATUS() decode into the actual exit code, as seen in example8.c above. waitpid() is the more precise sibling: it can wait on one specific child PID rather than whichever child happens to finish first, which matters once a parent has spawned more than one child and needs to reap them individually.

Why this matters: if a parent never calls wait()/waitpid() on a child that has exited, that child stays a zombie indefinitely, wasting a process-table slot. If the parent itself exits without reaping, the zombie is "adopted" and eventually reaped by the init process — but a long-running parent (like a server) that keeps spawning children without ever reaping them can accumulate zombies until it exhausts the system's process table.

6. Running a different program: the exec family

fork() gives you a second copy of the same program. To actually run a different program in that new process, you follow it with a call from the exec family (execve, execvp, execl, ...). exec replaces the calling process's code, data, heap, and stack with those of a new program, loaded from disk — same PID, same open file descriptors, but everything else about what's running is swapped out. Unlike fork(), exec does not create a new process and does not return on success — if it returns at all, it means loading the new program failed.

Putting fork(), exec(), and wait() together is exactly how a shell works, and the lecture slides for this module say as much directly — you now have enough to sketch your own:

  1. Read a command line from stdin.
  2. fork() a child process.
  3. In the child, call exec to run the requested program.
  4. In the parent, wait() for that child to finish, then go back to step 1.

This is precisely why a fork/exec pair is so common: fork() gets you a new process to work with, and exec() turns that process into a run of an arbitrary other program — the two functions compose into "run this program and wait for it," which is the fundamental operation every shell performs for every command you type.

A shell needs to run /bin/ls as a subprocess and keep running afterward itself. Why does it call fork() before exec(), instead of just calling exec() directly?
exec() doesn't create a new process — it overwrites the current one. If the shell called exec() on ls directly, the shell process itself would turn into ls and never come back. Forking first gives you a disposable child process to exec into, leaving the original shell process (the parent) intact and free to wait() and then prompt for the next command.
