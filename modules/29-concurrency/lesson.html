Concurrency

A web server can't afford to handle one client at a time while everyone else waits — and a CPU with eight cores is wasted if only one core ever runs. Concurrency is the umbrella idea that lets a program make progress on more than one thing at once. This module surveys the three main ways to get it (processes, threads, I/O multiplexing) and previews the hazards that come with it, which modules 30 and 32 cover in depth.

CS:APP reference: Chapter 8.5, 12.7.  |  This material comes after Game 2 and is tested only on the comprehensive Final.

Learning objectives

  • Distinguish concurrency (interleaved progress) from parallelism (simultaneous progress)
  • Explain why concurrency and networking naturally go together
  • Name the three main approaches to concurrency and a defining trait of each
  • Describe, at a preview level, why shared state under concurrency causes race conditions

1. Concurrency vs. parallelism

These two words get used interchangeably in casual conversation, but the course textbook is precise about the difference:

"By concurrently, we mean that the instructions of one process are interleaved with the instructions of another process. In most systems, there are more processes to run than there are CPUs to run them." — CS:APP 1.7.1

Picture two people building two separate brick walls:

  • Serial: one bricklayer builds wall A, finishes, then builds wall B.
  • Concurrent: one bricklayer alternates — a few bricks on A, pause, a few bricks on B, pause, back to A. Only one wall is actually being touched at any instant, but both make progress over time.
  • Parallel: hire a second bricklayer. Both walls now have bricks being laid on them at the literal same instant.

Concurrency is about structure — a program is written to have multiple independent logical flows that interleave. Parallelism is about execution — whether the hardware actually runs more than one flow at the exact same instant. You can have concurrency without parallelism (many processes time-sliced on a single core, each making incremental progress), and you can have parallelism only when you have multiple cores to spread work across. Open a task manager on any modern computer: there are always far more processes running than there are physical cores, so the OS must be interleaving most of them concurrently even when a few happen to run in true parallel.

2. Why this matters now: cores stopped getting faster, they multiplied

For decades, Moore's Law (transistor counts on a chip doubling roughly every two years) let chipmakers ship faster and faster single cores, and existing sequential programs simply got faster for free with each new generation. That trend broke down: clock-rate scaling hit power and heat limits, and the industry pivoted to putting multiple cores on a single chip instead (modern designs like Intel's Alder Lake even mix "performance" and "efficiency" cores on the same die).

The consequence for you as a programmer: further performance gains increasingly require you to write code that can use more than one core, not just wait for the next chip to be faster. A CPU-bound program — one limited by CPU speed rather than by waiting on I/O — only benefits from extra cores if it's structured to split its work across them.

3. Three approaches to concurrency

At the level this course cares about, there are three ways to structure a program so multiple things can make progress at once:

ApproachIdeaGives parallelism?
ProcessesClone the running program into a second, fully independent instanceYes, across cores
ThreadsRun multiple logical flows inside one process, sharing its memoryYes, across cores
Async / I/O multiplexingOne flow of control, but never block waiting for slow I/ONo — one task runs at a time

Processes are created by cloning the currently running program (you'll see the exact mechanism, fork(), in the next module). It's a relatively slow, heavy operation precisely because the whole program's state gets duplicated. The payoff is isolation: by default, no memory is shared between processes at all — if one wants to share data with another, it has to do so explicitly, through a file or a socket.

Threads are the lighter alternative — roughly 10× faster to create than a process — because multiple threads live inside the same process and share its memory automatically. That shared-memory model simplifies communication (no file or socket needed to pass data between threads), but it's also exactly where the hazards below come from. Threads are provided and scheduled by the OS, just like processes.

Async (event-driven / I/O multiplexing) takes a completely different approach: instead of creating more logical flows of control, one single flow of control avoids ever blocking. It hands the OS a list of sockets or files it's waiting on (via select, poll, or epoll), and the OS tells it which ones are ready. While waiting for one client's slow I/O, the program can go handle a different client instead of sitting idle. This gives you a form of concurrency with none of the true simultaneity of parallelism — only one task actually executes at any instant — but it also sidesteps some of the problems that come with genuinely parallel execution.

Why concurrency and networking are almost always discussed together: the network is slow. Any program that talks to the network spends most of its time blocked, waiting for bytes to arrive. The natural question is "what do you do while you wait?" — and the answer, across all three approaches, is: handle another client in the meantime.
A server uses I/O multiplexing (select/poll) on a single core to handle 500 simultaneous client connections. Is this concurrent, parallel, both, or neither?
All 500 connections make progress over time by interleaving on the single core (concurrent), but since there is only one core actually executing, no two connections are ever serviced at the literal same instant (not parallel).

4. The cost of concurrency: it's hard, and here's why

Concurrency doesn't come for free. The human mind reasons sequentially by default, and a concurrent program can interleave its logical flows in an enormous number of different orders — the notion of "what happens before what" becomes misleading, because the scheduler (not your source code's top-to-bottom order) decides the actual interleaving. Reasoning through all possible orderings by hand is error-prone at best and often outright infeasible.

There's a well-known joke about this: "Some programmers, when confronted with a problem, think 'I know, I'll solve it with threads!' Now they have two problems." The punchline is the point of this section — concurrency solves a real performance/responsiveness problem, but introduces a distinct class of correctness problems that only show up under concurrent execution. Three classical failure modes:

  • Races. The outcome depends on an arbitrary scheduling decision made elsewhere in the system. Classic example: two people withdrawing from the same shared bank account at the same time — if both read the balance before either writes back the new balance, one withdrawal can silently vanish. This is the core hazard of shared, mutable state under concurrency, and it's exactly what module 32 (Threads) covers in depth, because threads share memory by default.
  • Deadlock. Improper resource allocation prevents any forward progress at all — like gridlocked traffic where every car is waiting on another car that can't move either. Each party is individually blocked waiting for something only another blocked party can release.
  • Livelock / starvation / fairness. External events or scheduling decisions repeatedly prevent one particular task from making progress, even though the system as a whole isn't stuck — like someone who keeps getting cut in line and never reaches the front.

The common thread underlying all three: as soon as more than one flow of execution can touch the same resource, you need some mechanism to synchronize access to it — a way to say "only one flow may do this step at a time," or "this flow must wait until that flow is done." Designing that correctly, without introducing deadlock, is the central challenge of concurrent programming, and it's the thread this course picks back up in module 32 with mutexes.

Why do processes largely avoid the race-condition hazard that threads are especially prone to?
Races require shared, mutable state accessed by multiple concurrent flows. Processes are isolated by default — no memory sharing unless done explicitly through a file or socket — so there's far less shared state to race on. Threads, by contrast, share their entire address space automatically, which is exactly why races are the headline hazard covered in the Threads module.
