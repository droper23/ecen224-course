Optimization

Every piece of x86-64 you've read so far in this unit has almost certainly been unoptimized — literal, verbose, one C statement mapping cleanly to a few instructions. Turn on the compiler's optimizer and the same source can compile to code that's faster, denser, and much harder to map back to the original C. This module covers what the optimization flags actually do, the transformations a compiler applies, and the one thing that reliably stops it from applying them.

CS:APP reference: Chapter 5.1–5.3.  |  Last lecture topic before Game 2 opens (Nov 9).  |  Tested on: Game 2 and the Final.

Learning objectives

  • Explain what the -O0 through -O3 optimization levels do, and why -O0 is the right level for learning to read assembly
  • Identify common compiler optimizations: code motion, strength reduction, common subexpression elimination, and inlining
  • Explain why a compiler treats every procedure call as an opaque "black box"
  • Explain memory aliasing and why it can force a compiler to generate more conservative code than expected

1. Two competing goals

Code has to satisfy two objectives that are often in tension: it has to be clear — readable by other people during code review, and maintainable when requirements change — and it sometimes has to be fast, because a real-time system (video processing, flight control) has a hard deadline, or because a computation (weather simulation, DNA sequence analysis) is expensive enough that a constant-factor speedup saves real days of compute time. Both objectives share one non-negotiable requirement underneath them: the program must still work correctly under every condition. Optimizing compilers exist to relax the tension a little — to get some of the speed benefit without asking the programmer to sacrifice clarity by hand.

2. Optimization levels: -O0 through -O3

GCC (and most C compilers) expose a family of optimization levels via a command-line flag. Each higher level enables more aggressive, and more expensive-to-compute, transformations:

FlagWhat it does
-O0No optimization. Each C statement compiles about as literally and independently as possible — variables are reloaded from memory rather than kept in registers across statements, redundant work isn't removed, nothing is reordered. This is why essentially every example earlier in this unit has been -O0 code: it maps directly back to the source, which is exactly what you want while you're learning to read assembly.
-O1Basic optimizations with modest compile-time cost: simple dead code elimination, some register allocation improvements.
-O2The level most production software actually ships with. Enables inlining, stronger register allocation, instruction scheduling, and most of the transformations covered below.
-O3Adds more aggressive, sometimes riskier transformations aimed at numerical and loop-heavy code, such as more ambitious vectorization.

The practical consequence for this course: when you disassemble a real production binary (as in the Binary Bomb Lab), you should expect -O2-style code, not the -O0 code used to build intuition in lecture. -O2 assembly reuses registers aggressively across many source lines, reorders operations, and sometimes has no instruction that corresponds to any single line of the original C — it's harder to read, but it's what you'll actually encounter in the wild.

3. What optimizing compilers actually do

An optimizing compiler is not searching for a fundamentally better algorithm — that's still entirely the programmer's job; swapping an O(n²) insertion sort for an O(n log n) quicksort is a bigger win than any compiler flag, and no compiler will do that rewrite for you. What a compiler can do is provide a more efficient mapping of the algorithm you wrote onto the machine: better register allocation, better instruction selection and scheduling, dead code elimination, and a handful of well-known local transformations.

Code motion (loop-invariant hoisting)

If a computation inside a loop produces the same result on every iteration, it only needs to run once, outside the loop: 

/* before: n*i is recomputed every iteration */
void set_row(double *a, double *b, long i, long n) {
    long j;
    for (j = 0; j < n; j++)
        a[n*i + j] = b[j];
}

/* after: code motion pulls the invariant part out of the loop */
void set_row_opt(double *a, double *b, long i, long n) {
    long j;
    long ni = n * i;         /* computed once */
    for (j = 0; j < n; j++)
        a[ni + j] = b[j];
}

Strength reduction

Replace an expensive operation with a cheaper one that produces the same result — a multiply by a constant becomes a shift, or a running total replaces repeated multiplication inside a loop: 

/* 16*x can become x << 4 -- a shift instead of a multiply */
/* 2*x can become x+x -- an add instead of a multiply */

/* strength-reduced loop: track n*i incrementally instead of
   recomputing the multiply every iteration */
int ni = 0;
for (i = 0; i < n; i++) {
    for (j = 0; j < n; j++)
        a[ni + j] = b[j];
    ni += n;          /* one add replaces one multiply per outer iteration */
}

Whether this actually helps depends on the target machine: it's only a win if a multiply instruction genuinely costs more cycles than the add or shift it's replaced with, which is true on some processors and not others.

Common subexpression elimination (CSE)

If the same subexpression is computed more than once, compute it once and reuse the result: 

/* before: i*n is computed three separate times */
up    = val[(i-1)*n + j];
down  = val[(i+1)*n + j];
left  = val[i*n     + j-1];
right = val[i*n     + j+1];

/* after: share the common i*n term */
long inj = i*n + j;
up    = val[inj - n];
down  = val[inj + n];
left  = val[inj - 1];
right = val[inj + 1];

The hand-optimized version needs just one multiplication (i*n) instead of three (i*n, (i-1)*n, (i+1)*n) — every other access is reached by cheap addition or subtraction from the shared base. Compilers apply CSE, but they're often not sophisticated enough to spot every arithmetically-equivalent rewrite a human would — this is exactly the kind of thing worth doing by hand in performance-critical code.

Inlining

Replace a function call with a copy of the callee's body directly at the call site, eliminating call/return overhead and opening the door to further optimization across what used to be a call boundary. GCC applies this automatically at -O2, and the inline keyword is a hint a programmer can give the compiler to encourage it for a specific function.

You disassemble a stripped production binary and the code doesn't map cleanly onto any single C statement — registers are reused across what look like several unrelated computations. What most likely happened?
-O0 is the literal, one-statement-at-a-time mode. Dense, register-reusing, hard-to-trace-back-to-source code is the signature of -O2/-O3 optimization — and it's what you should expect in most real-world disassembly.

4. Optimization blocker #1: procedure calls

Consider a function that lowercases a string, called on a string of length N: 

void lower(char *s) {
    int i;
    for (i = 0; i < strlen(s); i++)
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] -= ('A' - 'a');
}

This looks like a simple O(N) loop, but it isn't: strlen(s) is called again on every single pass through the loop, and strlen itself has to walk the whole string looking for the terminating NUL. Calling it N times inside a loop that runs N times makes lower O(N²) overall — measured performance confirms it: running time quadruples when the string length doubles, the signature of quadratic growth. Hoisting the call out by hand, 

void lower2(char *s) {
    int i;
    int len = strlen(s);      /* compute once */
    for (i = 0; i < len; i++)
        if (s[i] >= 'A' && s[i] <= 'Z')
            s[i] -= ('A' - 'a');
}

restores linear, O(N) behavior — time now merely doubles when the string length doubles. The natural question is: this is exactly the kind of loop-invariant code motion from the previous section, so why didn't the compiler just do it automatically?

Because the compiler cannot prove it's safe. A function call is opaque to the optimizer — it's treated as a black box, because the compiler has no general way to guarantee that calling strlen(s) a second time returns the same value as the first. Maybe strlen has a side effect (updates some global counter); maybe s itself changed between calls (and here it genuinely does — lower is mutating the very string strlen is scanning); maybe strlen isn't even defined in this source file, so there's nothing to analyze at all. Rather than risk changing the program's observable behavior, the compiler falls back to calling it every time, exactly as written. The fix has to come from the programmer: do the code motion yourself, or mark the function inline so the compiler can see through the call boundary.

5. Optimization blocker #2: memory aliasing

Aliasing is when two different expressions can refer to the same memory location. C makes this easy to run into, especially with pointers — nothing stops two pointer parameters from pointing into overlapping memory. Consider summing the rows of an n×n matrix into a vector: 

void sum_rows1(double *a, double *b, long n) {
    long i, j;
    for (i = 0; i < n; i++) {
        b[i] = 0;
        for (j = 0; j < n; j++)
            b[i] += a[i*n + j];
    }
}

You might expect the compiler to keep the running sum in a register and only write to b[i] once, after the inner loop finishes, rather than writing to memory on every single iteration of j. But the actual generated code writes to b[i] every time through the inner loop: 

# sum_rows1 inner loop
.L53:
  addsd (%rcx), %xmm0        # load a[i][j], add into running sum
  addq  $8, %rcx
  decq  %rax
  movsd %xmm0, (%rsi,%r8,8)  # store to b[i] -- every iteration
  jne   .L53

The reason is aliasing: nothing in the function signature rules out a and b overlapping in memory. If a caller passes overlapping arrays — say, b pointing partway into a — then whether an intermediate write to b[i] happens on every inner-loop iteration or just once at the end can change the final answer, because later reads of a might actually be reading values that were just written through b. The compiler has no way to prove a and b don't overlap for an arbitrary caller, so it must be conservative and preserve the exact number and order of writes specified by the source.

The fix, once again, is for the programmer to supply the guarantee the compiler can't derive on its own — accumulate into a genuinely local variable that cannot alias anything, and write to memory only once: 

void sum_rows2(double *a, double *b, long n) {
    long i, j;
    for (i = 0; i < n; i++) {
        double val = 0;             /* local, provably not aliased */
        for (j = 0; j < n; j++)
            val += a[i*n + j];
        b[i] = val;                 /* single write, after the loop */
    }
}

Because val is a local variable whose address is never exposed, the compiler can prove nothing else can be reading or writing it, and the inner loop collapses to pure register arithmetic with no memory store at all: 

# sum_rows2 inner loop
.L66:
  addsd (%rcx), %xmm0   # load a[i][j], add into running sum
  addq  $8, %rcx
  decq  %rax
  jne   .L66
The pattern to remember: a compiler will not perform a transformation it cannot prove is safe for every possible input — including pathological ones, like overlapping arrays, that a reasonable caller would never actually pass. When you know a guarantee the compiler can't see (arguments don't alias, a function call has no side effects), encoding that guarantee yourself — via a local variable, a restrict-qualified pointer, or manual code motion — is often the only way to unlock the optimization by hand.
Why couldn't the compiler automatically turn sum_rows1's per-iteration write to b[i] into a single write after the inner loop, the way sum_rows2 does by hand?
This is memory aliasing: without a guarantee that a and b don't overlap, the compiler must assume a caller could pass overlapping pointers, in which case eliminating the intermediate writes would change what later reads of a see. It has to stay conservative.
