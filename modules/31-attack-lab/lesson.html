Attack Lab

The Attack Lab is the hands-on flip side of module 21's buffer-overflow lecture: instead of reading about a stack-smashing vulnerability, you exploit one yourself, against a binary that's uniquely randomized for you. This module isn't a lecture summary — it's a strategy primer on the workflow, the tools, and the concepts you'll actually need at the terminal.

This is a hands-on programming assignment, not a lecture — but it directly exercises the buffer-overflow concepts from module 21, which ARE tested on the Final.

Learning objectives

  • Explain what the Attack Lab is and why it exists as a hands-on complement to module 21
  • Describe the general workflow for finding and exploiting a stack buffer overflow
  • Identify the purpose of each tool involved: objdump, gdb, and a hex-encoding helper
  • Explain why this skill is taught for defensive understanding, not for attacking real systems

1. What this assignment is, and why it exists

Module 21 taught you, in the abstract, that writing past the end of a fixed-size stack buffer can corrupt the data sitting above it in memory — including the saved return address that tells a function where to resume execution when it returns. That's a striking claim. The Attack Lab is BYU's way of making you prove it to yourself: you're handed a small, uniquely-randomized vulnerable binary, and your job is to craft an input string that doesn't just crash it, but controls it — redirects its execution to code of your choosing.

The assignment is organized as five independent exploit phases, each pushing the technique further:

PhaseTechnique
1Redirect the return address to an existing function
2Inject new code into the stack and jump to it
3Inject new code and new data
4"Gadget farm" — chain together small existing instruction sequences (a return-oriented-programming style attack, useful when the stack itself can't be executed)
5Extra credit, combining ideas from the earlier phases

You don't have to repeat an earlier phase's exploit to attempt a later one — each phase is independent — but working through them in order is strongly recommended, since each builds directly on the disassembly and offset-finding skills from the one before it. There's no penalty for failing to exploit a given phase, and successful exploits are reported to a class leaderboard.

Every student's target binary is randomized, so there is no single "correct answer" to memorize — the specific offset, the specific address, the specific bytes you need all differ from student to student and must be discovered by inspecting your own target with the tools below. This module deliberately stays at the strategy level for that reason: what to look for and why, not what any particular address happens to be.

2. The general workflow

Every phase of this lab follows roughly the same sequence of steps, regardless of which exploit technique it calls for:

  1. Disassemble the vulnerable function. Find the specific function in your target that reads unbounded input into a fixed-size stack buffer — that's the vulnerability module 21 warned about. Read its disassembly to understand exactly how it sets up its stack frame.
  2. Find the buffer's offset to the saved return address. The whole exploit hinges on knowing exactly how many bytes separate the start of the buffer you're writing into from the saved return address sitting higher up the stack. Get this number wrong by even one byte and you'll corrupt the wrong data instead of gaining control. You work this out from the stack frame layout you saw in the disassembly — how much space the compiler reserved for the buffer, plus any other saved state between it and the return address.
  3. Decide what needs to be overwritten, and with what. Every phase comes down to the same question: which bytes at that offset do I need to replace, and with what value? For a simple redirect, it's just a new return address. For code injection, it's a return address plus a sequence of machine instructions placed somewhere the CPU will execute. For a gadget farm, it's a chain of addresses, each pointing at a short existing instruction sequence ("gadget") that does one small useful thing and then returns into the next gadget.
  4. Encode and deliver the exploit string. Once you know the byte sequence you need, you turn it into the actual raw bytes the vulnerable input-reading function will consume.
The one idea underlying all five phases: a stack buffer overflow lets you write attacker-controlled bytes into memory the program didn't intend for you to control — and if that memory includes a saved return address (or, in later phases, other data the control flow depends on), you've turned "I can write past the end of an array" into "I can make the CPU execute what I want."
Why does finding the exact offset from the buffer to the saved return address matter so much?
The exploit works by placing specific bytes at a specific stack location. If your offset is off by even a little, you'll either fail to reach the return address at all, or overwrite the wrong bytes and most likely just crash the program instead of redirecting it.

3. Your tools

ToolRole in the workflow
objdumpDisassembles the target binary into readable x86-64 assembly so you can study the vulnerable function's stack frame layout. A typical first step is dumping the whole binary to a file you can search through: objdump -d target > target.txt.
gdbLets you actually run the target under a debugger, set breakpoints inside the vulnerable function, and inspect the stack and registers live — invaluable for confirming the offset you worked out from the disassembly is actually correct before you commit to an exploit string.
a hex-encoding helper (hex2raw)Converts a human-readable hex string you construct (the bytes of your exploit) into the actual raw byte string the target program reads as input.
gccAvailable for compiling and assembling, useful if you want to test ideas about instruction encoding locally before targeting the real binary.

One detail worth flagging because it explains a strange step in the setup instructions: modern Linux distributions ship stack-protection mitigations on by default that would block this exact class of exploit. That's precisely why the assignment can't be done on a typical up-to-date lab machine — you SSH into a dedicated course server configured without those protections, so the underlying vulnerability is actually exploitable the way it would have been on an unprotected system. Your target binary also ships with debug information turned on, so both gdb and objdump can show you function and variable names directly rather than raw addresses only.

4. Why this is worth learning

It's worth being explicit about the purpose here: this lab exists to teach you to recognize and defend against buffer-overflow vulnerabilities, not to attack systems you don't own or have permission to test. The reason working exploit code is such an effective teacher is that it removes all ambiguity — a program either got hijacked by your crafted input or it didn't. Once you've personally walked a return address through a stack overflow, the defensive advice from module 21 (bounds-check every buffer write, prefer length-limited functions, treat stack-protection mechanisms like canaries as real mitigations rather than boilerplate) stops being abstract advice and becomes something you've seen the necessity of firsthand.

Scope reminder: everything in this lab targets a binary specifically built and distributed for this purpose, running on a server set up for it. The techniques generalize, but using them against systems you don't own or don't have explicit authorization to test is illegal, independent of how the skill was acquired.
Why does the Attack Lab have to run on a special course server (via SSH) instead of a normal up-to-date lab machine?
Current Linux distributions enable stack-protection defenses by default specifically to stop attacks like the ones this lab teaches. To let you actually exploit the vulnerability the way module 21 described it, the assignment runs on a server (ssh.et.byu.edu) set up without those protections.
