C Programming Lab — Part 2: Data Types & Strings

Where Part 1 introduced C's native types, this lab is about the ways picking the wrong one bites you: overflow, underflow, sign/zero extension, truncation, and integer promotion in mixed-type expressions. The second half covers C strings — which don't exist as a real type, only as null-terminated char arrays — and the specific bug of returning a pointer to a local array. You implement and debug real functions against provided test cases, using a small logging library instead of scattered printf calls.

Tested on: sign/zero extension and truncation are Game 1 and Final material (Module 03 — Integer Representations); the local-array-pointer bug previews stack-frame reasoning from Unit 4.
Official lab page: This primer covers the concepts — for exact CAEDM setup steps, starter code, and the TA pass-off checklist, use the official page: byu-cpe.github.io/ecen224/labs/04_data-types-and-strings.

Learning objectives

  • Explain why native C integer types (short/int/long) aren't a fixed size, and why stdint.h types (uint32_t, etc.) are safer
  • Trace what happens to a value under sign extension, zero extension, and truncation when casting between integer sizes
  • Predict which operand type "wins" when an expression mixes integer types (integer promotion)
  • Explain why C strings are just char arrays with a null terminator, not a real type
  • Identify why returning a pointer to a function-local array is unsafe, and how to fix it

1. Why stdint.h instead of int

short, int, and long have no size the C standard guarantees — only a minimum. Code that assumes int is 4 bytes can silently break on a platform where it isn't, which is exactly the kind of bug that's invisible until it isn't. stdint.h types like uint8_t, uint32_t, and int16_t pin down both the width and signedness in the name itself, which is why the lab (and the rest of the course) prefers them over native types.

Failure modeWhat happens
OverflowA uint8_t loop counter compared against 500 never reaches it — it wraps at 255 back to 0 forever
UnderflowDecrementing an unsigned 0 wraps to the type's max value (e.g. 4,294,967,295 for uint32_t) instead of going negative

There's a real memory-vs-safety tradeoff here too: a 4K image stored one byte per color channel (uint8_t) is about 25MB; the same image at uint64_t per channel would be roughly 200MB for identical color information. Bigger types reduce overflow risk but aren't free.

2. Sign extension, zero extension, truncation

These three describe what happens to the bits when you cast between integer sizes — the same material as Module 03 (Integer Representations), applied directly in code instead of on paper.

OperationWhenWhat happens
Sign extensionsigned type → larger signed typethe sign bit (MSB) is copied into all the new high-order bits, preserving the value
Zero extensionunsigned type → larger typethe new high-order bits are filled with 0
Truncationlarger type → smaller typethe extra high-order bits are simply dropped — data loss if they held meaningful information

Float/double casts follow the same shape: float → double is a safe, precision-gaining widen; double → float can lose precision and rounds the value to fit.

Integer promotion: in a mixed-type expression, smaller-than-int types get promoted to int/unsigned int before any arithmetic happens, and double dominates float which dominates integers. This is why uint8_t a = 200, b = 100; int sum = a + b; gives you 300, not a wrapped-around value — the addition itself happens in int, after promotion, before the result is ever stored back into a narrower type.

3. C strings and the local-array-return bug

C has no string type. A "string" is a char array ending in a null terminator (\0), and every string.h function — strlen(), sprintf(), strcpy(), strncat(), strncmp() — is really just doing array/pointer arithmetic that stops (or doesn't) at that byte.

Classic bug: a function that declares a local char buf[64] and returns buf is returning a pointer to memory that no longer belongs to it — that stack space is reclaimed the instant the function returns. The fix is to have the caller own the memory: pass a char * buffer in as a parameter and have the function fill it, instead of trying to hand memory back out. This is your first real encounter with the idea that a local variable's lifetime ends at its function's return — the same stack-frame reasoning Unit 4 covers explicitly.

4. Debugging: trace prints and a logging library

The lab pushes intentional and incremental programming: write small, testable pieces on purpose rather than large blocks you debug after the fact. Its recommended debugging technique is trace debugging — printing variable values at chosen points to see what the program actually did, versus what you assumed it did.

Scattering raw printf calls works but is hard to find and remove later, so the lab has you use a small logging library (log.c) instead: 

#include "log.h"
...
int value = 42;
log_info("The value is %d", value);

11:56:31 INFO  main.c:9: The value is 42

log_debug, log_warn, and log_error work the same way, each tagging output with a level so you can grep for it or strip it out later — a small taste of the structured debugging habits Module 12 (Debugging) covers more generally.

A function declares char result[32];, fills it in, and returns it as a char *. The caller prints garbage. Why?
A local array's memory belongs to its function's stack frame, which is reclaimed the moment the function returns. The returned pointer still points at that address, but nothing guarantees the data there is preserved — the fix is to have the caller pass in a buffer for the function to fill instead.
uint8_t a = 200; uint8_t b = 100; int sum = a + b; — what does sum end up holding?
Integer promotion means both uint8_t operands are converted to int before the + runs, so the arithmetic happens at full int width. The overflow only would have occurred if the addition happened at 8-bit width, or if the 300 were later truncated back into a uint8_t.
