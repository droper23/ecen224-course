Doorbell Lab

The capstone: everything from Image through Threaded Client becomes one cohesive "ding, snap, upload" appliance, plus one genuinely new skill — making the program start itself as a background daemon on every boot, via systemd.

Tested on: not itself exam content, but it's the integration point for nearly every systems concept the course has taught — the concepts threaded through it (memory, pointers, sockets, concurrency) are comprehensive-Final material.
Official lab page: This primer covers the concepts — for exact CAEDM setup steps, starter code, and the TA pass-off checklist, use the official page: byu-cpe.github.io/ecen224/labs/11_doorbell.

2. Daemons and systemd, in one paragraph

A normal program runs because a user typed a command and is watching a terminal. A daemon is a background program nobody directly launched — sshd, the process quietly listening for SSH connections, is the example the lab points to. On Linux, systemd is what manages this: "a system and service manager that runs as the first thing your computer boots" (PID 1). You interact with it through systemctl (start, stop, status, enable, disable), and you tell it about your own program with a unit file. 

# doorbell.service (goes in /etc/systemd/system, needs sudo)
[Unit]
Description=Smart doorbell

[Service]
WorkingDirectory=/home/pi/doorbell
ExecStart=/home/pi/doorbell/doorbell   # absolute path -- relative paths don't work here

[Install]
WantedBy=multi-user.target

systemctl enable doorbell is what makes it survive a reboot rather than just running until systemctl stop. Test with start/status first — confirming it runs on demand — before trusting it to also run automatically after a real reboot.

3. The boot race condition

Enabling on boot introduces a timing problem that never showed up when you launched the program by hand from a terminal: at boot, a separate program displays the Pi's IP address on the screen before other services are necessarily ready, and the doorbell program can start racing against it for control of the display. The fix the lab prescribes is blunt but effective — a 15-second sleep() at the top of main() before the doorbell touches the display, giving the IP-address program time to finish first. It's a real example of a race condition being solved by sequencing rather than synchronization, worth noticing precisely because it's the crude version of a problem Concurrency covers more rigorously.

4. The hidden menu: a tiny state machine

Detecting the sequence Up, Up, Down (in that order, presumably within some reasonable time of each other) to reveal a file-browser menu is a small state machine layered on top of button handling you already have. The general shape — track how far into a target sequence the last few inputs match, reset on a mismatch, trigger on a full match — is the same pattern you'd use for any input-sequence detector, not something specific to this hardware.

The doorbell runs fine when launched by hand from a terminal, but on an actual reboot the display sometimes shows garbled output before settling. What's the lab's fix, and why?
This is a boot-time race condition against another program that also uses the display. The lab's fix is a fixed delay before the doorbell touches the display, giving the other program time to finish — a sequencing fix, not a synchronization primitive.
What does systemctl enable doorbell do that systemctl start doorbell does not?
start runs the service immediately, once. enable registers it to be started automatically by systemd on every subsequent boot — the two are independent and this lab needs both, tested separately.
