Threaded Client Lab

Moves the slow network upload from the Client lab off the main loop and onto a POSIX thread, so the doorbell's menu stays responsive while a photo is sending — plus a status bar that has to reflect thread progress without ever calling display code from inside the thread itself.

Tested on: hands-on CAEDM work, not itself graded exam content — but pthread_create, shared state between threads, and stack-vs-heap lifetime are directly tested on the Final.
Official lab page: This primer covers the concepts — for exact CAEDM setup steps, starter code, and the TA pass-off checklist, use the official page: byu-cpe.github.io/ecen224/labs/10_threaded-client.

Learning objectives

  • Explain why a blocking network call on the main loop freezes the whole UI
  • Spawn a pthread_create thread that runs a function taking a void * argument
  • Identify why data passed into a thread must outlive the stack frame that launched it
  • Track a background thread's progress with shared state, without calling non-thread-safe display code from inside the thread

1. The bug you're fixing: everything blocks on everything

Run send_image directly from the button handler, before threading it, and you'll see the problem the lab wants you to feel: the menu freezes for as long as the upload takes. That's because a single-threaded program can only be doing one thing at a time — while send()/recv() block waiting on the network, nothing else in the process, including the code that redraws the screen or reads button input, gets to run at all.

2. pthread_create and the void * contract

Threading fixes this by giving the upload its own thread of execution, separate from the main loop. pthread_create takes four arguments: a pthread_t * to write the new thread's ID into, an attributes pointer (NULL for this course), a function pointer for the thread to run, and a void * argument passed straight through to that function. The void * is how you hand the thread whatever it needs (host, port, image buffer, length) as one bundled struct, cast back to its real type on the other side.

Watch for: passing the address of a local (stack) variable into pthread_create and then letting the calling function return. The thread may still be running against that address after the stack frame that owned it is gone — a classic use-after-free-shaped bug. Heap-allocate (or use file-scope/global storage for) anything a thread needs to keep using.

3. Progress without touching the display from the thread

The lab is explicit: don't call display functions from inside the thread. The display API isn't thread-safe, so drawing has to stay on the main loop. The pattern that satisfies both constraints is a shared state variable the thread updates (e.g. an enum: idle → sending → sent) and the main loop polls every frame to decide what the status bar should currently show and for how long.

pthread_join() exists for retrieving a thread's return value, but the lab specifically avoids it here — joining would block the caller until the thread finishes, which defeats the entire point of moving the upload off the main loop in the first place.

Why does the lab explicitly avoid pthread_join() right after spawning the upload thread?
pthread_join() waits for the target thread to finish before returning. Calling it right after pthread_create() would re-introduce the blocking behavior the lab is trying to eliminate.
A function running on the upload thread wants to update the on-screen status bar directly. What's wrong with that?
The lab is explicit that display functions must not be called from inside the thread. The safe pattern is the thread setting a shared status variable and the main loop reading it each frame to decide what to draw.
