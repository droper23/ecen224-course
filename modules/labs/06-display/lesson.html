Display Lab

Your code starts controlling real hardware: a Waveshare LCD + button HAT sitting on top of the Raspberry Pi Z2W that will become the doorbell. You link against a vendor GPIO library, draw shapes and text to the screen, read button input, and build a small selectable menu system — the first piece of the doorbell's actual user interface.

Tested on: not exam-tested directly. But this is where "linking against a library" (Module 13) and "structs/pointers as an API surface" (Modules 09–10) stop being abstract and start being how you talk to a physical device.
Official lab page: This primer covers the concepts — for exact CAEDM setup steps, the BCM2835 library install, starter code, and the TA pass-off checklist, use the official page: byu-cpe.github.io/ecen224/labs/06_display.

Learning objectives

  • Explain what GPIO pins are and why they're the standard way to attach peripherals to an SBC
  • Build a C project with a Makefile instead of manual gcc invocations, and explain what incremental compilation buys you
  • Link against a third-party vendor library (BCM2835) using -l
  • Call a peripheral's header-defined API (display.h, buttons.h) to draw shapes/text and read input
  • Design a stateful menu loop: current selection, wraparound, and dispatch to a handler function

1. From GPIO pins to a header file

The LCD/button HAT physically occupies all 40 GPIO pins on the Pi. Underneath, everything is just reading and writing specific memory-mapped registers at specific voltages and timings — but you never touch that layer directly. The BCM2835 library handles the low-level GPIO access, and on top of that, the lab gives you display.h, buttons.h, and device.h: ordinary C header files whose functions happen to have hardware side effects instead of just computing values in memory.

This is the same relationship you already know from Module 13 (Linking): your test.c calls functions it doesn't define, the linker resolves them against the library's object code, and at that point it genuinely doesn't matter to your source file whether the function prints to a terminal or lights up a physical pixel.

Watch out: display_init() must run before buttons_init(), or you'll segfault. And because the program needs raw hardware access, it must be run with sudo.

2. Building with a Makefile

Instead of retyping a long gcc command with library flags every time, the lab gives you a Makefile: make test or make <filename> compiles only the .c files that changed since the last build (tracked via their .o object files), then re-links. As your projects grow across the rest of the semester (display → file → camera → client → doorbell), this is what keeps rebuilds fast instead of recompiling everything from scratch every time you fix one line.

3. Drawing functions and the menu system

The drawing API is parameterized by coordinates (against DISPLAY_WIDTH / DISPLAY_HEIGHT), a font size (Font8 through Font24), and a color constant from colors.h. Required warm-up functions (clearScreen, drawHelloWorld, drawChars, drawStars, drawFlag) exist to get you comfortable calling that API before the real deliverable: a menu driven by an entries array of item names.

Menu requirementWhat it means
Idle stateNo redraw or action happens while no button is pressed — don't busy-loop-redraw every frame.
Highlighted selectionExactly one entry is drawn in a distinct color at any time.
Up/down navigationMoves the current-selection index; must wrap past the first/last entry instead of getting stuck.
Right = selectDispatches to the function tied to the highlighted entry name (e.g. selecting "Flag" calls drawFlag), waits, then redraws the menu.

Structurally this is a small state machine: one integer (the current index) plus a dispatch table mapping entries to handler functions. That pattern — and the wraparound arithmetic ((i + 1) % n style logic) — is exactly what Lab 07 (File) reuses for its own file-browser menu, so get it solid here.

4. Skills you'll need

  • Module 09 — Arrays, Strings & Structs: the entries array and how string arrays are indexed.
  • Module 10 — C Pointers: header-declared functions taking pointers/handles to hardware state.
  • Module 02 — Information Storage: colors here are just packed integers, the same bit-level reasoning as the byte/hex material in this module.
  • Lab 05 — Image: not a strict prerequisite, but the same "index into a flat data buffer correctly" mindset applies to screen coordinates here.
Your menu has 4 entries (indices 0–3) and the current selection is index 3. The user presses "down." What should the new selection be if the menu wraps correctly?
The lab explicitly requires wraparound: moving past the last entry returns to the first. With 4 entries, (3 + 1) % 4 == 0.
Why must display_init() be called before buttons_init()?
This is a real, documented ordering requirement of the hardware initialization sequence — get it backwards and the program segfaults before you even reach your own logic.
