Camera Lab

Wires a real camera into the doorbell project: capture a picture into a heap buffer, strip its BMP header, render it to the display, and reuse the filters you wrote in the Image lab — all triggered from the button you've already wired up in Display.

Tested on: this is hands-on CAEDM/hardware work and isn't graded content itself, but the buffer-parsing and heap-allocation discipline it builds is directly tested on Game 2 and the Final.
Official lab page: This primer covers the concepts — for exact CAEDM setup steps, starter code, and the TA pass-off checklist, use the official page: byu-cpe.github.io/ecen224/labs/08_camera.

Learning objectives

  • Capture a picture from the camera into a heap-allocated buffer
  • Explain why the raw capture is a full BMP file, not bare pixel data
  • Parse that buffer into a Bitmap struct and render it with the display API
  • Persist a captured image to disk with fopen/fwrite/fclose
  • Reuse prior filter functions against newly captured (not just file-loaded) image data

1. The buffer you get back isn't pixels — it's a file

camera_capture_data hands you a uint8_t * buffer, and it's tempting to assume that buffer is just rows of pixels you can draw directly. It isn't: it's the bytes of a complete .bmp file, header included. That's the same BMP header format you parsed in the Image lab — the difference here is you're seeing it live, straight out of a driver, instead of loaded from a file someone else already exported for you.

That's why the workflow goes through create_bmp before anything touches the screen: it walks the header to find where pixel data actually starts and hands you back a Bitmap struct whose pxl_data field is the part you can actually draw. Skip that step and you'll render header bytes as if they were pixels — garbage color noise at the top-left of a corrupted-looking image is the classic symptom.

2. Every allocation gets a matching release

This lab is where the malloc/free discipline from Dynamic Memory stops being an abstract rule and starts being something a TA actually checks: the Makefile builds with -Werror, and pass-off explicitly includes a no-leak check. The capture buffer, the Bitmap struct from create_bmp, and anything a filter allocates all need their release call before the function returns or the program exits.

AllocateRelease
malloc (raw capture buffer)free
create_bmpdestroy_bmp
fopen (writing doorbell.bmp)fclose
Watch for: a capture-and-display path that exits early (an error branch, a button that cancels mid-capture) is the easiest way to leak — every early return still owes the same frees as the normal path.

3. Reusing Image-lab filters against a live capture

remove_color_channel and or_filter from the Image lab were written against a buffer you loaded from a file. Porting them here works precisely because you already isolated the pixel-manipulation logic from the file-loading logic back then — the filters don't care whether pxl_data came from fopen or from create_bmp on a fresh capture, as long as the width, height, and per-pixel layout match. If a filter assumed something about how the buffer was obtained, this is where that assumption breaks.

camera_capture_data returns a buffer. Why can't you pass that buffer straight to display_draw_image_data?
The raw capture is a complete .bmp file, header and all — exactly like a file you'd load from disk. create_bmp parses that header so you get back a struct whose pxl_data is safe to draw.
