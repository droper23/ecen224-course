C Programming Lab — Part 1

Your first real C program, taken apart stage by stage. Instead of just running gcc simple.c and moving on, this lab walks gcc's four stages — preprocessing, compiling, assembling, linking — one command at a time, so you can inspect the intermediate output of each. The back half is a small challenge program that forces you to actually use C's native data types and printf format specifiers instead of just reading about them.

Tested on: the compilation pipeline is exactly Module 13 (Linking) material, and the data-type/casting content is directly tested on Game 1 and the Final.
Official lab page: This primer covers the concepts — for exact CAEDM setup steps, starter code, and the TA pass-off checklist, use the official page: byu-cpe.github.io/ecen224/labs/03_c-programming.

Learning objectives

  • Compile a C program with gcc and name its output with -o
  • Explain what each of the four compilation stages produces: preprocessed source, assembly, object code, and a linked executable
  • Identify C's native data types by size and describe what determines their range
  • Explain explicit vs. implicit casting, and why casting into a too-small type produces unexpected values
  • Use printf format specifiers correctly for different data types

1. The four stages of gcc

Running gcc simple.c hides four distinct steps behind one command. This lab has you run each one separately so you can see what each stage actually produces — the same pipeline Module 13 (Linking) covers, but here you're driving it by hand.

Assemble

→
Link

StageCommandWhat you get
Preprocessinggcc -E simple.c > simple_preprocessed.txtSource with #include/#define directives expanded — still C, but flattened
Compilinggcc -S simple.csimple.s: x86 assembly, the same kind of output you'll read starting in Unit 4
Assemblinggcc -c simple.csimple.o: machine code/opcodes in object-file segments, not yet a runnable program
Linkinggcc simple.c (or gcc simple.c -o simple)a.out (or your named executable): .o files merged with library code like stdio.o, external references resolved

Two things worth actually looking at: open simple.s and find one instruction you don't recognize yet, and hexdump simple.o to see that an object file isn't a flat blob — it's organized into segments (code, data) the linker later stitches together.

2. Native data types

TypeSizeStores
char1 byteinteger (also used for characters)
short2 bytesinteger
int4 bytesinteger
long8 bytesinteger
float4 bytesdecimal (IEEE floating point)
double8 bytesdecimal, more precision than float

Bit width sets the range: an N-bit unsigned type holds 0 to 2N-1; signed two's-complement holds -2N-1 to 2N-1-1 (see Module 03 — Integer Representations). unsigned trades the negative half of the range for a doubled positive range. These sizes are processor-dependent, not guaranteed by the language — the lab's own warning example is the Ariane 5 rocket explosion, caused by an oversized value forced into too small a type.

Casting risk: casting a value that doesn't fit the destination type produces silently wrong results, not an error. (char)(short)400 becomes -112, not 400 or a compile error — the extra bits just get truncated. Implicit casts (the compiler converting for you, with no explicit (type) in sight) are the dangerous ones, because there's no visual cue that a conversion happened at all.

The lab challenge (data.c) requires printing a uint8_t as its char equivalent, printing an unsigned int in hex, and using at least five different specifier types across separate printf calls — deliberately forcing you past just %d everywhere. It also asks you to try a format specifier in a way that "shouldn't" work, observe what actually happens, and explain it in a comment — the point being that mismatched specifiers don't reliably crash, they just read the wrong number of bytes off the stack and print garbage.

You cast the short value 400 down to a char and get -112 instead of 400. What happened?
400 doesn't fit in a signed 8-bit range (-128 to 127). Casting down truncates the extra bits rather than erroring, and whatever bit pattern is left over gets reinterpreted under two's complement — here, that pattern happens to represent -112.
Which stage of gcc's pipeline produces human-readable x86 assembly you can open in a text editor?
gcc -S stops right after translating C into assembly and writes it out as text (simple.s). Assembling (-c) turns that into binary machine code in an object file, which is no longer readable as text.
