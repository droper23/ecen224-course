Client Lab

Sends the picture you just captured across the network: open a TCP socket to a grading server, pack a homework ID and raw image bytes into one buffer with no delimiter between them, and push it through send() — which, unlike fwrite, never promises to take everything in one call.

Tested on: hands-on CAEDM work, not itself graded exam content — but sockets and byte-buffer framing are core Unit 5 material tested on the Final.
Official lab page: This primer covers the concepts — for exact CAEDM setup steps, starter code, and the TA pass-off checklist, use the official page: byu-cpe.github.io/ecen224/labs/09_client.

Learning objectives

  • Explain why a socket is opened, written to, and closed like a file — and where that analogy breaks down
  • Pack two pieces of data (an ID and an image buffer) into one contiguous send buffer with memcpy
  • Write a loop around send() that keeps sending until everything is actually transmitted
  • Read a Config struct populated with connection and payload details

1. A socket is "mostly" a file descriptor

This lab is deliberately light on new networking theory — Computer Networks and Socket Programming already covered socket()/connect()/send()/ recv(). What's new here is using them for real, against a real server (ecen224.byu.edu:2240, campus network only), with a payload that isn't a simple string. client_connect() is provided and returns a socket the same way fopen() returns a FILE *: from here on, most operations on it look like file I/O.

2. Building one buffer out of two pieces of data

The protocol here is intentionally minimal: the homework ID followed immediately by the raw image bytes, with no null terminator or separator between them. That rules out string-concatenation approaches (strcat would stop at the first 0x00 byte it finds inside the image data, silently truncating it). The correct approach is the same one you'd use to build any binary packet: allocate a buffer sized to hold both pieces, then memcpy each piece into its offset. 

uint8_t *payload = malloc(id_len + image_len);
memcpy(payload, hw_id, id_len);
memcpy(payload + id_len, image_data, image_len);
Watch for: treating the image bytes as a C string anywhere in this pipeline. Image data is binary — it can and will contain 0x00 bytes that are not the end of the buffer. Track lengths explicitly; never rely on a null terminator to know where the image data ends.

3. send() doesn't promise to finish the job

send() "always tries to send all the data you give it," but the return value tells you how many bytes actually went out — which can be less than what you asked for, and isn't an error. client_send_image() has to loop: send, check the return value, advance a pointer/offset by however many bytes actually went, and keep going until everything's been sent or send() returns a genuine error (negative). 

size_t sent = 0;
while (sent < total_len) {
    ssize_t n = send(sockfd, payload + sent, total_len - sent, 0);
    if (n < 0) { /* real error: bail out */ break; }
    sent += (size_t)n;
}

Skills you'll need

  • Module 27 — Computer Networks — IP addresses, ports, TCP vs. UDP.
  • Module 28 — Socket Programming — socket/connect/send/recv, with the same client.c you'll be extending here.
Why can't you build the ID+image payload with strcat?
strcat stops at the first null byte. Image data isn't text and will contain 0x00 bytes throughout, so string functions would silently truncate the payload. memcpy with explicit lengths is the correct tool.
send() returns a value less than the number of bytes you asked it to send, and no error occurred. What should client_send_image() do?
A partial send is normal, not an error. The correct pattern is a loop that tracks how much has been sent so far and keeps calling send() with the remaining bytes until the whole payload is out.
