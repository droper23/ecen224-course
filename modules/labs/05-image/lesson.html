Image Lab

The first "programming heavy" lab: you write three real image-processing functions in C — channel removal, grayscale conversion, and a neighbor-based OR filter — that operate directly on the raw byte layout of a BMP file loaded into a Bitmap struct. There's no image library doing the work for you; you're indexing into a flat byte array and reasoning about what each byte means.

Tested on: not directly exam-tested, but manipulating raw memory through structs and pointers — exactly what this lab forces you to do — is core to Game 1, Game 2, and the Final.
Official lab page: This primer covers the concepts — for exact CAEDM setup steps, starter code, and the TA pass-off checklist, use the official page: byu-cpe.github.io/ecen224/labs/05_image.

Learning objectives

  • Explain how a BMP file's pixel data is laid out as a flat array of bytes, not a 2D grid
  • Read and modify pixel color channels directly through a struct and a uint8_t *
  • Apply bitwise AND/OR/XOR operators to combine or mask color channel values
  • Implement the luminance formula for grayscale conversion, including truncation to an integer
  • Explain why a filter that reads neighboring pixels must read from a separate copy of the data

1. The Bitmap struct and flat pixel arrays

C has no image class, so the lab gives you a Bitmap struct that bundles everything about one loaded image: a FILE *, the BMP file/DIB headers, width and height, file size, and — the part you actually touch — pxl_data, a uint8_t * pointing at the raw pixel bytes. A second field, pxl_data_cpy, holds an unmodified copy of the same data.

Each pixel is three consecutive bytes — blue, green, red, in that order — not a struct with named fields. So pxl_data is 3 × width × height bytes long, and pixel (x, y)'s blue byte lives at pxl_data[3 * (y * width + x)], green at +1, red at +2. This is exactly the "array/pointer equivalence" and indexing-arithmetic material from Module 09 — Arrays, Strings & Structs and Module 10 — C Pointers, applied to something you can visually check for correctness: get the index arithmetic wrong and the output image looks obviously broken.

Watch out: BMP files store rows bottom-up. If your loop assumes top-down row order, your filters will still run without crashing — they'll just be wrong, and the wrongness won't always be visually obvious for every function.

2. The three functions

FunctionWhat it does
remove_color_channel()Zero out one specified channel (R, G, or B) across every pixel.
grayscale()Set every channel of every pixel to Y = 0.299R + 0.587G + 0.114B, truncated to an integer.
or_filter()Bitwise-OR each channel with the same channel from the pixel directly above and below, with edge handling at row 0 and the last row.

remove_color_channel() is a warm-up in array indexing. grayscale() forces you to be careful about integer truncation — the formula produces a float, and the assignment target is a uint8_t. or_filter() is the one that actually requires the two-buffer design: if you read and write to pxl_data in the same pass, a pixel you already OR'd gets read again by the next row's calculation, compounding the result incorrectly. That's why the filter must read from pxl_data_cpy and write to pxl_data — the copy stays a stable, unmodified snapshot of the original image for the whole pass.

3. Skills you'll need

  • Module 09 — Arrays, Strings & Structs: struct field access, contiguous array layout.
  • Module 10 — C Pointers: pointer arithmetic, the array/pointer duality pxl_data[i] vs *(pxl_data + i).
  • Module 26 — Dynamic Memory Allocation: the pixel buffers here are heap-allocated; the same use-after-free/leak hazards apply if you ever resize or reload an image.
  • Lab 04 — C Programming Part 2: this lab assumes you're already comfortable with the pointer/array material it covers.
A pixel's blue byte is at pxl_data[300]. Where is that same pixel's red byte?
Each pixel is 3 consecutive bytes in blue, green, red order. If blue is at index 300, green is at 301 and red is at 302 — the same pixel, offset by +2 from blue.
Why does or_filter() need to read from pxl_data_cpy instead of reading and writing pxl_data in place?
A neighbor-based filter must compute every output pixel from the original input. If you overwrite in place, a pixel's already-filtered value can feed into the filter calculation for the next row, producing a result that depends on the order you happened to loop in — which is not what the filter is supposed to compute.
