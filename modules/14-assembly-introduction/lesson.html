Assembly Introduction

Everything above this layer — C, functions, structs, loops — is a story the compiler tells to make programming tractable for humans. The CPU only ever sees the story it produces: sequences of instructions operating on registers and memory. This module is the bridge into that world — the x86-64 register set, AT&T syntax, and how to get from a C program to the assembly and machine code the processor actually runs.

CS:APP reference: Chapter 3.2.  |  Last lecture topic before Game 1 opens (Oct 12).  |  Tested on: Game 1 and the Final.

Learning objectives

  • Explain why programmers read assembly even when they don't write it by hand
  • Name the 16 x86-64 general-purpose registers and their four access widths
  • Explain the sub-register overlap between %rax/%eax/%ax/%al, including the 32-bit zero-extension rule
  • Recognize AT&T syntax: register, immediate, and operand-order conventions
  • Use gcc -S to see a C function's assembly, and read basic objdump -d output

1. Why read assembly at all

You will very rarely hand-write x86-64 assembly in this course or afterward. You'll read it constantly, for three reasons that come up throughout the rest of this unit:

  • Understanding what the compiler actually did. Optimization, calling conventions, and struct/array layout all become concrete once you can see the instructions a piece of C compiles to — and that's the only way to answer "what does this C code actually cost."
  • Debugging at the machine level. When a program crashes with no source-level explanation, or when you're using gdb to inspect a crash inside a library you don't have source for, assembly and register/memory state are all you have.
  • Security. Buffer overflow attacks (later in this course) work by corrupting memory in a way that redirects what instructions the CPU executes next. Understanding that requires understanding what's actually on the stack and in registers at the machine level, not just what the C source says should happen.

2. A few terms, precisely

These words get used loosely in casual conversation but mean specific, different things:

  • Instruction Set Architecture (ISA) — everything you need to know to write assembly for a processor: its registers, its word size, the format of its instructions, and the effect each instruction has on machine state. x86-64 is an ISA; so is ARM.
  • Microarchitecture — how a specific chip implements that ISA (pipeline depth, cache sizes, clock frequency). Two very different chips can implement the same ISA and run the exact same assembly.
  • Assembly code — a human-readable text representation of machine instructions.
  • Machine code — the actual bytes that encode those instructions. Object code is machine code where addresses of global symbols aren't filled in yet (recall Module 13 — this is exactly what the linker resolves); executable code is the final, fully-resolved form the processor runs.

3. Programmer-visible state

From assembly's point of view, a CPU has exactly four things it can read or write:

  • Program counter (PC) — the address of the next instruction to execute. On x86-64 it's called %rip ("instruction pointer").
  • Register file — a small set of named storage locations, heavily used because they're far faster to access than memory.
  • Condition codes — single-bit flags recording status from the most recent arithmetic/logic instruction (e.g. did it produce zero, did it overflow), used to make conditional branches work. You'll cover these in detail in the next module.
  • Memory — one big byte-addressable array holding both code and data, including the stack that supports function calls.

4. The x86-64 register set

x86-64 has 16 general-purpose registers, each 64 bits wide. Each one can also be accessed as a smaller, narrower window onto its own low-order bits — not as a separate register, but as a different name for part of the same storage. This overlap is one of the most common exam questions in this unit, so it's worth internalizing the pattern rather than memorizing a table.

64-bit32-bit16-bit8-bitHistorical role
%rax%eax%ax%alreturn value
%rbx%ebx%bx%blcallee-saved
%rcx%ecx%cx%cl4th argument
%rdx%edx%dx%dl3rd argument
%rsi%esi%si%sil2nd argument
%rdi%edi%di%dil1st argument
%rbp%ebp%bp%bplbase/frame pointer
%rsp%esp%sp%splstack pointer
%r8–%r15%r8d–%r15d%r8w–%r15w%r8b–%r15b5th arg (%r8), 6th arg (%r9), general purpose

Read that table as one physical 64-bit storage cell per row, with four different names that each expose a different number of its low-order bits: %al is literally the low byte of %ax, which is the low 16 bits of %eax, which is the low 32 bits of %rax. The suffix letters you'll see on instructions mirror this: b (byte, 1 byte), w (word, 2 bytes), l (long/double word, 4 bytes), q (quad word, 8 bytes) — e.g. movq moves 8 bytes, movl moves 4.

The one asymmetry to memorize: writing to a 32-bit sub-register (e.g. movl $5, %eax) automatically zeroes the upper 32 bits of the full 64-bit register — this is a hard rule of the x86-64 ISA, not a compiler courtesy. But writing to the 16-bit or 8-bit sub-registers (%ax, %al) leaves the upper bits of the containing register untouched, whatever garbage happened to be there before. This inconsistency between the 32-bit case and the 16-/8-bit case is exactly the kind of thing exam questions probe.
%rax holds 0xffffffffffffffff. After executing movl $1, %eax, what does %rax hold?
Writing a 32-bit value to %eax zero-extends: it sets the low 32 bits to the new value and clears the upper 32 bits of %rax, unlike writes to the 16-bit %ax or 8-bit %al, which leave everything above them alone.

5. AT&T syntax (vs. Intel)

There are two common notations for x86 assembly. Intel's own tools default to Intel syntax; gcc, gdb, and objdump on Linux default to AT&T syntax, which is what CS:APP uses and what this entire course uses. You need to be able to recognize AT&T syntax on sight:

Immediates$0x180x18

The two that trip people up most: registers always get a % prefix and immediate (literal constant) operands always get a $ prefix in AT&T syntax — and operands go source, then destination, the mirror image of how you'd read it in Intel syntax or in a C assignment. movq %rax, %rbx means "copy the value in %rax into %rbx," not the other way around.

6. Anatomy of an instruction

Take this line from a real compiled function:

movq %rax, (%rbx)

mov is the operation (move/copy data); the q suffix says it's moving a quad word — 8 bytes. The source operand %rax is a register. The destination operand (%rbx) uses parentheses to mean "memory at the address held in this register" — i.e. M[%rbx], not %rbx itself. So the whole instruction is: take the 8-byte value currently in %rax, and store it to the memory address that %rbx points at. This is the compiled form of a C statement like *dest = t;, where t had been computed into %rax and dest into %rbx.

Instructions fall into three broad categories, all of which you'll see in detail over the next several modules:

  • Arithmetic/logic operations on register or memory data
  • Data transfer between memory and registers (load from memory, store to memory)
  • Control transfer that changes the PC: unconditional jumps, conditional branches, calls and returns

7. From C to assembly to bytes

Take this small C function:

long plus(long x, long y);
void sumstore(long x, long y, long *dest)
{
    long t = plus(x, y);
    *dest = t;
}

Compiling with gcc -Og -S sum.c stops the pipeline right after the compiler proper, producing a .s file of AT&T assembly — no assembling or linking yet:

sumstore:
   pushq   %rbx
   movq    %rdx, %rbx
   call    plus
   movq    %rax, (%rbx)
   popq    %rbx
   ret

-S is the flag to remember: it's the fastest way to answer "what did the compiler actually do with this line of C," and you'll reach for it constantly in this unit and the ones that follow. (-Og asks for light optimization that still keeps the assembly close to readable; without it, gcc's default optimization can reorder and simplify code enough to make it much harder to map back to the source.)

Assembling that .s file turns each instruction into raw bytes — for example movq %rax, (%rbx) assembles to the 3 bytes 48 89 03. The result still needs the linker (Module 13) to resolve the call to plus before it's a runnable executable.

8. Reading it back: objdump

Going the other direction — from raw bytes back to assembly — is disassembly. objdump -d is the standard tool: it can be run on either a complete executable or a single .o file, and it reconstructs an approximate rendition of the assembly purely from the byte patterns, with no access to the original source: 

0000000000400595 <sumstore>:
  400595:  53               push   %rbx
  400596:  48 89 d3         mov    %rdx,%rbx
  400599:  e8 f2 ff ff ff   callq  400590 <plus>
  40059e:  48 89 03         mov    %rax,(%rbx)
  4005a1:  5b               pop    %rbx
  4005a2:  c3               retq

A few things to notice. x86-64 instructions are variable length — from 1 to 15 bytes — but the encoding is designed so that from a given starting byte, there is only one possible decoding into instructions; a disassembler doesn't have to guess where one instruction ends and the next begins. Also notice the disassembler dropped the q suffix (mov instead of movq, retq shown instead of ret in some tools) — the disassembler's naming convention can differ slightly from the compiler's, even though they describe the same instructions. And because object code carries so little information about the original source, disassembly can be applied to anything that might be executable code — not just programs you compiled yourself.

gdb (Module 12) can disassemble too, from inside a running or loaded program: 

gdb ./prog
(gdb) disassemble sumstore
Which AT&T-syntax instruction copies the value 24 into register %rdi?
AT&T syntax needs $ before a literal immediate value (24 = 0x18) and lists operands source-then-destination, so the immediate comes first and %rdi — the destination — comes last.
Which command produces the human-readable x86-64 assembly for a C file without assembling or linking it?
gcc -S stops right after compilation and emits a .s text file of assembly. -c goes further and produces a binary .o object file; objdump -d disassembles an already-compiled binary, not a C source file.
