The Memory Hierarchy

A CPU can execute an instruction in well under a nanosecond, but fetching a value from main memory can take a hundred times that long, and from disk a million times that long. If every memory access ran at main-memory speed, the CPU would spend almost all of its time waiting. Caches close that gap — not by being fast enough everywhere, but by betting on how programs actually behave.

CS:APP reference: Chapter 6.  |  Tested on: This material comes after Game 2 and is tested only on the comprehensive Final.

Learning objectives

  • Explain why the CPU-memory speed gap makes a memory hierarchy necessary
  • Distinguish SRAM from DRAM and explain why each sits where it does in the hierarchy
  • Define temporal and spatial locality, and identify each in a piece of C code
  • Describe cache hits and misses in terms of blocks, placement, and replacement
  • Explain why row-major traversal of a 2D C array is faster than column-major traversal

1. The problem: the CPU is much faster than memory

Over the last several decades, CPU clock speeds and DRAM (main memory) speeds have improved at wildly different rates. Processor cycle times have dropped by roughly three orders of magnitude since 1980, but DRAM access latency has only dropped by a couple of hundred-fold — and disk seek times have barely improved at all. The practical result is a widening gap: a modern CPU can execute dozens of instructions in the time it takes to fetch a single word from main memory, and millions of instructions in the time it takes to read from disk.

If every load and store instruction had to wait for main memory, the CPU would spend nearly all its time stalled. The fix is not to make all of memory fast — fast memory is expensive and physically large — it's to build a hierarchy: a small amount of very fast, very expensive memory close to the CPU, backed by progressively larger, slower, and cheaper memory further away.

2. SRAM vs. DRAM

Two different circuit technologies show up at different levels of the hierarchy, and their physical differences explain why:

SRAM61× (fast)Yes~100×Cache memories
DRAM110× (slower)No — must be refreshed every 10–100 ms1×Main memory, frame buffers

SRAM (static RAM) stores each bit in a small loop of six transistors that holds its value as long as power is applied. It's fast and stable, but each cell takes more silicon area, which makes it expensive and limits how much you can fit on a chip. DRAM (dynamic RAM) stores each bit as a charge on a single capacitor, which is far denser and cheaper per byte — but the charge leaks away, so the hardware must refresh every cell every few milliseconds, and DRAM is slower and more sensitive to electrical noise. This trade-off is exactly why SRAM is used for caches (small, fast, expensive) and DRAM for main memory (large, slower, cheap).

Why is DRAM used for main memory instead of SRAM, even though SRAM is faster?
Main memory needs to be large (gigabytes), and SRAM's 6-transistors-per-bit cost makes that prohibitively expensive and physically large. DRAM's 1-transistor-plus-capacitor cell is far denser and cheaper, at the cost of needing constant refresh and being slower — an acceptable trade for a lower, larger tier of the hierarchy.

3. The hierarchy, level by level

Putting these technologies together (plus disk, which is slower and cheaper still) gives the classic pyramid every systems course draws: 

   registers                (on CPU, ~0 cycle latency)
   L1 cache      (SRAM)     ~4 cycles
   L2 cache      (SRAM)     ~10 cycles
   L3 cache      (SRAM)     ~40-75 cycles
   main memory   (DRAM)     ~100+ cycles
   local disk / SSD         ~100,000+ cycles
   remote storage (network) millions of cycles

Each level acts as a cache for the level below it: a smaller, faster device holding a copy of a subset of the data from the larger, slower device beneath it. Registers hold words pulled from L1; L1 holds cache lines pulled from L2; L2 holds lines pulled from L3 or main memory; main memory itself acts as a cache for disk (that's the basis of virtual memory, covered next module). The general rule holds at every level: the closer to the CPU, the faster and smaller (and more expensive per byte) the memory. The result is a system that feels almost as fast as the fastest level and almost as large and cheap as the slowest one — as long as the data you need is usually near the top.

4. Why caching works: locality

Caching is a bet: that the CPU won't need arbitrary, uniformly random addresses, but will keep revisiting a small, predictable neighborhood of memory. That behavior is called locality of reference, and it comes in two forms:

  • Temporal locality: if a memory location was referenced recently, it's likely to be referenced again soon. A loop variable or an accumulator you update every iteration exhibits strong temporal locality.
  • Spatial locality: if a memory location was referenced, memory locations near it are likely to be referenced soon too. Walking through an array element by element exhibits strong spatial locality — and so does fetching instructions, since code typically executes sequentially.

Consider a simple sum:

sum = 0;
for (i = 0; i < n; i++)
    sum += a[i];
return sum;

sum shows temporal locality — the same variable is read and written every iteration, so it can live in a register the whole time. The array a[] shows spatial locality — it's accessed with stride 1 (one element at a time, in order), so each cache block fetched from memory gets used for several consecutive iterations before the next block is needed. The instructions of the loop body itself exhibit both kinds of locality too: they're executed repeatedly (temporal) and stored sequentially (spatial).

A loop repeatedly re-reads the same accumulator variable on every iteration. Which kind of locality does this best illustrate?
Referencing the exact same memory location repeatedly, close together in time, is the definition of temporal locality — it means once the value is pulled into a register or cache, it stays there and gets reused instead of being re-fetched.

5. Cache basics: blocks, hits, and misses

Hardware caches don't move individual bytes between levels — they move fixed-size chunks called blocks (or, at the L1/L2 level, cache lines, typically 64 bytes). When the CPU asks for a byte, the whole block containing it gets copied up into the cache. This is what turns spatial locality into a real performance win: once one element of an array triggers a block fetch, several of its neighbors ride along for free.

On every memory reference, the hardware checks whether the needed block is already present:

  • Cache hit: the block is already in the cache — the CPU gets the data quickly.
  • Cache miss: the block isn't present, so it must be fetched from the next level down. The hardware must decide a placement policy (where in the cache the new block goes) and, if the cache is full, a replacement policy (which existing block to evict as the "victim").

This is exactly why access pattern matters, not just how much data you touch. Compare row-major and column-major traversal of the same 2D array in C, where 2D arrays are stored in row-major order (each row laid out contiguously in memory): 

// Row-major traversal: stride-1, follows memory layout
int sum_rows(int a[M][N]) {
    int i, j, sum = 0;
    for (i = 0; i < M; i++)
        for (j = 0; j < N; j++)
            sum += a[i][j];   // consecutive j -> consecutive addresses
    return sum;
}

// Column-major traversal: same total accesses, terrible locality
int sum_cols(int a[M][N]) {
    int i, j, sum = 0;
    for (j = 0; j < N; j++)
        for (i = 0; i < M; i++)
            sum += a[i][j];   // consecutive i -> jumps N elements each time
    return sum;
}

Both functions touch every element exactly once and do the same amount of arithmetic. But sum_rows reads memory with stride 1 — each cache block fetched (holding several consecutive ints) gets fully used before moving on. sum_cols jumps N elements between consecutive accesses, so it very likely touches a new, uncached block almost every single access, evicting blocks it will need again on the next row. For a large enough array, this pattern difference alone can make row-major traversal several times faster, with no change to what's being computed — purely from respecting the memory hierarchy.

Why is column-major traversal of a large 2D C array typically much slower than row-major traversal, even though both touch every element exactly once?
Since rows are contiguous in memory, striding down a column means each access lands in a different, likely-uncached block, while row-major access reuses each fetched block for many consecutive iterations. Same work, very different cache behavior.
