C I/O

C has no built-in notion of "print" or "read a number" — input and output are just ordinary library functions declared in <stdio.h>. This module covers printf and scanf's format-string mini-language, why terminal I/O is buffered, and the pitfalls that make scanf one of the most common sources of bugs in intro C code.

Due: HW6 — C I/O (closed Sep 28).  |  Tested on: Game 1 and the Final.

Learning objectives

  • Read and write printf/scanf format specifiers, including flags, field width, precision, and length modifiers
  • Explain why terminal I/O is buffered, and how that changes when output actually appears
  • Choose the correct conversion character for a given C type, and explain common mismatches (%d vs %ld vs %f)
  • Check scanf's return value to detect a failed or partial conversion
  • Explain the pitfall of mixing scanf("%d", ...) with getchar/fgets, and how leftover input causes it

1. I/O is a library, not a language feature

C itself has no print keyword. Input and output are ordinary functions, defined by the ANSI C standard and declared in the <stdio.h> header (which, remember from Module 6, contains only declarations — the actual implementation lives in the C standard library your compiler links against). The core functions:

FunctionDoes
getchar()read the next character from stdin
putchar(c)write character c to stdout
printf(fmt, ...)convert and write formatted output to stdout
scanf(fmt, ...)read from stdin and convert into the given arguments
sprintf(s, fmt, ...)like printf, but writes into a string s
sscanf(s, fmt, ...)like scanf, but reads from a string s

Three predefined streams exist as soon as your program starts: stdin (default input, the keyboard), stdout (default output, the screen), and stderr (also the screen by default, but a separate stream conventionally reserved for error messages so they can be redirected independently of normal output). A file variant of every function above exists too — fprintf, fscanf, fgetc, fputc — each taking an explicit FILE * stream argument, covered in section 5 below.

2. Buffering: why output doesn't always appear right away

Both stdin and stdout are normally buffered: a buffer is a temporary staging area in memory that characters pass through before they actually reach the terminal, or before your program actually sees them.

  • Input side: keystrokes are captured and held by the terminal's own line-buffering as you type, which is what lets you use backspace to fix a typo before hitting enter. Your program doesn't see any of it until you press Enter (\n) — the whole line is released to stdin at once.
  • Output side: text you printf is typically held in a buffer and not actually drawn to the screen until a newline is written, the buffer fills up, or the program exits normally. This is why a printf without a trailing \n can appear to "not print" — it's sitting in the buffer, and will show up eventually, but possibly out of order relative to other output if you're mixing buffered and unbuffered streams (like stdout and stderr).
Practical consequence: if you're debugging with printf statements and your program crashes, prints you expected to see might never have been flushed to the screen. Ending debug prints with \n, or calling fflush(stdout) explicitly, makes sure output actually appears before a crash swallows it.

3. printf: formatted output

printf's first argument is a format string containing two kinds of content: ordinary characters, copied to the output as-is, and conversion specifications, which each consume and format the next argument in the list. 

printf("X = %d, Y = %d\n", x, y);

A conversion specification begins with % and ends with a conversion character, with optional pieces in between, in this order: 

%  [flags]  [field width]  [.precision]  [length modifier]  conversion-char
  • Flags: - left-justifies within the field width (default is right-justified); 0 pads with leading zeros instead of spaces.
  • Field width: a number giving the minimum number of characters to print, padding with spaces (or zeros) if the value is shorter.
  • Precision (after a .): for %f, how many digits after the decimal point (default 6); for %s, the maximum number of characters printed from the string.
  • Length modifier: h for a short argument, l (letter ell) for a long argument.

The most common conversion characters:

CharArgument typePrints as
d, iintsigned decimal
uunsigned intunsigned decimal
x, Xintunsigned hex (lower/upper case digits)

The single most common printf bug: the conversion character must match the argument's actual type, and the compiler often won't catch a mismatch for you. %d expects a plain int — passing a long there is undefined behavior on many platforms because the two types are different sizes; use %ld for long. Likewise, %f expects a double, not an int — passing an int where %f expects a double reads the wrong bit pattern and prints garbage, because integers and floating-point numbers use completely different bit encodings (recall Module 5). There is no automatic conversion happening here the way there is in an ordinary expression like x + 1.0 — printf just reads however many bytes the format specifier tells it to, from wherever the arguments happen to be.

Field width and precision interact in ways worth seeing spelled out. With printf("%s", "hello, world") (12 characters):

"%s"        :hello, world:      default
"%10s"      :hello, world:      min field 10 (string already exceeds it)
"%.10s"     :hello, wor:        max 10 characters printed
"%-10s"     :hello, world:      min field 10, left justified
"%15.10s"   :     hello, wor:   min field 15, max 10 characters

And with printf("%f", 12345.12345):

"%f"        :12345.123450:   default precision, 6 digits
"%.3f"      :12345.123:      precision 3
"%15.3f"    :      12345.123:  min field 15, precision 3
A function takes a long counter. Which format specifier correctly prints it with printf?
%d is sized for a plain int; on most 64-bit platforms long is a different (wider) size, so the length modifier l is required: %ld. %f is for floating-point types entirely, not integers.

4. scanf: formatted input, and its traps

scanf mirrors printf in reverse: it reads characters from stdin, interprets them according to a format string, and stores the converted results through its remaining arguments — which must all be pointers, since scanf needs to know the address to write into, not just a value. 

int day, year;
char monthname[20];
scanf("%d %s %d", &day, monthname, &year);   /* reads: 25 Dec 1988 */

Note there's no & before monthname — an array name already decays into a pointer to its first element (this will make more sense after Module 9 on arrays and Module 10 on pointers; for now, the rule is: scanf needs an address, and an array name already is one, while a plain variable like day needs & to produce one).

For each conversion, scanf skips leading whitespace, then reads characters until it hits the first one that doesn't belong to the value being converted: %d reads until the first non-digit, %s reads until the first whitespace character. Any literal, non-% text in the format string (including plain spaces) must match the input stream, or the conversion stops right there.

Always check the return value. scanf returns the number of successful conversions, which is not necessarily the number you asked for. If the input doesn't match the format — e.g. a user types letters where a number was expected, or a literal character in the format string like / doesn't appear in the input — scanf simply stops converting and returns early, leaving the remaining arguments untouched (and full of whatever garbage they had before, if they're uninitialized locals — see Module 6). Code that ignores scanf's return value and barrels ahead is one of the most common sources of bugs in early C assignments. 

int matched = scanf("%s %d/%d/%d %lf", name, &month, &day, &year, &gpa);
/* input "Muss 02 16 69 3.02" doesn't match the literal '/', so scanf
   stops after 2 successful conversions and returns 2, not 5 */

Note also the length modifier for scanf: %lf is required to read into a double * (unlike printf, where %f alone works for a double argument, because default argument promotion converts float to double automatically when passed through ... — but scanf is writing through a pointer, so no such promotion happens, and the size must be exact).

A program calls int n = scanf("%d %d", &a, &b); and the user types 7 banana. What happens?
scanf converts greedily until it hits input that doesn't match the next specifier. "7" satisfies the first %d, but "banana" isn't a valid integer, so the second %d fails and scanf stops there, leaving b unchanged. The return value (1) is how a careful program would detect that only one of the two requested conversions actually succeeded.

5. getchar/fgets vs. scanf: the leftover-newline trap

A specific, extremely common bug: mixing scanf("%d", ...) with a later call to getchar() or fgets(). The problem is what %d doesn't consume: it reads digits and stops at the first non-digit — including the newline the user typed to submit their input. That \n stays sitting in the input buffer, and the very next read (say, a getchar() meant to read the user's next keypress) immediately reads that leftover newline instead of waiting for new input: 

int n;
char c;
printf("Enter a number: ");
scanf("%d", &n);          /* user types "5\n"; %d consumes "5", leaves "\n" in the buffer */
printf("Enter a letter: ");
c = getchar();              /* immediately reads the leftover '\n', not the letter! */

%c has the same problem in reverse: unlike every other scanf conversion, %c does not skip leading whitespace by default, so a %c placed right after a %d in the same format string will often read that leftover newline as its character. A leading space in the format string (" %c") explicitly tells scanf to skip whitespace first.

This is also why line-oriented input (a whole line of text, including embedded spaces) is usually read with fgets rather than scanf("%s", ...): %s stops at the first whitespace character, so it can't read a full line like "John Smith" in one call, and — just like gets, which the standard library dropped entirely because of this — a bare %s with no field width has no idea how large the destination buffer is, so it will happily write past the end of it on long input. fgets(buf, sizeof(buf), stdin) reads a whole line at once, up to a given maximum size, and is the safer default for reading user input as text.

6. File and string variants

The same formatted I/O extends beyond the terminal. File variants take an explicit FILE * stream, opened first with fopen: 

FILE *infile  = fopen("myinfile.txt", "r");   /* NULL on failure */
FILE *outfile = fopen("myoutfile.txt", "w");

fprintf(outfile, "The answer is %d\n", x);
fscanf(infile, "%s %d/%d/%d %lf", name, &month, &day, &year, &gpa);

fclose(infile);
fclose(outfile);
ModeMeaning
"r"read (file must exist)
"w"write (existing contents are discarded)
"a"append
"r+"read and write

Always check whether fopen succeeded before using the result — it returns NULL on failure (file doesn't exist, no permission, etc.), and dereferencing that through fscanf or fprintf is undefined behavior.

sprintf and sscanf do the same job but against an in-memory string instead of a stream — useful for building or parsing strings without touching a file or the terminal at all: 

char buf[64];
sprintf(buf, "x = %d, y = %d", x, y);   /* build a string in memory */
sscanf(buf, "x = %d, y = %d", &x, &y); /* parse one back out */
