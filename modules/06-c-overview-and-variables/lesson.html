C Overview & Variables

Every module from here through the rest of the course assumes you can read and write C. This module covers why the language looks the way it does, how a .c file becomes a running program, and how C thinks about variables — their types, their sizes, and where they live.

Due: HW5 — C Overview, Variables (closed Sep 25).  |  Tested on: Game 1 and the Final.

Learning objectives

  • Explain why C is used as a systems programming language rather than a higher-level one
  • Trace a C program through the compilation pipeline: preprocessing, compiling, assembling, linking
  • Distinguish a declaration from a definition, and explain why the distinction matters across files
  • List C's basic types, their approximate sizes, and when to reach for the fixed-width stdint.h types instead
  • Determine a variable's scope (local, global, static) and its default initial value

1. Why C?

C is a systems programming language: it was designed to write operating systems, compilers, and embedded firmware, not spreadsheets or web pages. That design goal explains almost everything unusual about it. C gives you direct control over memory layout (this course spends multiple units on exactly what that memory looks like), it compiles straight to native machine instructions instead of running inside a virtual machine, and it has no garbage collector — if you allocate memory, you are responsible for freeing it, and if you access memory incorrectly, the language will not stop you. That's dangerous, but it's also why C runs close to the hardware with almost no runtime overhead, and why understanding C is really understanding how the machine underneath it works — which is the actual point of this course.

C is also small. It has no built-in string type, no built-in dynamic arrays, no classes, and only a handful of keywords. Everything else — input/output, string manipulation, math, memory allocation — is provided by the C Standard Library (<stdio.h>, <string.h>, <math.h>, <stdlib.h>, ...), not the language itself. Several implementations of that standard library exist — glibc on most Linux systems, the Microsoft CRT on Windows, musl on lightweight Linux distributions — but they all implement the same interface, which is why the same #include <stdio.h> works everywhere.

2. Hello, World, and where it lives

Every C program starts execution in a function named main. A minimal program:

#include <stdio.h>

int main(void)
{
  printf("Hello, World!\n");
  return 0;
}

A few conventions worth internalizing immediately, because they show up in every program you write this semester:

  • #include <stdio.h> pulls in the declarations for printf and friends. Angle brackets < > tell the preprocessor to look in system directories; double quotes " " tell it to look in your own project directories first.
  • main returns an int. Returning 0 conventionally means "no error"; a nonzero return code signals failure to whatever process launched your program (the shell, a test harness, etc.).
  • Text your program prints with printf goes to the terminal, a stream called stdout (standard out). Text the user types goes to a stream called stdin (standard in). You'll use both heavily starting next module.

Also notice what you cannot do: unlike some scripting languages, C does not allow executable statements outside of a function. A bare printf(...) sitting at file scope, outside of main or any other function, is a compile error. A global variable declaration at file scope, on the other hand, is completely normal — the distinction is between statements (which run) and declarations (which just reserve meaning or storage).

3. From source file to running program

When you run gcc main.c, it looks like one step, but it's actually a pipeline of four distinct phases. Understanding this pipeline matters for the rest of the course: later units on linking, memory layout, and debugging all assume you know what each phase produces. 

source (.c)  --preprocess-->  expanded source
             --compile----->  assembly (.s)
             --assemble---->  object code (.o)
             --link--------->  executable
  • Preprocessing. The preprocessor handles every line starting with # before real compilation begins. #include literally copies the named file's text into that location. #define performs find-and-replace text substitution throughout the file. Nothing here understands C syntax yet — it's a pure text transformation.
  • Compiling. The compiler translates the preprocessed C source into assembly language for the target CPU architecture (you'll write and read x86-64 assembly directly starting in Unit 3 of this course).
  • Assembling. The assembler turns human-readable assembly into object code — machine instructions, packaged into a .o file, but not yet a runnable program.
  • Linking. The linker stitches multiple object files (and library code such as the C standard library) together into one executable, resolving references between files — for example, connecting a call to printf in your object file to printf's actual compiled implementation.

This is also why C source is split into .c and .h files. .c files are compiled independently and linked together afterward. .h ("header") files don't contain implementations; they contain declarations — function prototypes like printf's, and type definitions like uint32_t — so that one .c file can use code defined in another without seeing its source. 

gcc main.c            # produces an executable named a.out
./a.out                # runs it
gcc main.c -o myExe    # name the executable myExe instead

For labs with multiple source files, you'll typically use make, a build tool that runs the right sequence of gcc invocations for you based on a Makefile.

Which compilation phase is responsible for turning #include <stdio.h> into the actual text of that header file?
The preprocessor runs first and handles every line starting with #. #include is a pure textual copy-paste of the named file's contents, performed before the compiler ever looks at C syntax or semantics.

4. Statements, blocks, and scope

C code is made of statements, each ending with a semicolon. A block is a set of statements bounded by braces { }; blocks are associated with functions, loops, and if statements, and blocks can nest inside other blocks. 

int main(void)
{
  int i = 5;      /* this is a block */
  {
    int i = 6;    /* a nested block, with its own 'i' */
  }
  return 0;
}

That nested example is really about scope: where a name is visible from.

  • Local scope. A variable declared inside a block is only visible inside that block (and any blocks nested within it). It ceases to exist once the block ends.
  • Global scope. A variable declared outside any function is visible throughout the entire file, and (unless marked static) from other files too.

When a local variable has the same name as a global one, the local variable hides the global for the rest of that block: 

int i = 5;              /* global i */

int main(void) {
  int i = 6;             /* local i, hides the global one */
  printf("%d\n", i);     /* prints 6, not the global 5 */
  return 0;
}

Marking a global static restricts its visibility to the file it's declared in — other .c files in the same program can no longer reference it, even with a matching declaration. That's the main tool C gives you for keeping a file's internal helper variables and functions from leaking into the rest of a multi-file program.

A global int i = 5; sits above main. Inside main, a nested inner block declares its own int i = 6;. After that inner block ends, what does printf("%d\n", i); print if called from the outer block of main (where main itself declared no i)?
A local variable's scope ends with its enclosing block. Once the inner block with its own i ends, that variable is gone; a reference to i from the outer block falls back to whatever the next enclosing scope provides — here, the global i = 5, since main's own block never declared an i of its own.

5. Declaring variables: types and sizes

A declaration specifies a type and a list of one or more variable names: 

int lower, upper, step;
char c, line[1000];
int i, test, foo, bar = 6;   /* only bar is initialized to 6! */

That last line is a classic gotcha: the initializer only applies to the variable immediately before it, not to the whole comma-separated list.

C's basic built-in types:

TypeHoldsTypical size
chara single byte / character1 byte
intan integer, the machine's natural word size4 bytes
floatsingle-precision floating point4 bytes
doubledouble-precision floating point8 bytes

The qualifiers short and long adjust an integer's size: short is guaranteed to be at least 16 bits and no longer than int; long is guaranteed to be at least 32 bits and no shorter than int. The word int can be omitted after them — short sh; and short int sh; are the same declaration.

The problem with "typical size": the C standard only guarantees minimums for short, int, and long — their exact sizes are allowed to vary by compiler and platform. That's fine for a lot of code, but it's fatal when you need an exact bit width, e.g. for a network packet format, a hardware register, or any question this course asks about "the 32-bit value at this address." For that, <stdint.h> gives you exact-width types: int8_t, uint8_t, int16_t, uint16_t, int32_t, uint32_t, int64_t, uint64_t. Prefer these whenever the exact size matters, which in this course is most of the time.

Constants (literals) also have types, and suffixes let you override the default:

LiteralType
1234int
1234Llong
1234Uunsigned int
1234ULunsigned long
037int, written in octal (leading 0)
0x1Fint, written in hex
123.4double
123.4Ffloat

A character constant like 'x' is written in single quotes, has type int, and its value is that character's ASCII encoding — '0' is the integer 48, not 0. Don't confuse it with a string constant like "x", written in double quotes, which is an array of characters terminated with a hidden '\0' (this distinction becomes critical next module, and again when we cover strings in Module 9).

6. Declaration vs. definition

This distinction is easy to skate past in an intro course, but it's exactly the kind of thing a homework or exam question will test, and it matters again the moment you start splitting a program across multiple files.

  • A declaration tells the compiler that a name exists and what its type is, without necessarily reserving storage for it. A function prototype (int addNumbers(int, int);) or an extern variable declaration are pure declarations.
  • A definition actually reserves storage (for a variable) or provides the body (for a function). int x = 5; is a definition. So is a full function with its { ... } body.

Every definition also counts as a declaration, but not every declaration is a definition. A variable or function can be declared many times across many files (so each file's compiler knows it exists and what type it is), but it must be defined exactly once in the whole program. Header files exist specifically to hold declarations, so multiple .c files can agree on a shared interface without each of them trying to define the same thing twice.

Variables also differ in how they're initialized by default, depending on where they live:

Global variablesLocal (automatic) variables
Default valueInitialized to zero automaticallyUndefined — contains garbage until you set it
InitializerMust be a constant expressionMay be any expression, including a function call
When initializedOnce, at program startEvery time the enclosing function/block is entered

Reading an uninitialized local variable is one of the most common sources of bugs in C programs — the value isn't zero, it's whatever bit pattern happened to already be in that memory location. Always initialize local variables explicitly.

7. const vs. #define

C gives you two different tools that both look like "make this value unchangeable," and they behave quite differently: 

const double e = 2.71828182845905;   /* a real, typed variable */
#define PI 3.14159265                /* pure text substitution */

A const variable has an actual type and a scope, just like any other variable — it just can't be written to after initialization. A #defined name has neither; the preprocessor performs blind find-and-replace on the source text before the compiler ever sees it, which means it can produce surprising results if you're not careful with parentheses: 

#define OFFSET 5
#define SIZE OFFSET + 3
...
char buf[SIZE * 2];   /* expands to: OFFSET + 3 * 2 = 5 + 3 * 2 = 11, not 16! */

Because the substitution is purely textual, SIZE * 2 does not expand to (5 + 3) * 2 — it expands to 5 + 3 * 2, and ordinary operator precedence takes over from there. This is exactly why library code that uses macros defensively wraps them in parentheses: #define SIZE (OFFSET + 3). A const variable has no such trap, because it's a real value, not a find-and-replace rule — but it also isn't a true compile-time constant, so it can't be used to size an array or as a switch case label.

Given #define SIZE OFFSET + 3 with OFFSET defined as 5, what does char buf[SIZE * 2]; actually allocate?
Macros are pure text substitution, performed before the compiler applies operator precedence. SIZE * 2 literally becomes OFFSET + 3 * 2, then 5 + 3 * 2 — multiplication binds tighter than addition, giving 5 + 6 = 11, not (5+3)*2 = 16.
