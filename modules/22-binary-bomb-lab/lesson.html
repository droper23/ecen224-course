Binary Bomb Lab

The binary bomb is a compiled program with six phases, each one waiting for a specific input. Guess wrong and it prints BOOM! and reports the explosion to a leaderboard; guess right and you advance. There is no source code for the phases — only a binary, a debugger, and a disassembler. Everyone gets a different bomb, so this module can't give you any answers. What it can give you is the workflow for finding them yourself.

Tested on: this is a hands-on programming assignment, not a lecture — but the reverse-engineering skill it builds is directly tested on Game 2 and the Final.

Learning objectives

  • Explain what the bomb lab is and why it's built around disassembly instead of source code
  • Describe a repeatable workflow for approaching an unfamiliar compiled phase
  • Use objdump -d to get a static disassembly of a binary
  • Use core gdb commands to set breakpoints and inspect registers and memory at runtime
  • Apply general strategy tips for isolating a phase's expected input without guessing blindly

1. What the assignment is, and why it exists

The bomb lab was created at Carnegie Mellon by the authors of the CS:APP textbook this course follows, and it's been used at universities worldwide for decades — it's a well-known rite of passage in systems courses, not something unique to ECEn 224. Each student downloads their own randomly generated bomb binary. Running it presents six phases in sequence; each phase reads a line of input, and the bomb either accepts it and moves to the next phase, or detects a wrong answer and "explodes" (prints BOOM! and reports the failure). Every phase tests a different C construct and how it compiles to machine code:

PhaseTests your understanding of
1String comparison
2Loops
3Switch statements and jump tables
4Recursive function calls
5Pointers
6Linked lists, pointers, and structures together

The entire point of the exercise is that you cannot get through it by pattern-matching against lecture slides or memorizing a few instruction idioms. You have no source for the phase functions — only compiled code. The only way to know what a phase wants is to actually read the disassembly instruction by instruction, understand what it's computing, and reason backward from a comparison to the value that would satisfy it. That's precisely the skill this whole unit has been building toward, and it's the skill Game 2 and the Final test directly: given unfamiliar assembly, can you reconstruct what it's doing?

2. Your tools

  • objdump -d — produces a static disassembly of the whole binary. This is your map: read it before you start guessing at runtime behavior.
  • gdb — the debugger. Lets you run the bomb under your control, pause it at chosen points, and inspect exactly what's in registers and memory at that moment.
  • strings <filename> — dumps every printable string embedded in the binary. Phase prompts, error messages, and sometimes the literal strings a phase is comparing against are readable this way.
  • gcc — useful not on the bomb itself, but as a sandbox: if a piece of disassembly is confusing, write a small C snippet you think might produce it (e.g. a switch statement) and compile it yourself to compare the output.

The bomb is compiled with debug information intact, so both gdb and objdump can show you real function and variable names instead of just raw addresses — use that; it's a significant head start over a fully stripped binary.

3. A general workflow

  1. Get a full static disassembly first. Run objdump -d bomb > bomb.asm and read it in an editor, not just on the terminal — you'll be jumping back and forth between phase functions and helper functions constantly.
  2. Read a phase function from the top. Don't jump straight to the comparison at the bottom. Work out what's happening to the input first: is it being parsed as a number, scanned character by character, split into fields?
  3. Find the comparisons. Every phase eventually does some form of "compare what I computed from your input against what I expect," using instructions like cmp and a conditional jump (je, jne, jg, and so on) that leads to the explosion path if the comparison fails. Identify exactly what's being compared and to what.
  4. Use gdb to check your reasoning at runtime. Set a breakpoint right before or after the comparison, run the bomb with a guessed input, and inspect the actual register and memory values. This turns "I think this is what it's checking" into a confirmed fact instead of a guess.
  5. Work backward to the required input. Once you know exactly what value (or values) a phase's comparison needs to succeed, and how your input got transformed into what's being compared, you can work out what input would produce that value.

4. Useful gdb commands

CommandWhat it does
break <func>Set a breakpoint at the start of a function (e.g. break phase_2)
runStart (or restart) the program under gdb, stopping at breakpoints
step / nextExecute one source line, stepping into calls (step) or over them (next)
stepi / nextiSame idea, but one machine instruction at a time — what you'll use most once you're reading raw assembly
print <expr>Print the value of a register or expression, e.g. print $rax
x/4xb <addr>Examine memory: 4 units, hex format, byte size, starting at <addr> (swap b for w/g for word/giant-word sizes)
disasDisassemble the current function (or another, by name) right inside gdb
info registersDump every general-purpose register's current value at once
continueResume execution until the next breakpoint or program exit
Tip: a breakpoint that stops you at the top of a phase function, followed by repeated stepi/nexti paired with print and x/… on whatever register or address just changed, is enough to work through almost every phase — you rarely need much more than this small set of commands.

5. General tips

  • Work one phase at a time. Don't try to read the whole binary end to end before starting — get phase 1 defused, then move to phase 2 with the confidence and vocabulary you built solving the first one.
  • Look for parsing before comparison. Many phases start by calling something like sscanf to pull numbers or fields out of your input string before ever comparing anything. Recognize that pattern early and you'll immediately know how many values a phase expects and roughly what shape they take, before you've even reached the actual check.
  • When disassembly is confusing, reproduce it. If you suspect a chunk of code is a compiled switch statement, write your own small switch in C and compile it with the flags suggested for this lab (roughly: gcc -S -fverbose-asm -fno-asynchronous-unwind-tables -fno-pie yourcode.c) to see matching output you can compare line by line against the bomb's.
  • Trust the debugger over your assumptions. It's easy to misread an offset or a comparison direction. When in doubt, set a breakpoint and look at the actual bytes rather than guessing from the disassembly alone.
  • Don't brute-force guess. The input space for most phases is far too large to guess blindly, and the point of the lab is the reverse-engineering process itself — the same process Game 2 will ask you to do by hand, on paper, without a debugger.
