Integer Representations

Binary alone only gives you non-negative numbers. This module covers how negative numbers get represented — and why nearly every real machine settled on one specific scheme, two's complement, instead of the more "obvious" sign-bit approach. We'll also cover the exact range formulas, sign extension, truncation, and the C casting rules that turn "signed vs. unsigned" from a footnote into a real source of bugs.

CS:APP reference: Chapter 2.2.  |  Due: HW2 — Integer Representations (closed Sep 18).  |  Tested on: Game 1 and the Final.

Learning objectives

  • Convert between decimal and two's-complement binary by hand, for a given word size
  • State and apply the range formulas for unsigned and two's-complement signed integers
  • Explain why two's complement was chosen over sign-magnitude or one's complement
  • Apply sign extension and truncation correctly when converting between C integer types
  • Predict the (often surprising) result of C expressions that implicitly mix signed and unsigned operands

1. The problem: representing negative numbers

Plain binary only encodes non-negative integers — there's no built-in notion of a minus sign. The most obvious fix is a sign bit: reserve the most significant bit to mean "negative" (1) or "positive" (0), and let the remaining bits encode the magnitude. This is called sign-magnitude representation. It's intuitive, but it has two serious problems. First, it wastes an encoding: with the MSB reserved for sign, an n-bit number can only represent magnitudes up to 2n-1 - 1, effectively halving your usable range compared to unsigned. Second, and worse, it produces two representations of zero — 0000 ("+0") and 1000 ("−0") in 4 bits — which is wasteful and, worse, breaks ordinary addition: adding 5 + (-5) with sign-magnitude arithmetic does not fall naturally out of ordinary binary addition the way you'd want.

2. One's complement, and why it's not quite enough

An alternative: represent a negative number by flipping (complementing) every bit of its positive counterpart, instead of using a dedicated sign bit convention. This is one's complement. It still has a sign bit (the MSB is 1 for negatives), and it still has a negative zero (1111 is "−0" in 4 bits) — so it doesn't fix the wasted-encoding problem. It does make addition closer to working naturally, but not perfectly: adding two one's-complement numbers sometimes produces a carry out of the top bit that has to be wrapped back around and added to the low bit (an "end-around carry") to get the correct result. That extra step is exactly the kind of special-case hardware logic engineers want to avoid.

3. Two's complement: the representation everyone uses

Two's complement starts from one's complement and removes the negative zero by shifting every negative value down by one. The result, for a 4-bit example: instead of one's complement's -7 through +7 with two zeros, two's complement covers -8 through +7 — one extra negative value, and exactly one representation of zero (0000). This asymmetry (one more negative number than positive) is a direct, permanent consequence of removing the duplicate zero, and it shows up throughout the course — for instance, -TMin (negating the most negative value) always overflows.

The formal weight of each bit in two's complement is the same as unsigned binary, except the most significant bit carries a negative weight, -2n-1, instead of positive. For a 4-bit number b3b2b1b0, the value is: 

value = b3·(-2^3) + b2·2^2 + b1·2^1 + b0·2^0

So 10112C = -8 + 0 + 2 + 1 = -5, and 11102C = -8 + 4 + 2 + 0 = -2. To negate a two's-complement number, there's a simple mechanical shortcut: invert every bit, then add 1. For example, 5 = 0101; invert to get 1010; add 1 to get 1011, which is -5 — matching the formula above.

Why did the industry converge on two's complement specifically? Because it makes addition hardware trivially simple: you add two two's-complement numbers with exactly the same binary adder circuit you'd use for unsigned addition, discard any carry out of the top bit, and the result is correct two's-complement arithmetic automatically — no end-around carry, no special-casing the sign bit. One adder circuit handles both signed and unsigned addition identically at the bit level; only the interpretation of the result differs. That hardware simplicity, more than any mathematical elegance, is why every mainstream CPU today uses two's complement.

Why did two's complement win out over sign-magnitude and one's complement as the standard signed representation?
Two's complement eliminates the wasted duplicate-zero encoding and, critically, makes signed addition just ordinary binary addition with the carry-out discarded — no end-around carry (one's complement) and no special sign-bit handling (sign-magnitude) required.

4. Range formulas

For a word size of w bits, the representable ranges are:

wUMax (unsigned)TMax (signed)TMin (signed)
8255127-128
1665,53532,767-32,768
324,294,967,2952,147,483,647-2,147,483,648
6418,446,744,073,709,551,6159,223,372,036,854,775,807-9,223,372,036,854,775,808

In general: UMax = 2w - 1, TMax = 2w-1 - 1, and TMin = -2w-1. Notice |TMin| = TMax + 1 — the direct consequence of two's complement having one extra negative value, discussed above. Both signed and unsigned use exactly the same number of total bit patterns (2w) for a given w; using signed representation doesn't lose any encodings, it just shifts which range of integers those 2w patterns cover, from [0, 2w-1] to [-2w-1, 2w-1-1].

5. Sign extension and truncation

Converting a smaller integer type to a larger one (e.g. short to int) is called expansion, and how you fill in the new, wider bits depends on signedness:

  • Zero extension (unsigned): pad with 0s on the left. E.g. unsigned short x = 15213 (0011 1011 0110 1101) expands to int ix = x as 0000 0000 0000 0000 0011 1011 0110 1101.
  • Sign extension (signed): pad with copies of the original sign bit. E.g. signed short y = -15213 (1100 0100 1001 0011) expands to int iy = y as 1111 1111 1111 1111 1100 0100 1001 0011 — the value stays -15213 because sign extension preserves both the sign and the numeric value.

Going the other direction — a larger type to a smaller one — is truncation: the high-order bits that don't fit are simply dropped, regardless of signedness, and whatever bit pattern remains is reinterpreted in the smaller type. This can silently change the value. int x = 53191 is 0000 0000 0000 0000 1100 1111 1100 0111; truncating to a 16-bit short sx = x keeps only the low 16 bits, 1100 1111 1100 0111, which as a signed short is -12345 — not 53191. The bits are preserved exactly; only the count of bits and their interpretation changed.

When a conversion needs to change both size and signedness at once (e.g. short to unsigned int), C applies the size change first, then reinterprets the sign — not the other way around.

6. The signed/unsigned casting gotcha

In C, converting between a signed and unsigned type of the same size does not change a single bit. It only changes how those bits are interpreted: 

signed char v = -63;
unsigned char uv = v;
printf("v = %d, uv = %u\n", v, uv);
// prints: v = -63, uv = 193

Both v and uv hold the identical bit pattern 1100 0001. Interpreted as signed (two's complement): -27 + 26 + 20 = -128 + 64 + 1 = -63. Interpreted as unsigned: 27 + 26 + 20 = 128 + 64 + 1 = 193. Same bits, two different numbers — purely a matter of interpretation.

The real danger is that C does this conversion implicitly, not just on explicit casts. Whenever a binary operator (including comparisons like <, >, ==) has one signed and one unsigned operand of the same size, C silently converts the signed operand to unsigned before comparing: 

-1 < 0    // TRUE  — both operands are signed int, ordinary comparison
-1 < 0U   // FALSE — the 0U forces -1 to be converted to unsigned first;
          //         as unsigned, -1's bit pattern becomes UINT_MAX,
          //         which is NOT less than 0

This exact trap shows up in real, dangerous-looking code. Consider: 

/* WARNING: buggy code */
float sum_elements(float a[], unsigned length)
{
    int i;
    float result = 0;
    for (i = 0; i <= length-1; i++)
        result += a[i];
    return result;
}

If length is 0, the programmer's intent is clearly "the loop shouldn't execute." But length is unsigned, so length - 1 is computed in unsigned arithmetic first: 0 - 1 wraps around to UINT_MAX (a huge positive number), not -1. Then i <= length-1 compares the signed i against that huge unsigned value, i gets implicitly converted to unsigned too, and the loop runs far out of bounds instead of not running at all. The fix is to avoid computing length - 1 in unsigned arithmetic in the first place — for example, loop with i < length instead of i <= length - 1.

Why does -1 < 0U evaluate to FALSE in C?
When one operand is unsigned and they're the same size, C's usual arithmetic conversions silently convert the signed operand to unsigned first. -1's two's-complement bit pattern reinterpreted as unsigned is UINT_MAX, which is not less than 0.
int x = 53191; is truncated to short sx = x;. What happens to the underlying bits during this conversion?
Truncation just drops the high-order bits that don't fit in the smaller type — no rounding or rescaling happens. That's exactly why 53191 truncates to the surprising value -12345: the remaining 16 bits happen to form a negative number in two's complement.
