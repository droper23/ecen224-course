C Pointers

Pointers are the single most important idea in this entire course. Everything after this module — the stack, the heap, function calls at the assembly level, buffer overflow attacks — is really just "what a pointer is" applied in more detail. A pointer is not a magic reference; it is a plain number: a memory address, stored in a variable like any other. Take this module seriously.

Tested on: Game 1 and the Final. This is core, foundational material — expect it woven into nearly every remaining unit of the course, not just tested once.

Learning objectives

  • Explain what a pointer's value actually is (an address), and distinguish a pointer variable from the thing it points to
  • Use & and * correctly, including in declarations vs. expressions
  • Explain why arr[i] and *(arr + i) are the same operation, including how pointer arithmetic scales by element size
  • Declare and reason about a pointer to a pointer
  • Explain why C is pass-by-value, and how passing a pointer simulates pass-by-reference
  • Identify NULL pointers, uninitialized (garbage) pointers, and the bugs each one causes

1. A pointer is just an address

Every variable you declare has two things: a value, and an address — the location in memory where that value is stored. Ordinarily you only ever think about the value. A pointer is a variable whose value is an address — it "points to" wherever that address is. 

uint32_t x = 0;
uint32_t *p;      /* p is declared as a pointer to a uint32_t */
p = &x;           /* p now holds the address of x */

Concretely, if x happens to live at address 0x100, then after p = &x;, p's own value is the number 0x100 — stored in p's own separate memory location. On a typical 32-bit architecture, an address (and so a pointer's value) is itself 32 bits wide; on the 64-bit systems this course otherwise focuses on, it's 64 bits. Either way: a pointer is not special magic, it is a number, and it takes up real, fixed-size storage just like an int does.

Two operators are the entire foundation of pointers, and they are exact opposites of each other:

OperatorNameDoes
&xaddress-of / referencegives the address where x lives
*pdereference / indirectionaccesses (reads or writes) the value stored at the address p holds
int x = 7;
*(&x) = 7;   /* take x's address, then dereference it — same as just writing to x directly */

& only applies to things that actually live somewhere in memory — a variable or an array element — not to a literal constant, a register, or an arbitrary expression. You can't write &5 or &(a + b); there's no single memory address that "holds" a computed expression's result.

2. Reading a pointer's value vs. what it points to

It's worth walking through exactly what each line does, because this is where most of the early confusion happens: 

uint32_t x = 0;
uint32_t *p;
p = &x;       /* p := address of x, e.g. 0x100 */
*p = 13;      /* go TO address 0x100, write 13 there — x is now 13 */
printf("%x\n", x);    /* d  — x's own value */
printf("%x\n", &x);   /* 100 — x's address */
printf("%x\n", p);    /* 100 — p's value (which is x's address) */
printf("%x\n", *p);   /* d  — dereferencing p reads x's value */
printf("%x\n", &p);   /* 104 — p is a variable too, and it has its OWN address */

That last line is the detail people miss: p itself lives somewhere in memory, separate from x. &p is the address of the pointer variable itself, not the address it's currently holding. A pointer is a box that happens to contain an address; the box itself also has an address, one level further out.

Rule: a pointer should always point to something valid, or be NULL. A freshly declared pointer with no initializer holds garbage — whatever bit pattern was already sitting in that memory, which is not a valid address for anything you own. Dereferencing it is undefined behavior: it might crash immediately (a segmentation fault, if you're lucky and the garbage address isn't mapped to your process), or it might silently read or corrupt memory that belongs to something else entirely, which is far more dangerous because nothing visibly goes wrong right away. 
uint16_t *p2;      /* uninitialized — garbage value */
*p2 = 13;          /* undefined behavior: writing through a garbage address */
Given uint32_t x = 0; uint32_t *p = &x; uint32_t **p2a = &p; — what does **p2a refer to?
p2a holds the address of p (a pointer to a pointer). Dereferencing once, *p2a, gets you p's value — which is the address of x. Dereferencing again, **p2a, follows that address to get x's actual value. Each * peels back one layer of indirection.

3. Pointer arithmetic and arrays: arr[i] is *(arr + i)

This is the single most important equivalence in this module, and it's not a coincidence or a shorthand — it's literally how array indexing is defined in C. An array name, used in an expression, decays into a pointer to its first element. So arr[i] and *(arr + i) are not just equivalent in effect — the compiler treats them as exactly the same operation. 

int a[5];
int *pa = &a[0];    /* pa points to a[0] — equivalently, pa = a; */
int x = *pa;         /* copies a[0] into x */
int y = a[2];         /* copies a[2] into y */
int z = *(pa + 2);    /* also copies a[2] into z — same operation as y */

The reason this works is that pointer arithmetic is automatically scaled by the size of the pointed-to type. pa + 2 does not mean "add 2 to the numeric address"; it means "advance 2 elements," which the compiler implements as adding 2 * sizeof(*pa) bytes to the address. This is exactly why a pointer's declared type matters, even though its stored value is just a number in every case:

Pointer typep + 1 advances the address by
char *1 byte
short *2 bytes
int *4 bytes
double *8 bytes
struct my_t *sizeof(struct my_t) bytes
uint16_t A[5] = {0, 2, 4, 6, 8};
uint16_t *p = A;      /* p points to A[0], e.g. address 0x100 */
p++;                   /* p now points to A[1] — address 0x102, NOT 0x101 */
p = p + 2;             /* p now points to A[3] — advanced 2 uint16_t's = 4 bytes */

Because of this equivalence, everything valid with array subscripting is expressible with pointers, and vice versa — p[1] works even though p is declared as a plain pointer, not an array, because p[1] is defined as *(p + 1) regardless of whether p started life as an array name or an ordinary pointer variable.

An array name is not a pointer variable. a in int a[5]; is a label for a fixed block of memory, not a variable that itself holds an address you can reassign. a = pa; and a++; are both illegal — there's no storage location holding "a's current pointer value" the way there is for an actual pointer variable like pa. This is subtle: a behaves like a pointer in most expressions (it decays into one), but it is not an lvalue you can assign to.

Valid pointer arithmetic is otherwise deliberately limited: you can add or subtract an integer offset, compare two pointers, or subtract one pointer from another — but only when both pointers point into the same array. Subtracting two pointers into the same array gives you the number of elements between them: 

int a[5];
int *p = &a[1];
int *q = p + 2;        /* q points to a[3] */
if (p < q) printf("%ld\n", q - p);   /* prints 2 — element count, not byte count */
Given uint16_t A[5]; uint16_t *p = A; p = p + 3; — if A starts at address 0x100, what address does p now hold?
uint16_t is 2 bytes. Pointer arithmetic scales by the pointed-to type's size, so p + 3 advances 3 elements = 3 × 2 = 6 bytes: 0x100 + 6 = 0x106. This is precisely the mechanism that makes arr[i] and *(arr + i) equivalent — the "+i" is always in units of elements, never raw bytes.

4. Pointers and function parameters: simulating pass-by-reference

C is strictly pass-by-value: when you call a function, every argument is copied into the function's local parameters. The function operates on its own private copies; it has no way to reach back and modify the caller's original variables — unless you explicitly hand it their addresses. 

void swap(int x, int y)      /* WRONG — x and y are local copies */
{
  int temp = x;
  x = y;
  y = temp;
}
/* swap(a, b) has zero effect on a and b — only the copies got swapped */

To let a function actually modify the caller's variables, pass pointers to them. The function still receives its parameters by value — but now what's being copied is an address, and dereferencing that address reaches the original variable, not a copy of its value: 

void swap(int *px, int *py)   /* px, py are pointers — still passed by value! */
{
  int temp = *px;
  *px = *py;
  *py = temp;
}
swap(&a, &b);   /* pass addresses — this DOES swap a and b */

It's worth being precise about what happened: px and py are still local copies, exactly as pass-by-value promises — but what got copied into them was a's and b's addresses, and an address copy still points at the same original memory. This is why C is accurately described as "always pass-by-value," full stop — pointers don't violate that rule, they just make the value being passed an address instead of a plain number, which is enough to simulate pass-by-reference for every practical purpose.

This is also the mechanism behind returning "multiple values" from a function that can only return one value directly: pass pointers to as many output variables as you need, and write through them.

Why does void swap(int x, int y) fail to swap the caller's variables, while void swap(int *px, int *py) succeeds?
C never stops being pass-by-value. In the first version, x and y are fresh copies of a and b's values, so swapping them is invisible to the caller. In the second version, px and py are still fresh copies — but copies of a and b's addresses. *px and *py dereference those addresses, reaching the original a and b directly, so the swap is visible outside the function.

5. Pointers to structures

Given a pointer to a struct, you can reach a member two equivalent ways: dereference first, then use ., or use the combined arrow operator ->: 

struct point { int x; int y; };
struct point s1 = {1, 2};
struct point *p = &s1;

(*p).x = 3;   /* dereference p, then access member x — parens required! */
p->y = 4;     /* equivalent, and the conventional way to write it */
printf("%d, %d\n", p->x, p->y);   /* 3, 4 */

The parentheses in (*p).x are not optional: . has higher precedence than unary *, so *p.x without parentheses would parse as *(p.x) — trying to access a member x directly on p (which is a pointer, not a struct, and has no such member) and then dereference the result. -> exists specifically so you never have to write the awkward parenthesized form.

6. NULL pointers and common bugs

NULL is a special pointer value (defined as 0, or more precisely a null pointer constant, in the standard headers) that is guaranteed not to point to any valid object. It's the conventional way to say "this pointer intentionally points to nothing right now" — e.g. fopen returns NULL on failure (Module 7), rather than a pointer to a real file. 

int *p = NULL;
if (p != NULL) {
  *p = 5;    /* only dereference after confirming it's non-NULL */
}

The three pointer bugs worth being able to recognize by sight, because they're the ones this course (and real debugging) will keep confronting you with:

BugWhat's actually wrong
Uninitialized pointerDeclared but never assigned; holds garbage. Dereferencing it accesses a random address.
NULL dereferenceExplicitly points to nothing (address 0), and something dereferences it anyway (e.g. skipping the != NULL check after fopen/malloc). Typically crashes immediately and predictably, which — compared to the other two rows here — actually makes it one of the easier pointer bugs to diagnose.
Dangling pointerOnce pointed somewhere valid, but that memory has since been freed or gone out of scope; the pointer's bit pattern is now stale.
Notice the common thread: in every case, the fix is the same discipline stated back in section 2 — a pointer should always be either NULL or pointing at something currently valid, and code that dereferences a pointer should be confident which of those two states it's in before doing so.
