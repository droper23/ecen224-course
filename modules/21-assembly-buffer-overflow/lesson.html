Buffer Overflow

C trusts you completely: it never checks that a write to an array actually lands inside that array. Module 19 showed that the stack frame packs local variables right next to the return address that controls where execution goes next. Put those two facts together and you get one of the most consequential bug classes in computing history — this module covers the mechanism, why it's dangerous, and the defenses modern systems build in.

CS:APP reference: Chapter 3.10.  |  Tested on: Game 2 and the Final.

Learning objectives

  • Explain mechanically how writing past the end of a stack buffer can corrupt a saved return address
  • Identify why unbounded string functions like gets() and strcpy() are dangerous, and what to use instead
  • Describe how a corrupted return address can hijack control flow ("stack smashing")
  • Name the three major modern mitigations and explain what each one actually prevents
  • Explain why none of these mitigations fully eliminates the underlying problem

1. The setup: no bounds checking, and neighbors on the stack

Two ordinary facts about C combine into a serious problem the moment you put them together:

  • C performs no bounds checking on array references. Writing to buf[24] when buf only has 4 elements is not an error the language detects — it's just a memory write to whatever address that indexing arithmetic happens to compute.
  • Local variables share the stack with control information. As Module 19 covered, a stack frame holds local variables (like a character buffer) right alongside saved register values and the return address that says where execution resumes after the function returns.

So: a write to an out-of-bounds array element that lives on the stack doesn't just corrupt some unrelated variable — if the array is stored below (i.e., before, given the stack grows down) the saved registers and return address in memory, writing past its end walks straight into that control information. This is generically called a buffer overflow, and when it clobbers a return address specifically, it's often called stack smashing.

2. How it happens: unbounded string input

The single most common real-world trigger is a string-handling function that copies input of unknown length into a fixed-size buffer with no limit check. The classic offender is gets(): 

/* Get a string from stdin -- classic (dangerous) implementation */
char *gets(char *dest) {
    int c = getchar();
    char *p = dest;
    while (c != EOF && c != '\n') {
        *p++ = c;          /* no check that p is still inside dest's buffer! */
        c = getchar();
    }
    *p = '\0';
    return dest;
}

gets() has no parameter for the buffer's size — it simply keeps writing characters until it sees a newline or end-of-file, no matter how big the destination actually is. strcpy() has the same defect for a different reason: it copies until it sees a NUL byte in the source, regardless of how much room the destination has. scanf(), fscanf(), and sscanf() inherit the same risk whenever they're given an unbounded %s conversion.

Consider a function with an obviously undersized buffer:

void echo() {
    char buf[4];   /* way too small for typical input */
    gets(buf);
    puts(buf);
}

Compiled, the frame for echo allocates 24 bytes below the return address:

echo:
  subq  $24, %rsp     # allocate the frame -- buf gets 4 bytes of it
  movq  %rsp, %rdi     # pass &buf[0] to gets
  call  gets
  ...

A 4-byte buffer sitting inside a 24-byte frame means there are exactly 20 bytes of "extra" space before the saved return address is reached. An input string of 24 characters fits inside that slack and the return address survives untouched. An input just one byte longer starts overwriting the return address itself — at that point, what ret jumps to next is no longer under the program's control, it's whatever bytes the input happened to supply. Depending on exactly what ends up there, the visible result ranges from the program working by pure coincidence, to a segmentation fault, to — if an attacker chose those bytes deliberately — execution being redirected to code of the attacker's choosing. This is exactly how the 1988 Morris worm and countless vulnerabilities since have compromised real machines: not through some exotic flaw, but through an ordinary unbounded string copy into an ordinary stack buffer.

Why is a stack buffer overflow potentially more dangerous than, say, overflowing an array allocated on the heap?
The danger isn't the stack itself — it's proximity. A stack frame packs local buffers next to saved registers and the return address, so a big enough overflow reaches control information that directly determines what code runs next.

3. Fixing the source: bounded functions

The most direct defense is simply not calling unbounded functions on untrusted input in the first place. Every dangerous function above has a bounded counterpart that takes an explicit size limit:

AvoidUse instead
gets(buf)fgets(buf, sizeof(buf), stdin)
strcpy(dst, src)strncpy(dst, src, sizeof(dst))
scanf("%s", buf)scanf("%63s", buf) (an explicit width), or fgets

This is a code-level fix, not a system-level one — it only helps if the programmer actually uses the bounded version everywhere. The next section covers what the platform does to protect programs that don't.

4. System-level mitigations

Because programmers keep making the same mistake, modern compilers and operating systems add layers of defense that don't rely on every line of code being written correctly. Three are standard on essentially every machine you'll use:

MitigationHow it worksWhat it stops
Stack canariesThe compiler (GCC's -fstack-protector, on by default) inserts a random guard value between local buffers and the saved return address. Before returning, it re-checks that value; a mismatch aborts the program instead of returning.Detects that an overflow reached the return address, and stops before control is transferred to corrupted data — but only for buffers the compiler chose to protect, and only for a straight-through overflow that has to cross the canary to reach the return address.
ASLR (stack randomization)The OS places the stack (and other regions) at a randomized address each time the program runs.Makes it much harder for an attacker to know in advance the address of anything they'd want to jump to — but a large-enough exposed range, or a leaked address, can defeat it.
Non-executable stack (NX / DEP)The OS marks stack (and heap) memory pages as writable but not executable, using a hardware-enforced permission bit.Blocks the classic technique of writing attacker-supplied machine code onto the stack and jumping into it — but does not stop an attacker from redirecting control to code that already exists and is already marked executable, such as chaining together fragments of the program's own compiled code (an approach known as return-oriented programming).
None of these fixes the underlying bug. Canaries, ASLR, and NX are all mitigations that make exploitation harder and turn many overflows into a clean crash instead of a hijack — they don't stop C from writing wherever an out-of-bounds index says to. The only real fix is not overflowing the buffer in the first place: use bounded functions, validate lengths, and treat every buffer that touches untrusted input as security-critical code.
A program is compiled with stack canaries, ASLR, and a non-executable stack all enabled. Is it now safe to call gets() on untrusted input?
These are called mitigations, not fixes, for a reason: the array write with no bounds check still happens exactly as before. A canary can only detect corruption after the fact, ASLR can be defeated by a leaked address, and NX doesn't stop attacks that reuse existing executable code. The buffer is still overflowed.
