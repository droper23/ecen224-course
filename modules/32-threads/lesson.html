Threads

Threads are the lightweight alternative to processes previewed back in module 29: multiple logical flows of execution that share one process's entire address space instead of each getting an isolated copy. That sharing is what makes threads fast and easy to communicate between — and it's exactly what makes them dangerous. This module covers the pthreads API, the race conditions shared memory invites, and mutexes as the fix.

CS:APP reference: Chapter 12.3, 12.5.  |  This material comes after Game 2 and is tested only on the comprehensive Final.

Learning objectives

  • Contrast threads and processes: what each shares and what each keeps private
  • Use pthread_create/pthread_join to spawn and reap a thread
  • Explain why shared memory between threads creates race conditions
  • Explain how a mutex prevents a race, and what deadlock is

1. What is a thread?

A thread is a logical flow of execution that runs inside the context of a process. Multiple threads can run concurrently within a single process, and — this is the defining difference from module 30's processes — all threads in a process share that process's entire virtual address space: the same code, the same global data, the same heap, the same open file descriptors. What each thread keeps private is much smaller: its own thread ID (TID), its own stack and stack pointer, its own program counter, its own general-purpose registers and condition codes. The OS kernel schedules threads automatically, the same way it schedules processes.

ThreadsProcesses
Address spaceShared across all threads in a processPrivate to each process by default
Creation costCheap — roughly 10× faster than a processRelatively slow and heavy
CommunicationTrivial — just read/write shared memoryRequires explicit IPC (a file, a socket, shared memory)
Logical structureA flat pool of peer threads within one processA parent/child tree hierarchy
Isolation / safetyNone between threads — a bug in one can corrupt another's dataStrong — one process crashing doesn't corrupt another's memory

What threads and processes have in common: each has its own logical control flow, each can run concurrently with the others (genuinely in parallel, if there are multiple cores available), and each gets context-switched by the scheduler. Where they differ is exactly what you'd expect from "threads share memory, processes don't": threads are cheaper to create and trivially easy to communicate between, at the cost of losing the safety net of isolation.

2. The pthreads interface

Pthreads (POSIX threads) is the standard C interface — around 60 functions — for creating, coordinating, and tearing down threads. The two you'll use constantly: 

#include <pthread.h>

int pthread_create(pthread_t *restrict thread,
                    const pthread_attr_t *restrict attr,
                    void *(*start_routine)(void *),
                    void *restrict arg);

int pthread_join(pthread_t thread, void **retval);

pthread_create spawns a new thread that immediately starts running start_routine. The attr argument (thread attributes) is usually just NULL for the default behavior; arg is a single void * pointer passed through to the thread's function, which is how you get data into a thread since it doesn't take a normal argument list; the thread's pthread_t ID is written into thread. pthread_join is the thread equivalent of wait() from module 30 — it blocks the calling thread until the target thread finishes, and can capture its return value through retval.

A minimal pthreads program makes the shape clear: 

void *thread(void *vargp) /* thread routine */
{
    printf("Hello, world!\n");
    return NULL;
}

int main()
{
    pthread_t tid;
    pthread_create(&tid, NULL, thread, NULL);
    pthread_join(tid, NULL);  // wait
    exit(0);
}

start_routine's signature, void *(*)(void *), is a function pointer — a variable that holds the address of a function rather than an address of data. The general syntax for declaring one mirrors an ordinary declaration with the name wrapped in parens and starred: int (*add)(int, int) declares a pointer to a function taking two ints and returning an int, and you'd call through it as (*add)(5, 10). pthread_create uses exactly this mechanism because it has to accept an arbitrary caller-defined function to run as the new thread — C doesn't have a lighter-weight syntax for "pass in a callback" than a function pointer.

3. A worked example: thread2.c

Here is the real thread2.c distributed for this course. It spawns one peer thread to do work while the main thread does its own, separate work at the same time: 

int main() {
    printf("******* Threading Example *******\n");
    pthread_t thread;

    if (pthread_create(&thread, NULL, do_work, NULL)) {
        printf("An error occurred while creating thread.\n");
        return EXIT_FAILURE;
    }

    printf("Main: Hi!\n");
    for (int i = 0; i < 10; i++) {
        printf("Main: Doing work... (%d)\n", i);
        sleep(1);
    }

    pthread_exit(NULL);
    return EXIT_SUCCESS;
}

void *do_work(void *arg) {
    printf("Peer: Hi!\n");

    for (int i = 0; i < 10; i++) {
        printf("Peer: Doing work (%d)...\n", i);
        sleep(1);
    }
    pthread_exit(NULL);
}

Notice there's no pthread_join here — instead, both the main thread and the peer thread call pthread_exit(NULL), which terminates just the calling thread without ending the whole process (that's the contrast with plain exit(), which tears down every thread in the process at once). Because main doesn't wait for the peer, and both threads print once per second in a loop, the "Main: Doing work..." and "Peer: Doing work..." lines interleave on your terminal in whatever order the scheduler happens to run them — a live demonstration of concurrent, not sequential, execution.

Each thread here only touches its own local loop variable i — one declared inside main's for, the other inside do_work's for — so even though their output interleaves unpredictably, there's no shared data being fought over. That's the calm case. The next section shows why it usually isn't this simple.

4. The hazard: race conditions on shared memory

The moment two threads both read and write the same shared variable, you have a race condition risk — this is the core hazard module 29 previewed. Suppose, instead of each thread incrementing its own private loop counter the way thread2.c does, both threads incremented one shared global counter: 

int counter = 0;  // shared by every thread

void *do_work(void *arg) {
    for (int i = 0; i < 10; i++) {
        counter++;   // NOT safe if another thread does this too
    }
    return NULL;
}

counter++ looks like one step, but it isn't at the machine level: the CPU has to read counter's current value, add one to it, then write the new value back. If two threads both read the same old value before either writes its incremented result back, one of the two increments is silently lost — the exact "two people spending from the same shared account" race described in module 29. Which interleaving actually happens depends on the scheduler, which is why race conditions are so notoriously hard to reproduce and debug: the same program can produce the correct answer on one run and a subtly wrong one on the next.

This is precisely the trade-off from section 1: threads share memory to make communication effortless, and that same sharing is what makes uncoordinated access to shared data unsafe. Local variables (each thread's own stack) are safe by construction — module 29's table noted local variables are not shared between threads. Global variables and heap data are shared, and that's where synchronization becomes necessary.

Why doesn't thread2.c as written have a race condition, even though the main thread and the peer thread both run a loop at the same time?
Races require the same writable memory location to be accessed by more than one thread without coordination. thread2.c's two loop counters each live on their own thread's private stack, so nothing is actually shared here — only the interleaving of their printf output is nondeterministic, not any underlying data.

5. Mutexes: the basic fix

A mutex ("mutual exclusion" lock) is the standard tool for protecting shared data: it lets you mark a region of code as one only a single thread may execute at a time. Any other thread that tries to enter while it's locked simply blocks until the thread holding it unlocks it. 

pthread_mutex_init(&mutex, NULL);

pthread_mutex_lock(&mutex);
counter++;              // now safe: only one thread can be here at a time
pthread_mutex_unlock(&mutex);

Wrapping the read-modify-write of counter between pthread_mutex_lock and pthread_mutex_unlock turns the three machine-level steps back into something that behaves as if it were a single atomic step from every other thread's point of view — no other thread can sneak in and read a stale value while the lock is held. The section of code between lock and unlock is often called a critical section.

Mutexes solve races, but they introduce their own hazard if used carelessly: deadlock, previewed back in module 29 as traffic gridlock. The classic version happens with two mutexes: thread A locks mutex 1 and then tries to lock mutex 2, while thread B has already locked mutex 2 and is trying to lock mutex 1. Neither thread can ever proceed — each is waiting on a lock the other is holding, forever. The general defense is discipline: always acquire multiple locks in the same, consistent order across every thread that needs them.

What does locking a mutex around counter++ actually prevent?
A mutex doesn't change how counter++ executes at the machine level (it's still read, add, write) — it changes who else is allowed to touch counter while that happens. Any other thread trying to lock the same mutex has to wait until it's unlocked, so the three-step increment is never interleaved with another thread's access to the same variable.
