Debugging

Every program you write will have bugs. The difference between a frustrating afternoon and a five-minute fix is whether you have a process for finding them. This module covers the mindset that keeps bugs out in the first place, the categories of errors you'll run into, and the concrete tools — compiler warnings, printf, and gdb — for tracking down the ones that get through anyway.

CS:APP reference: Chapter 7.10.  |  Tested on: Game 1 and the Final.

Learning objectives

  • Explain why incremental development shrinks the search space for bugs
  • Distinguish syntactic, semantic, and algorithmic errors
  • Recognize the common causes of segfaults, uninitialized-variable bugs, off-by-one errors, and memory corruption
  • Read a compiler warning or error and use it to localize a bug, and know what -Wall -Wextra catch
  • Use gdb's core commands — breakpoints, step, print, backtrace — to inspect a running program

1. Debugging starts before you write the bug

Edsger Dijkstra put it bluntly: "If debugging is the process of removing software bugs, then programming must be the process of putting them in." You cannot avoid writing bugs entirely, but you can radically change how many you write and how long they take to find, just by how you approach writing code in the first place.

Contrast two strategies. Guess-and-check programming means trying something, running it, and seeing what happens — low mental effort per line, but you're rarely sure the code is correct in all cases, and the resulting code is often hard to read later, which makes the debugging you eventually have to do slower. Intentional programming means thinking through what a piece of code needs to do before you write it, prioritizing code that is clear and easy to follow. It costs more up front. It saves far more later, because clear code is easier to reason about when something goes wrong.

The same trade-off shows up at the scale of a whole program. Whole development — writing a large chunk of a program and only then testing it — means that when something breaks, the bug could be anywhere in all the code you just wrote: a needle in a haystack. Incremental development — writing a small, testable chunk, confirming it works, and only then moving to the next chunk — keeps the search space small. If a chunk was working before your last change and isn't now, you know almost exactly where to look. Test-driven development pushes this further: write the tests a piece of code should pass before you write the code, so every change you make afterward is checked automatically, both for the new behavior and for the old behavior you don't want to break.

None of this is free advice about style for its own sake — meaningful variable names and clear structure are a bug countermeasure. Code like Balance = Balance - LastPayment; is easy to check against your intent; code that does the same arithmetic with variables named I, II, and III is not, and every extra second you spend decoding what a variable is is a second you're not spending on whether the logic is correct.

2. Three kinds of errors

When something goes wrong, it helps to know which category you're in, because each one is found differently:

  • Syntactic errors — the code isn't legal C at all (a missing semicolon, an unmatched brace). The compiler catches these for you and refuses to produce an executable.
  • Semantic errors — the code is legal C, but it doesn't do what you intended. The compiler has no way to know your intent, so it compiles cleanly and the bug only shows up when you run the program.
  • Algorithmic errors — the code does exactly what you intended, but what you intended doesn't solve the actual problem. The program "works" in the sense of matching your design, and the design is wrong.

A single missing brace shows how syntactic and semantic errors can hide next to each other:

main (){
  int i
  int j;
  for (i = 0; i <= 10; i++)
      j = i * 7;
     printf("%d x 7 = %d\n", i, j);
}

int i with no semicolon is a syntactic error — the compiler will refuse to build this and point you straight at the line. But even after you fix that, the printf is not inside the loop body (there's no { } around it), so it only runs once, after the loop finishes, instead of once per iteration. That compiles fine — it's a semantic error, and it will only show up when you notice the output is missing 10 lines.

3. Common C bugs to recognize on sight

A few categories of bug account for a disproportionate share of debugging time in C, precisely because C does not protect you from them the way higher-level languages do.

  • Segmentation faults. The OS kills your process because it tried to access memory it doesn't own — dereferencing a NULL or uninitialized pointer, indexing far past the end of an array, or using memory after it's been freed. A segfault tells you that you touched bad memory, not why — that's what a debugger is for.
  • Uninitialized variables. Local variables in C do not start at zero; they hold whatever bits were already sitting in that stack slot. Code that reads a variable before writing to it can appear to work by accident (if the leftover bits happen to be harmless) and then fail unpredictably later, often when you least expect it — which makes it one of the nastier bugs to reproduce.
  • Off-by-one errors. Loop and array bounds are the classic source: a loop written as for (i = 0; i <= n; i++) over an array of size n reads or writes one element past the end on the last iteration. C performs no bounds checking, so this doesn't necessarily crash immediately — it silently corrupts whatever memory happens to sit right after the array.
  • Memory corruption. Writing outside the bounds you were given — through a bad array index, a bad pointer, or a buffer that's too small for what you copy into it — can overwrite a completely unrelated variable, a saved return address, or the heap's own bookkeeping data. The symptom often shows up far away from the cause: a variable that "changes on its own" a hundred lines after the actual bad write. This is also the root cause behind buffer-overflow security vulnerabilities, which you'll see again later in this course.
A program crashes with a segmentation fault. What does that tell you?
A segfault means the OS caught an illegal memory access — a bad pointer dereference, an out-of-bounds array access, use-after-free, and so on. It doesn't localize the bug for you; that's what tools like gdb and careful reasoning are for.

4. Let the compiler find bugs for you

The cheapest bug to fix is one the compiler catches before you ever run the program. If your code doesn't compile, that's where to start — and read the line number the compiler reports, though remember it's an estimate: a missing brace or semicolon on one line often surfaces as an error several lines later, at the point where the compiler's parsing finally breaks down.

Warnings matter just as much as errors, because C will happily compile code that is almost certainly a bug — an assignment where you meant a comparison, a function used before it's declared, a variable that's never used. By default gcc stays quiet about most of these. Turning on warnings makes the compiler tell you: 

gcc -Wall -Wextra -o prog main.c sum.c
  • -Wall enables a broad set of warnings for constructs that are usually mistakes (unused variables, comparisons that are always true, a suspicious-looking if with an empty body, and more)
  • -Wextra adds further warnings -Wall doesn't cover

Treat warnings as errors you haven't looked at yet. A clean compile with -Wall -Wextra won't catch algorithmic or all semantic errors, but it eliminates a large class of mistakes for free, before you ever have to reach for a debugger.

5. Finding bugs: confirmation, not guessing

Debugging is fundamentally a process of confirming assumptions until you find the one that's false. As Norman Matloff put it, finding a bug means confirming the many things you believe are true about your program, one at a time, until you hit the one that isn't. You believe a variable has a certain value at a certain point; you believe an if/else takes the branch you expect; you believe a function receives the arguments you passed it. Debugging is checking each of those beliefs against reality.

The efficient way to do this is binary search over your program's behavior: pick a point roughly in the middle of the buggy code path, confirm whether everything up to that point is correct, and then recurse into whichever half still contains the bug. This is exactly why incremental development (Section 1) helps so much — it does binary search for you in advance, by keeping "everything up to the last chunk I tested" already confirmed.

6. Printf debugging

The simplest technique: add printf calls at strategic points to print out a variable's value, or to print a marker that tells you which branch of an if was taken. It requires no special tools and works anywhere you can run the program, which makes it genuinely effective for confirming a specific assumption quickly.

It has real drawbacks, though. Every time you want to check something new, you have to add a print, recompile, and rerun; once you're done, you have to remember to remove the prints again (or they clutter your real output). For a large program, or a bug that only appears after a lot of execution, this recompile-rerun cycle is slow compared to a debugger, where you can inspect any variable at a breakpoint without editing the source at all.

7. Using gdb

gdb (the GNU debugger) lets you pause a running C program and inspect it directly — step through it instruction by instruction, or line by line, and look at any variable's actual value, without adding a single print statement. You'll use it in this course's lab assignments, and again in the bomb and attack lab assignments later in the semester, so it's worth being comfortable with the basics now. Compile with -g so gdb can map machine instructions back to your source lines: 

gcc -g -o prog main.c sum.c
gdb ./prog
CommandWhat it does
break sum / b sum.c:20Set a breakpoint at a function name or a file:line — execution stops there
run / rStart (or restart) the program, running until the first breakpoint
next / nExecute the next source line, stepping over function calls
step / sExecute the next source line, stepping into function calls
print x / p xPrint the current value of variable or expression x
backtrace / btShow the call stack — which function called which, all the way to main
continue / cResume running until the next breakpoint (or the program ends)

The workflow this enables is exactly the "confirmation" idea from Section 5: set a breakpoint right before the point where you believe something is true, run, and use print to check it. If it's wrong, backtrace tells you how you got there, and you move your breakpoint earlier to find where the value went bad.

Your program segfaults somewhere inside a function that's called from several places. You want to know which call path led to the crash. Which gdb command tells you that?
backtrace prints the full chain of function calls (the call stack) that led to the current point of execution, which is exactly what you need to find which caller triggered the crash.
Which best describes the relationship between printf-debugging and gdb?
Both are tools for the same underlying task — confirming what your program is actually doing. printf is quick and requires no tooling but needs a recompile for every new question; gdb lets you inspect any variable or the call stack interactively, without touching the source.
