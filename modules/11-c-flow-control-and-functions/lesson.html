Flow Control & Functions

This module rounds out core C syntax: the branching and looping constructs that control which statements run, and functions — how C organizes code into reusable, callable units. Later in the course, once you're reading x86-64 assembly, you'll see exactly how each of these constructs actually compiles down to jumps and comparisons and stack frames. For now, the goal is fluency in the C-level syntax and semantics.

Tested on: Game 1 and the Final.

Learning objectives

  • Write correct if/else chains and explain the dangling-else ambiguity
  • Choose between for, while, and do-while loops based on when the condition should be tested
  • Trace a switch statement including fallthrough behavior, and explain why break matters
  • Distinguish a function declaration (prototype) from its definition
  • Trace a recursive function's calls and explain, at a conceptual level, why each call needs its own stack frame

1. Statements and blocks, and the dangling else

An expression becomes a statement once it's followed by a semicolon (x = 0;, i++;). Braces { } group multiple statements into a single compound statement, a block, which can be used anywhere a single statement is expected — as the body of an if, a loop, or a function.

The if/else statement expresses a decision: the condition is evaluated first, and the following statement runs only if it's nonzero; the (optional) else branch runs if it's zero. 

if (expression)
  statement1;    /* runs if expression is nonzero */
else
  statement2;    /* runs if expression is zero */
The dangling else. When if statements nest without braces, it's not always visually obvious which if an else belongs to: 
if (n > 0)
  if (a > b)
    z = a;
  else
    z = b;
Indentation here is a lie the reader tells themselves — C's actual rule is that an else always binds to the closest previous if that doesn't already have an else. So the else above binds to if (a > b), not if (n > 0), regardless of how it's indented. If you intend the outer binding, you must force it with explicit braces: if (n > 0) { if (a > b) z = a; } else z = b;. When in doubt, use braces.

else if chains multiple conditions for a multi-way decision. Conditions are evaluated top to bottom, in order, and the first true one wins — later branches are never even evaluated once one has matched: 

if (score >= 90)
  grade = 'A';
else if (score >= 80)
  grade = 'B';
else if (score >= 70)
  grade = 'C';
else
  grade = 'F';
In if (n > 0) if (a > b) z = a; else z = b; (no braces), which if does the else belong to?
C resolves the dangling-else ambiguity with a fixed rule: an else always attaches to the nearest preceding if that doesn't already have its own else. Here that's if (a > b), so z = b only runs when n > 0 AND a <= b — not simply whenever n <= 0, which is what indentation alone might suggest.

2. Switch statements and fallthrough

switch is a multi-way branch that tests one expression against a set of constant integer values: 

switch (c) {
  case '+':
    r = a + b;
    break;
  case '-':
    r = a - b;
    break;
  case '*':
    r = a * b;
    break;
  default:
    printf("Invalid operation!\n");
    break;
}
Cases fall through by default. Execution jumps to the matching case label and then just keeps running statements downward — it does not automatically stop at the next case. break is what causes an immediate exit from the switch; omit it, and control "falls through" into the next case's code, running it too: 
switch (c) {
  case '+':
  case '-':        /* no break above — '+' and '-' share this code */
    r = do_add_or_sub(a, b, c);
    break;
  case '*':
    r = a * b;
    /* forgot break here! */
  case '/':
    r = r / c;      /* BUG: this now runs for '*' too, by accident */
    break;
}
Stacking case labels with no code between them (like '+' and '-' above) is a deliberate, idiomatic use of fallthrough. Forgetting a break where you didn't intend fallthrough is one of the most common switch-statement bugs in C.

default runs if no other case matches; it's optional, and if it's absent and no case matches, the switch simply does nothing and control continues after it. default's position among the cases doesn't affect when it runs — it's only reached by falling through or by no other case matching, not by its textual position — though convention places it last.

3. Loops: for, while, do-while

C has three looping constructs, and the difference between them is really about when the condition is tested and how the loop's bookkeeping is organized. 

while (expression)
  statement;
/* tests the condition BEFORE each iteration — may run zero times */

for (expr1; expr2; expr3)
  statement;
/* equivalent to:
   expr1;                 // initialize, runs once
   while (expr2) {         // condition, tested before each iteration
     statement;
     expr3;                // increment/update, runs after each iteration
   }
*/

do
  statement;
while (expression);
/* tests the condition AFTER each iteration — always runs at least once */

for is preferred whenever a loop has a natural init/test/update structure, because it keeps all three pieces of loop control together and visible in one place, rather than scattered across the loop body. Any of the three clauses can be omitted — for (;;) { ... } is an idiomatic infinite loop — and the comma operator lets you initialize or update more than one variable at once: 

for (i = 0, j = strlen(s) - 1; i < j; i++, j--) {
  /* i counts up, j counts down, together */
}

do/while is the right choice specifically when the loop body must run at least once regardless of the condition — e.g. reading input and then checking whether to continue: 

do {
  c = getchar();
} while (c == ' ');   /* skip spaces — but only checks AFTER reading one */

break exits the innermost enclosing loop (or switch) immediately. continue skips the rest of the current iteration's body and jumps straight to the next iteration's test/update: 

for (i = 0; i < n; i++) {
  if (a[i] < 0)
    continue;      /* skip negative elements, but keep looping */
  /* ...process positive elements... */
}
A loop must read at least one line of input before it can decide whether to keep looping. Which loop construct is the natural fit?
while and for both test their condition BEFORE the first iteration, so if the condition itself depends on something the loop body hasn't produced yet (like a line just read), they can't be evaluated correctly on the first pass. do/while tests after the body runs, guaranteeing at least one execution before any check — exactly what "read, then decide whether to continue" needs.

4. Functions: declaration vs. definition, revisited

A function definition gives its full body: 

int addNumbers(int x, int y)
{
  return x + y;
}

A function declaration (also called a prototype) only announces the function's name, return type, and parameter types — enough for the compiler to check calls against it, without yet providing an implementation: 

int addNumbers(int, int);   /* declaration/prototype — no body */

int main(void)
{
  printf("Result is: %d\n", addNumbers(4, 5));   /* compiler checks this call against the prototype */
}

int addNumbers(int x, int y)   /* the actual definition, can come later in the file */
{
  return x + y;
}

This is exactly the declaration/definition distinction from Module 6, applied to functions: a function can be declared (via a prototype, often pulled in from a header file) in as many places as needed, but defined exactly once. Prototypes are what let one .c file call a function that's actually defined in a different .c file — the caller only needs to know the function's signature at compile time; the linker resolves the actual call to the real definition afterward.

If a function's return type isn't declared, older C compilers assume int; modern compilers require you to state it explicitly, including void for a function that returns nothing: 

void printBanner(void) {
  printf("=== Welcome ===\n");
  return;          /* bare return is fine — no value to give back */
}

double atof(char s[]) {   /* non-int return types must always be declared */
  double val;
  ...
  return val;
}
A function whose non-int return type isn't declared before use (e.g. calling atof in a file that never saw its prototype) is a real bug: the compiler falls back to assuming int, silently reinterprets the returned bits as the wrong type, and produces garbage results with no error at compile time on older compilers. Modern compilers reject this outright — another good reason to always #include the header that declares a library function before calling it.

5. Recursion and the stack-frame intuition

A recursive function calls itself, typically working on a smaller version of the same problem each time, until it reaches a base case simple enough to answer directly without recursing further. 

int factorial(int n)
{
  if (n <= 1)
    return 1;                       /* base case */
  return n * factorial(n - 1);      /* recursive case */
}
/* factorial(4) = 4 * factorial(3)
                = 4 * (3 * factorial(2))
                = 4 * (3 * (2 * factorial(1)))
                = 4 * (3 * (2 * 1))
                = 24 */

Every recursive call is a completely fresh function call, with its own independent copy of every local variable and parameter — the n inside factorial(3) is a different n from the one inside factorial(4), even though they share the same name in the source code. This is only possible because each call gets its own private storage for its locals and parameters, layered on top of the call that made it. That private storage region is called a stack frame, and the collection of frames, one per currently-active call, is the call stack.

Conceptually, calling factorial(4) pushes a new frame for that call; it calls factorial(3), which pushes another frame on top; and so on, until factorial(1) hits the base case and returns without recursing further. As each call returns, its frame is popped off, and control resumes in the frame just below it, which still has its own n and its own pending multiplication waiting to complete. A chain of recursive calls with no base case, or a base case that's never reached, keeps pushing frames indefinitely — this is what a stack overflow actually is: the call stack running out of the memory reserved for it.

This is intentionally just the conceptual picture for now — what a stack frame actually contains, exactly how it's laid out in memory, and how the CPU manages pushing and popping frames at the assembly level is covered in depth starting in Module 15 and beyond, once you're reading x86-64 assembly directly. The takeaway to carry forward from this module is simpler: recursion works because each call's locals are independent, and that independence has a real memory cost, one frame per active call.
In factorial(4) calling factorial(3) calling factorial(2), why don't the three calls' local variables named n interfere with each other?
Every call to a function — recursive or not — gets a fresh stack frame holding its own parameters and local variables. The three calls all happen to use the source-level name n, but they refer to three physically separate pieces of storage, one per frame, which is exactly why factorial(4)'s n can still be waiting at 4 while factorial(2)'s n is independently 2.
