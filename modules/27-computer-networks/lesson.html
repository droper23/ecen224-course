Computer Networks

So far every program you've written has lived on one machine. Network programming breaks that boundary: two processes, potentially on opposite sides of the planet, exchanging bytes over a connection as if they were talking directly to each other. This module builds the conceptual model — addresses, ports, protocols, and connections — that the next module's socket code is built on top of.

CS:APP reference: Chapter 11.1–11.3.  |  Tested on: This material comes after Game 2 and is tested only on the comprehensive Final.

Learning objectives

  • Describe the client-server model and identify the client and server roles in an interaction
  • Explain what an IP address and a port identify, and how together they form a socket address
  • Describe the layered network stack conceptually (application, transport, network, link)
  • Contrast TCP and UDP at a conceptual level: reliable ordered streams vs. fire-and-forget datagrams
  • Explain what DNS does and why it exists

1. The client-server model

Nearly every network application is built around the same shape: a server process that manages some resource, and one or more client processes that want something done with it. The pattern repeats regardless of what the resource actually is (a file, a web page, a database row):

  1. The client sends a request to the server.
  2. The server, which has been waiting for exactly this, handles the request.
  3. The server sends a response back.
  4. The client handles the response.

Client and server are processes, not machines — they might be running on the same host or on opposite sides of the world; the model doesn't care. It's helpful to picture a vending machine: the machine (server) sits idle managing its resource (snacks) until a customer (client) makes a request (inserts money, presses a button), at which point it acts and dispenses a response.

2. A network, at a glance

A computer network connects many hosts together through routers, and the Internet itself is just an ad hoc interconnection of many smaller networks with no fixed topology and wildly different link speeds. Data is broken into packets and sent hopping from router to router until it reaches its destination; different packets between the same two hosts may even take different physical routes to get there. Since the individual networks along the way can be physically and technically incompatible with each other, every host and router runs common protocol software — an agreed-upon set of rules for how to cooperate when moving data from network to network — that smooths over those differences and makes the whole patchwork look, to an application, like one uniform network.

A protocol does two jobs: it defines a uniform naming scheme (so every host can be addressed the same way regardless of what physical network it's actually on), and it defines a standard packet format for actually moving data — a header (metadata like size and source/destination address) plus a payload (the actual data being sent). TCP/IP is the protocol suite the Internet, and this course, is built on.

3. Thinking in layers

Protocol software is organized in layers, each one responsible for a different slice of the problem and relying on the layer below it to move bytes reliably enough for its own job. You don't need the full seven-layer OSI model for this course — a simplified four-layer picture is enough:

LayerJobExamples
ApplicationWhat your program actually wants to sayHTTP, SSH, your own socket code
TransportGetting a message between two processes (ports)TCP, UDP
NetworkGetting a packet between two hosts, across routersIP
LinkGetting a frame across one physical hop (one LAN/WAN link)Ethernet, WiFi

Each layer wraps the layer above it's data in its own header as the data heads out (this is called encapsulation) and strips its own header back off as the data arrives at the matching layer on the other end. A router in the middle only needs to look far enough into a packet to make a forwarding decision at the network layer — it doesn't need to understand the application data being carried at all. This layering is exactly what lets you write socket code without caring whether the other machine is connected over Ethernet, WiFi, or something else entirely; the layers below transport hide that from you completely.

4. IP addresses and domain names

Every host on the Internet is identified by at least one IP address — traditionally a 32-bit number, conventionally written in dotted-decimal notation as four bytes separated by periods, e.g. 128.187.16.184. Since 32-bit numbers are hard for humans to remember or type reliably, the Internet maintains a separate, human-friendly naming layer: domain names like byu.edu, organized hierarchically (a domain name is a sequence of words separated by periods, and each suffix is a broader sub-domain the name belongs to).

DNS (Domain Name System) is the piece that ties these two together: a huge, distributed, worldwide database mapping domain names to IP addresses. Conceptually, you can think of it as a giant lookup table of host entries — your machine asks "what IP address does byu.edu correspond to right now?" and gets an answer back, before it can actually open a connection to that host. This lookup step is exactly why a DNS outage can make "the internet is down" even though every server involved is actually running fine — the names simply can't be resolved to addresses.

5. Ports, sockets, and connections

An IP address identifies a host, but a host can be running many network programs at once (a web server, an SSH server, a mail server, all on the same machine). A port is a 16-bit number that identifies a specific process on that host. Some ports are well-known, permanently reserved for a specific kind of service by convention (port 22 for SSH, port 80 for HTTP, port 443 for HTTPS); others are ephemeral, assigned automatically and temporarily by the OS to a client process when it initiates a connection.

A socket address is the pair IP address : port, uniquely identifying one endpoint. A connection between a client and a server is uniquely identified by the pair of socket addresses at both ends — the "socket pair" (client_addr:client_port, server_addr:server_port). This is exactly how a server can accept requests from many different clients on the same well-known port at once: each client connects from its own IP address and its own ephemeral port, so every connection's socket pair is unique even though the server-side half is identical for all of them.

A single web server, listening on port 80, is handling requests from two different browsers on two different laptops at the same time. How does the server (and the OS) keep the two connections apart?
A connection isn't identified by the server's socket address alone — it's identified by the (client IP:port, server IP:port) pair together. Since each client has a distinct IP address and its own ephemeral port, the two connections have distinct socket pairs even though they share the same server-side endpoint.

6. TCP vs. UDP

Both live at the transport layer, both use ports to route data to the right process, and both ride on top of IP — but they make very different promises to the application above them.

TCPUDP
ModelConnection-oriented byte streamConnectionless datagrams
ReliabilityGuaranteed delivery, retransmits lost dataNo guarantee — a datagram can simply vanish
OrderingBytes arrive in the order they were sentDatagrams can arrive out of order, or not at all
OverheadHigher — handshakes, acknowledgments, retransmissionLower — send and forget
Typical useWeb (HTTP), SSH, email — anything that needs correctnessVideo/voice streaming, DNS lookups — anything that prefers speed and can tolerate loss

A TCP connection behaves like the "connections" described above: point-to-point (one specific client, one specific server), full-duplex (both sides can send at the same time), and reliable (a stream of bytes sent by one side is guaranteed to eventually arrive at the other side, in the exact order it was sent) — the underlying protocol software handles retransmitting lost packets and reordering out-of-order ones so the application never has to think about it. UDP, by contrast, just fires individual, independent datagrams at a destination with no setup and no guarantee any particular one arrives, arrives once, or arrives in order. That sounds strictly worse, but for something like a live video call, a datagram that arrives late is often useless anyway — UDP's lack of retransmission overhead can matter more than occasional loss. The socket programming you'll do next module builds directly on top of this choice: you pick TCP when correctness matters more than speed, and UDP when speed matters more than perfect delivery.

Why might a live video call use UDP instead of TCP, even though UDP offers no delivery guarantees?
TCP's reliability comes from retransmitting lost data and holding later data until earlier data arrives in order — both of which add latency. For real-time media, a dropped or late frame is often not worth waiting on, so UDP's lower overhead is the better trade, even though it can lose data silently.
