Integer Arithmetic

Fixed-width integers can't hold every possible result of adding or multiplying two numbers together. This module covers exactly what happens when they don't fit — wraparound for unsigned, undefined behavior for signed — plus the shift-based tricks compilers use to turn multiplication and division by powers of two into fast instructions.

CS:APP reference: Chapter 2.3.  |  Due: HW3 — Integer Arithmetic (closed Sep 21).  |  Tested on: Game 1 and the Final.

Learning objectives

  • Predict the result of unsigned addition overflow (wraparound) for a given word size
  • Predict two's-complement signed addition overflow, including positive and negative overflow
  • Explain why signed overflow is undefined behavior in C, despite wrapping predictably on real two's-complement hardware
  • Convert multiplication and division by powers of 2 into shift operations, and reason about rounding direction

1. Unsigned addition: wraparound

A w-bit register can only hold w bits. If you add two w-bit unsigned numbers, the mathematically correct ("true") sum can need up to w+1 bits to represent — for example, with 4 bits, 15 + 15 = 30, but the maximum 4-bit value is only 15. The hardware doesn't grow an extra bit; it simply drops any carry out of the top bit and keeps only the low w bits. That's unsigned overflow, and the result is exactly the true sum modulo 2w: 

4-bit unsigned: range is 0000 to 1111 (0 to 15)
15 +  1 = 1111 + 0001 = 1 0000  -> drop carry -> 0000  (0, not 16)
15 + 15 = 1111 + 1111 = 1 1110  -> drop carry -> 1110  (14, not 30)

Overflow only ever wraps around at most once for a single addition, since adding two w-bit numbers can never produce a true sum ≥ 2w+1. Unsigned overflow is not a bug or an error condition in C — it's fully defined, predictable modular arithmetic, and some algorithms (hash functions, checksums, cryptography) rely on it deliberately.

2. Two's-complement (signed) addition: overflow both directions

Signed addition works the same way at the bit level — compute the true sum (which may need w+1 bits), then keep only the low w bits and reinterpret them as two's complement. But because the representable signed range is [-2w-1, 2w-1-1], overflow can now happen in either direction:

  • Positive overflow: adding two positive numbers produces a true sum ≥ 2w-1 that doesn't fit, so the truncated result wraps around into the negative range.
  • Negative overflow: adding two negative numbers produces a true sum < -2w-1, so the truncated result wraps around into the positive range.

The pattern to recognize: Pos + Pos → Neg means positive overflow. Neg + Neg → Pos means negative overflow. Two operands with different signs can never overflow — their true sum is already guaranteed to fit within the representable range.

The important hardware fact underlying all of this: unsigned addition and signed (two's-complement) addition have exactly the same bit-level behavior. The CPU uses one adder circuit regardless of how you declared your variables; only the interpretation of the result bits differs: 

int s, t, u, v;
s = (int) ((unsigned) u + (unsigned) v);
t = u + v;
if (s == t) printf("equal");  // always true
In 4-bit two's complement, you add 5 + 5 and get -6. What happened?
Two positive operands whose true sum exceeds the representable maximum wrap around into negative values — that's positive overflow by definition, regardless of the sign of the wrapped result. Neg + Neg → Pos is negative overflow; Pos + Pos → Neg is positive overflow.

3. Signed overflow is undefined behavior in C

Here's the subtlety that trips people up: on virtually every real two's-complement CPU, signed overflow wraps around exactly as shown above — it's completely deterministic at the hardware level. But the C language standard does not guarantee two's-complement representation, and it declares that signed integer overflow is undefined behavior (UB). That's not just a technicality: because it's UB, an optimizing compiler is legally allowed to assume signed overflow never happens, and it can use that assumption to eliminate or reorder checks that depend on it. A classic example: a compiler may optimize away a check like if (x + 1 < x) (intended to detect overflow) entirely, because it's allowed to assume x + 1 < x is simply always false for a signed x under the no-overflow assumption — even though on real hardware that comparison could actually be true when x is INT_MAX.

Takeaway: unsigned overflow in C is fully defined (modular wraparound). Signed overflow is undefined behavior — the hardware will wrap predictably, but the compiler is not required to preserve that behavior, so code that silently relies on signed wraparound is a real, exam-relevant bug, not just bad style.

4. Multiplication and the shift trick

Multiplying two w-bit values can require up to 2w bits to represent the full, exact product. C doesn't grow the result type automatically: it truncates the 2w-bit product down to w bits, keeping only the low-order bits — the same truncation behavior from the previous module. This means integer multiplication overflows silently and easily: 

int x = 50000 * 50000;  // exact product is 2,500,000,000
// INT_MAX is only 2,147,483,647 -- this overflows a 32-bit int

Multiplying or dividing by a power of 2 is special, because it corresponds exactly to shifting the binary representation: y = x * 8; is equivalent to y = x << 3;, and this is one of the most common optimizations a compiler applies automatically — a shift instruction is dramatically cheaper than a general multiply on most hardware, so compilers rewrite multiplications by constant powers of 2 into shifts whenever they can prove it's safe.

5. Division by a power of 2, and rounding direction

Division by a power of 2 can similarly be implemented with a shift — but only carefully, because C integer division rounds toward zero, while a plain arithmetic right shift rounds toward negative infinity. Those agree for positive numbers but disagree for negative ones. For a non-negative x, y = x / 2; and y = x >> 1; (logical or arithmetic; sign bit is 0 either way) give identical results. For a negative x, a naive arithmetic right shift rounds down (further negative) rather than toward zero, so compilers generating code for signed division by a power of 2 must insert an extra bias-and-correct step before shifting to get C's toward-zero rounding exactly right — they can't just emit a bare shift instruction the way they can for multiplication. 

int x = -7;
x / 2;    // -3  (C rounds toward zero)
x >> 1;   // -4  (arithmetic shift rounds toward negative infinity)
// -7 / 2 and -7 >> 1 are NOT the same value
Why can't a compiler always replace signed integer division by a power of 2 with a plain arithmetic right shift?
For positive numbers, shifting right and dividing by a power of 2 agree. For negative numbers they diverge: -7/2 is -3 in C (rounds toward zero) but -7 >> 1 is -4 (rounds toward negative infinity), so the compiler must add a correction step to use a shift for signed division.

6. Practical takeaway

Integer overflow is one of the most common real-world sources of bugs and security vulnerabilities — from silently wrong financial calculations to buffer-size computations that wrap around to a small or negative number and defeat a bounds check. There's no way to avoid the possibility of overflow entirely; the practical defense is choosing a data type with enough range for your problem, being explicit about signedness, and testing boundary values (near TMin/TMax/UMax) rather than assuming "it'll never get that big."
