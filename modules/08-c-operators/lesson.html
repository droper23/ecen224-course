C Operators

C packs a lot of behavior into a small set of symbols. This module covers arithmetic, relational, logical, and bitwise operators; the classic = vs. == typo; pre- vs. post-increment; short-circuit evaluation; and the precedence table you'll need to read C expressions correctly instead of guessing.

Due: HW7 — C Operators (closed Sep 30).  |  Tested on: Game 1 and the Final.

Learning objectives

  • Apply C's arithmetic, relational, logical, and bitwise operators correctly, including integer division and modulo
  • Distinguish bitwise operators (& | ^ ~ << >>) from logical operators (&& || !) and explain why confusing them compiles but misbehaves
  • Predict the result of pre- vs. post-increment/decrement in an expression
  • Evaluate a ternary conditional expression and explain why it's an expression, not a statement
  • Use C's operator precedence and associativity table to read an unparenthesized expression correctly
  • Explain short-circuit evaluation and when it matters for correctness, not just efficiency

1. Arithmetic operators

C's binary arithmetic operators are + - * / %; unary + and - also exist and bind more tightly than their binary counterparts. Two things about / and % trip people up constantly:

  • Integer division truncates. 5 / 3 is 1, not 1.666... — when both operands are integer types, the fractional part is simply discarded (truncated toward zero), not rounded.
  • % only works on integers. It gives the remainder after integer division (5 % 3 is 2) and cannot be applied to float or double operands at all — that's a compile error, not a silent truncation.

Mixed-type arithmetic triggers implicit type conversion: when a binary operator's operands have different types, the "lower" type is promoted to the "higher" one before the operation, following roughly short → int → long → float → double (and unsigned outranks signed of the same size). So: 

int num1 = 5;
double num2 = 1.5;
int num3 = num1 / num2;
/* num1 is promoted to double: 5.0 / 1.5 = 3.33333...
   the double result is then truncated back to int for the assignment: num3 = 3 */

The same promote-then-truncate pattern happens across an assignment even without a division: int x = 1; x = x + 4.3; computes 1 promoted to 1.0, adds to get 5.3, then truncates back to int for the assignment, giving x = 5. You can also force a conversion explicitly with a cast: (double)ticks / TICKS_PER_SECOND converts ticks to double before the division happens, rather than letting truncation happen first.

What does 7 / 2 + 7 % 2 evaluate to in C, where both operands are int?
Integer division truncates: 7 / 2 = 3. The modulo gives the remainder: 7 % 2 = 1. 3 + 1 = 4. Both operators share the same (higher) precedence as multiplication and are evaluated left to right, but here they're in separate additive terms so each is computed independently first.

2. Relational and logical operators

The relational operators > >= < <= and equality operators == != all return 1 (true) or 0 (false). The logical operators && (AND), || (OR), and unary ! (NOT) treat any nonzero operand as true and zero as false, and themselves return 1 or 0. 

if (!valid) ...       /* same as: if (valid == 0) ... */
The single most infamous C bug: = is assignment; == is comparison. Because an assignment expression itself evaluates to the assigned value, this compiles cleanly and does something completely different from what you meant: 
if (x == 1) statement;   /* correct: runs statement only if x is 1 */
if (x = 1)  statement;   /* WRONG: assigns 1 to x, which is truthy, so
                             statement ALWAYS runs, and x is now 1 */
Some compilers warn about this with -Wall; get in the habit of reading your warnings, and consider writing comparisons as if (1 == x) so that an accidental = becomes an assignment to a constant, which most compilers flag as an outright error.

A second classic mistake is chaining comparisons the way you might in math class: 

if ('a' <= x <= 'z') statement;               /* WRONG */
if (('a' <= x) && (x <= 'z')) statement;       /* correct */

'a' <= x <= 'z' does not mean "x is between 'a' and 'z'." Relational operators associate left to right, so this parses as ('a' <= x) <= 'z': first computes a 0/1 result from 'a' <= x, then compares that 0 or 1 against 'z' — which is almost always true, regardless of what x actually is. Each comparison must be written out and joined with && explicitly.

3. Short-circuit evaluation

&& and || evaluate their operands left to right and stop ("short-circuit") as soon as the overall result is already determined:

  • a && b — if a is false, the whole expression is already false, so b is never evaluated.
  • a || b — if a is true, the whole expression is already true, so b is never evaluated.

This is not just an efficiency trick — it's frequently load-bearing for correctness, especially when the right-hand side has a side effect or would be unsafe to evaluate on its own: 

if (i < lim - 1 && (c = getchar()) != '\n') ...
/* getchar() is only called if i < lim - 1 is still true */

x || ++y;   /* ++y only runs if x is false (0) */

A very common real pattern is guarding a pointer dereference with a null check on its left: if (p != NULL && p->x > 0) relies on short-circuiting to guarantee p->x is never evaluated when p is NULL (you'll see this again once pointers are formally introduced in Module 10).

Given int y = 0; and int x = 5;, what does x || ++y; leave y as?
x is 5, which is truthy, so the || operator already knows the overall result is true without looking at the right-hand operand. Short-circuit evaluation means ++y is never executed at all, so y stays 0. This is well-defined behavior, not undefined behavior — || and && are exactly the operators the language guarantees an evaluation order for.

4. Increment and decrement: prefix vs. postfix

++ adds 1 to its operand; -- subtracts 1. Both can be used as a prefix (++n) or postfix (n++) operator, and the difference is entirely about when the old vs. new value is used in the surrounding expression — in both cases, n itself ends up incremented either way.

FormValue used in the expressionEffect on the variable
++n (prefix)the new value, after incrementingincremented
n++ (postfix)the old value, before incrementingincremented
int n = 5;
int x = n++;   /* x = 5 (old value used), n is now 6 */

int m = 5;
int y = ++m;   /* m becomes 6 first, y = 6 (new value used) */

This shows up constantly in loop and array idioms — e.g. copying a string one character at a time with a compact postfix pattern: 

while ((s[i++] = t[j++])) ;   /* copies t into s, including the '\0' */

Each iteration reads t[j], writes it into s[i], and only then advances both i and j for next time — because postfix ++ yields the pre-increment value for use in the surrounding expression, while still bumping the variable as a side effect.

Watch for unsequenced side effects. C does not guarantee the order in which a function's arguments are evaluated, and an expression that reads and writes the same variable without a sequence point between the two is undefined behavior. Both a[i] = i++; and printf("%d %d\n", ++n, power(2, n)); are classic examples the language explicitly leaves unspecified or undefined — don't write code that depends on one particular order here, even if your specific compiler happens to do what you expect today.

5. Bitwise operators

Bitwise operators only apply to integral operands (char, short, int, long) and operate on individual bits, not on the value's truth/falseness the way logical operators do:

OperatorMeaning
&bitwise AND
|bitwise OR
^bitwise XOR
~bitwise NOT (complement, unary)
<<left shift
>>right shift
n = n & ~0x07;   /* clear (zero out) the lowest 3 bits */
n = n | 0x07;    /* set the lowest 3 bits to 1 */
n = n << 2;      /* shift bits 2 positions left */
n = n >> x;      /* shift right; fills with 0s if n is unsigned */
Do not confuse &/| with &&/||. Both pairs compile in almost any context involving integers, which is exactly what makes the mistake dangerous — there's no compiler error to catch you. & is a bitwise AND of every bit position; && is a logical AND that only cares whether each side is zero or nonzero as a whole. 4 & 1 is 0 (binary 100 AND 001 shares no set bits) even though both 4 and 1 are individually truthy, so 4 && 1 is 1. Using & where you meant && is a classic silent logic bug.

6. Assignment operators and the ternary operator

Most binary operators have a corresponding compound assignment form, op=, where op is one of + - * / % << >> & ^ |: 

i += 2;      /* same as: i = i + 2; */
x *= y + 1;  /* same as: x = x * (y + 1); */

In general, expr1 op= expr2 is equivalent to expr1 = (expr1) op (expr2), except that expr1 is only evaluated once — which matters if the left side has a side effect, like arr[i++] += 3;.

The ternary (conditional) operator ?: is C's only three-operand operator, and it's an expression, not a statement — it produces a value that can be used anywhere an expression is expected, including nested inside another expression: 

expr1 ? expr2 : expr3
/* expr1 is evaluated first; if nonzero, the result is expr2 (expr3 is
   never evaluated); if zero, the result is expr3 (expr2 is never
   evaluated) */

z = (a > b) ? a : b;   /* z = max(a, b) */
Why is z = (a > b) ? a : b; meaningfully different from writing it as an if/else that assigns z in each branch?
An if/else is a statement — it controls flow but produces no value of its own. expr1 ? expr2 : expr3 is an expression that evaluates to expr2 or expr3, so it can be used anywhere a value is expected: printf("%d\n", (a > b) ? a : b); embeds it directly as a function argument, which a bare if/else cannot do.

7. Precedence and associativity

Precedence determines which operator in an unparenthesized expression binds first when different operator types are mixed; associativity determines the order among operators of the same precedence (left-to-right, or right-to-left). A partial table, from highest precedence to lowest:

OperatorsAssociativity
() [] -> .left to right
! ~ ++ -- + - * & (type) sizeof (unary)right to left
* / %left to right
+ -left to right
<< >>left to right
< <= > >=left to right
== !=left to right
&left to right
^left to right
|left to right
&&left to right
||left to right
?:right to left
= += -= ...right to left

Two rows worth memorizing specifically, because they're common exam bait:

  • Unary &, +, -, and * bind tighter than their binary forms, and much tighter than ==. So if (x & MASK == 0) does not mean "mask x, then compare to zero" the way it visually reads — == has higher precedence than bitwise &, so this parses as x & (MASK == 0), comparing MASK to 0 first and then bitwise-ANDing x with that 0-or-1 result. Always parenthesize: if ((x & MASK) == 0).
  • Assignment is right-to-left associative, which is what makes chained assignment work: a = b = c = 5; evaluates as a = (b = (c = 5)), so all three end up 5.

C also deliberately leaves some things unspecified even when precedence and associativity are clear: the order in which a single operator's operands are evaluated (except for && || ?: ,) is not guaranteed, and neither is the order function arguments are evaluated in. x = f() + g(); might call f() or g() first — don't write code whose correctness depends on which.

How does if (x & MASK == 0) actually get parsed, given that == has higher precedence than bitwise &?
== binds tighter than &, so MASK == 0 is evaluated first, producing 0 or 1, and then x is bitwise-ANDed with that single bit — almost never what was intended. This is a real, frequently-cited C gotcha, which is exactly why explicit parentheses around bitwise/comparison mixes are considered good style.
