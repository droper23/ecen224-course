Loops & Switches

x86-64 has no for instruction and no switch instruction — everything you write with those keywords gets reduced to the compare-and-jump primitives from the last module. This module is about recognizing the patterns the compiler builds from those primitives, so you can read disassembled loops and jump tables and reconstruct the C that produced them.

CS:APP reference: Chapter 3.6.  |  Tested on: Game 2 and the Final.

Learning objectives

  • State the do-while → goto translation and use it as the base case for every other loop form
  • Recognize the jump-to-middle and guarded-do patterns gcc uses to compile while and for loops
  • Reconstruct a loop's C source structure (test, body, update) from disassembled x86-64
  • Explain how a jump table implements a switch in O(1) time, and read the indirect-jump syntax that dispatches through one
  • Explain why the compiler abandons the jump table for a sparse switch and falls back to a compare tree

1. There is no loop instruction

do/while, while, and for are all C-level conveniences. None of them has a dedicated machine instruction; the compiler lowers all three down to the same raw material — conditional tests and jumps — using a handful of standard translation patterns. Once you know the patterns, reading a compiled loop is a matter of pattern-matching, not puzzling out each jump from scratch.

2. do-while: the base case

do/while is the simplest loop to translate, because its test already comes after the body — exactly where a backward conditional jump wants to live: 

do
  Body
while (Test);
// equivalent goto form
loop:
  Body
  if (Test)
    goto loop;

A worked example — pcount counts the number of 1-bits in x ("popcount") by repeatedly checking the low bit and shifting: 

long pcount_do(unsigned long x) {
  long result = 0;
  do {
    result += x & 0x1;
    x >>= 1;
  } while (x);
  return result;
}
movl    $0, %eax      # result = 0
.L2:                     # loop:
  movq  %rdi, %rdx
  andq  $1, %rdx        #   t = x & 0x1
  addq  %rdx, %rax      #   result += t
  shrq    %rdi           #   x >>= 1
  jne     .L2             #   if (x) goto loop
ret

shrq %rdi (shift right, no explicit count means shift by 1) sets ZF exactly when the result is 0, so jne .L2 after it is testing "is x, after the shift, still nonzero" — precisely the while (x) condition, with no separate testq needed.

3. while: two compiler strategies

A while loop's test comes before the body, which doesn't fit the do-while pattern directly — the loop might need to execute zero times. Compilers handle this with one of two rewrites, both of which reduce back to do-while form:

StrategyIdeaWhen you'll see it
Jump-to-middleJump straight to the test on entry; body sits above the testLower optimization levels (e.g. -Og)
Guarded-doGuard the loop with an upfront if (!Test) goto done;, then it's a plain do-whileHigher optimization levels
while (Test)
  Body
// jump-to-middle
goto test;
loop:
  Body
test:
  if (Test)
    goto loop;
done:
// guarded-do
if (!Test)
  goto done;
loop:
  Body
  if (Test)
    goto loop;
done:

The same pcount loop, written as while, compiles (jump-to-middle) to:

movl    $0, %eax      # result = 0
jmp     .L3              # goto test
.L2:                     # loop:
  movq  %rdi, %rdx
  andq  $1, %rdx        #   t = x & 0x1
  addq  %rdx, %rax      #   result += t
  shrq    %rdi           #   x >>= 1
.L3:                     # test:
jne     .L2              #   if (x) goto loop
rep; ret

The overall shape is identical to the do-while version except for one extra unconditional jmp at the top — the giveaway that this loop's test was originally written before the body. (rep; ret is a historical no-op prefix some compilers add before a ret that's the target of a conditional jump, to avoid a branch-predictor quirk on certain AMD chips; it doesn't change program behavior.)

Reading tip: to find a loop in disassembly, look for a backward jump — a jX whose target address is earlier in the code than the jump itself. That target is the top of the loop body. Then check whether there's an unconditional jmp immediately before that target: if so, you're looking at jump-to-middle and the real test is down at the bottom, right before the backward jump.
You're reading disassembly and see an unconditional jmp to a label right after loading the loop's initial values, with the loop body sitting between that label's target and a conditional backward jump at the bottom. What loop-compilation pattern is this?
A plain do-while never needs the initial unconditional jmp — its test is naturally at the bottom already. The leading jmp to a test at the bottom is exactly the jump-to-middle rewrite of a while/for loop, which needs to reach the test before running the body the first time.

4. for loops reduce to while loops

for is just syntactic sugar over while, and the compiler treats it that way — first rewriting for into an equivalent while, then applying the while-loop translation from the previous section: 

for (Init; Test; Update)
  Body
// equivalent while form
Init;
while (Test) {
  Body
  Update;
}

Rewriting pcount as a for loop over each bit position:

long pcount_for(unsigned long x) {
  long result = 0;
  for (size_t i = 0; i < WSIZE; i++) {
    unsigned bit = (x >> i) & 0x1;
    result += bit;
  }
  return result;
}
movl    $0, %eax        # result = 0
movl    $0, %edx        # i = 0
jmp     .L3                # goto test
.L2:                       # loop:
  shrq  %rdi              #   x >>= 1   (shifting x instead of re-shifting by i each time)
  andq  $1, %rdi          #   t = x & 0x1
  addq  %rdi, %rax        #   result += t
  incq    %rdx              #   i++
.L3:                       # test:
  cmpq  $WSIZE, %rdx      #   i : WSIZE
jl      .L2                #   if (i < WSIZE) goto loop
rep; ret

At higher optimization the compiler often uses the guarded-do form instead, and can even elide the initial test entirely when it can prove the loop always runs at least once — for example, when i starts at the constant 0 and WSIZE is a positive constant, the compiler already knows 0 < WSIZE holds, so it skips straight into the loop body without checking. That optimization disappears the moment the bound comes from an unknown runtime parameter instead of a constant.

5. Switch statements: jump tables

An if/else if chain checking n cases costs up to n sequential compares. When a switch's case labels are small integers packed close together, the compiler can instead build a jump table: an array of code addresses, indexed directly by the switch expression, giving O(1) dispatch to any case regardless of how many there are. 

switch (x) {
  case val_0: Block0; break;
  case val_1: Block1; break;
  /* ... */
  case val_n1: Blockn1; break;
}
// extended-C idea of what the compiler builds
goto *jtab[x];

Here's a switch with multiple case labels sharing code (5 and 6), a fall-through case (2 falls into 3), and a gap (4 is missing, handled by default): 

long switch_eg(long x, long y, long z) {
  long w = 1;
  switch (x) {
    case 1:
      w = y * z;
      break;
    case 2:
      w = y / z;
      /* fall through */
    case 3:
      w += z;
      break;
    case 5:
    case 6:
      w -= z;
      break;
    default:
      w = 2;
  }
  return w;
}
switch_eg:
  movq    %rdx, %rcx
  cmpq    $6, %rdi       # x : 6
  ja      .L8              # if x > 6 (unsigned!), go straight to default
  jmp     *.L4(,%rdi,8)   # indirect jump: fetch target from L4[x], go there

  .section .rodata
  .align 8
.L4:                        # the jump table itself, one 8-byte address per case
  .quad .L8   # x = 0 -> default
  .quad .L3   # x = 1
  .quad .L5   # x = 2
  .quad .L9   # x = 3
  .quad .L8   # x = 4 -> default (missing case)
  .quad .L7   # x = 5
  .quad .L7   # x = 6

.L3:                        # case 1
  movq    %rsi, %rax
  imulq   %rdx, %rax       # y*z
  ret
.L5:                        # case 2
  movq    %rsi, %rax
  cqto
  idivq   %rcx              # y/z
  jmp     .L6                #   then fall into case 3's code
.L9:                        # case 3 (entered directly, or via fallthrough from case 2)
  movl    $1, %eax
.L6:                        # merge point for the fallthrough
  addq    %rcx, %rax       # w += z
  ret
.L7:                        # case 5, 6
  movl    $1, %eax
  subq    %rdx, %rax       # w -= z
  ret
.L8:                        # default
  movl    $2, %eax
  ret

Two things to notice: first, ja .L8 is an unsigned "above" comparison against the constant 6, which handles negative x and out-of-range x in one instruction — a negative number, interpreted as unsigned, is huge, so it's automatically "above" 6 and falls to default. Second, the indirect jump jmp *.L4(,%rdi,8) uses exactly the addressing-mode syntax from Module 15: no base register, index %rdi, scale 8 (because each table entry is an 8-byte address), displacement .L4 (the table's start). It fetches the address stored at .L4 + 8·x and jumps there.

In the switch_eg jump table, why does the compiler compare with cmpq $6, %rdi; ja .L8 before the indirect jump, instead of jumping through the table unconditionally?
A jump table's array only has as many slots as the range it was built for — here, x = 0 through 6. Any x outside that range (including negative x, which reads as huge when compared unsigned by ja) would index outside the table and jump to garbage, so the compiler always range-checks before the indirect jump and sends out-of-range values straight to the default case.

6. When the compiler skips the jump table

A jump table trades space for speed: it needs one entry for every integer in the covered range, whether or not that value is an actual case label. That's a great trade when cases are dense (0–6, no huge gaps). It's a terrible trade when they're sparse: 

/* Return x/111 if x is a multiple of 111 and <= 999, else -1 */
int div111(int x) {
  switch (x) {
    case 0:   return 0;
    case 111: return 1;
    case 222: return 2;
    /* ... */
    case 999: return 9;
    default:  return -1;
  }
}

A jump table covering 0–999 to serve 10 real cases would need 1000 table entries — almost entirely pointing at default. The compiler recognizes this is a bad trade and instead falls back to a binary search over the case values: a balanced tree of cmp/je/jg comparisons that narrows the range by half at each step. 

cmpl    $444, %eax
je      L8
jg      L16
cmpl    $111, %eax
je      L5
jg      L17
testl   %eax, %eax
je      L4
jmp     L14              # no match -> default
...

Instead of the O(1) dispatch a dense jump table gives you, this costs O(log n) comparisons — still far better than a linear O(n) chain checking every case in listed order, and without wasting memory on nearly a thousand unused table slots.

Why doesn't gcc build a jump table for the div111 switch (cases 0, 111, 222, ..., 999)?
Jump tables are indexed by the raw case value, so their size is determined by the range of values, not the number of cases. A sparse switch like this one would need a huge, almost entirely-unused table; the compiler instead emits a binary-search-style tree of compares, which costs O(log n) time but no wasted memory.
