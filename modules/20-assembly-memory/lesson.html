Memory Management

Every process you run gets carved into a handful of regions — stack, heap, static data, and executable code — each with its own lifetime and its own rules. Module 19 covered how the stack supports a single function call; this module zooms out to where that stack actually lives in the address space, and reconnects the pointers and addresses you learned as a C mental model (Module 10) to the concrete bytes assembly manipulates.

CS:APP reference: Chapter 3.10.  |  Tested on: Game 2 and the Final.

Learning objectives

  • Sketch the x86-64 Linux process memory layout and name what lives in each region
  • State which direction the stack and heap each grow, and why
  • Explain where local variables live during a function call and how they're addressed
  • Connect a C pointer to the actual memory address it holds at the assembly level

1. The process address space

When the OS loads a program, it doesn't just hand it one flat blob of memory — it lays out several distinct regions across the process's virtual address space, each serving a different kind of storage:

RegionContainsNotes
StackLocal variables, saved registers, return addressesRuntime stack, capped at 8 MB by default; grows and shrinks automatically as calls happen
HeapDynamically allocated memoryGrows as needed via malloc(), calloc(), C++ new, etc.
DataGlobal variables, static variables, string constantsStatically allocated — size fixed at compile/link time
Text / shared librariesThe executable machine instructionsRead-only, so a bug can't accidentally overwrite your own code

On x86-64 Linux, these regions sit at wildly different ends of a 64-bit address space (not drawn to scale, since the space between them is mostly unused): 

0x00007FFFFFFFFFFF  ----------------------  high addresses
                      Stack        (grows DOWN, toward lower addresses)
                      ...
                      Shared Libraries
                      Heap         (grows UP, toward higher addresses)
                      Data
                      Text
0x0000000000400000  ----------------------
0x0000000000000000                          low addresses

The two dynamically-sized regions — stack and heap — are deliberately placed far apart and told to grow toward each other: the stack grows down from a high address, the heap grows up from a low one. That maximizes how much either one can expand before the process runs out of address space, and it's also exactly why running off the end of a stack buffer reaches toward lower addresses (a detail that matters a great deal in Module 21).

Why are the stack and heap placed at opposite ends of the address space, growing toward each other?
Both the stack and heap can grow during a single run of the program in ways the compiler can't predict, so placing them at opposite extremes of the address space and having them grow inward gives each the most room possible.

2. Where local variables actually live

A C local variable isn't a name the machine understands — it's either a register or a specific offset within the current stack frame, chosen entirely by the compiler. Take: 

long call_incr() {
    long v1 = 15213;
    long v2 = incr(&v1, 3000);
    return v1 + v2;
}
call_incr:
  subq    $16, %rsp          # carve out 16 bytes of frame
  movq    $15213, 8(%rsp)    # v1 lives at 8(%rsp)
  movl    $3000, %esi        # 2nd arg to incr: 3000
  leaq    8(%rsp), %rdi      # 1st arg to incr: &v1
  call    incr
  addq    8(%rsp), %rax      # v1 + incr's return value (v2)
  addq    $16, %rsp          # release the frame
  ret

v1 never gets a register of its own here — the compiler decided it needed a real memory address (because call_incr takes its address with &v1 to pass to incr), so it's stored 8 bytes into the newly allocated frame, at 8(%rsp). v2, on the other hand, never gets a memory slot at all: the compiler keeps it in %rax the whole time, straight from incr's return value through to the final addq. This is the general rule: the compiler only spends stack space on a local variable when it has to — because it's too big for a register, its address is taken, or there simply aren't enough registers to go around.

3. Pointers are just addresses

Module 10 introduced the C mental model of a pointer: a variable whose value is the address of another variable. At the assembly level there is no separate "pointer type" at all — a pointer is simply a 64-bit quantity in a register or memory slot that happens to hold an address, and dereferencing it is simply using that value as the memory operand of an instruction. Look again at incr, called from the example above: 

long incr(long *p, long val) {
    long x = *p;
    long y = x + val;
    *p = y;
    return x;
}
incr:
  movq    (%rdi), %rax    # x = *p        (dereference: read from address in %rdi)
  addq    %rax, %rsi      # y = x + val
  movq    %rsi, (%rdi)    # *p = y        (dereference: write to address in %rdi)
  ret                      # return x, already sitting in %rax

%rdi holds p — not the value *p points at, but the address itself, computed back in call_incr by leaq 8(%rsp), %rdi. movq (%rdi), %rax is exactly C's *p: "go to the address held in %rdi and read 8 bytes from there." movq %rsi, (%rdi) is exactly *p = y: write through that same address. There's no magic — a C pointer dereference always compiles down to using a register's value as a memory address, rather than using the register's value directly.

This is also why leaq ("load effective address") and movq read so differently even though they can look similar on the page: leaq 8(%rsp), %rdi computes an address and stores that address in %rdi without touching memory at all (it's how &expr compiles), while movq 8(%rsp), %rdi would instead go read 8 bytes of actual memory content from that address. Confusing the two is one of the most common assembly-reading mistakes in this unit.

In AT&T syntax, what's the difference between leaq 8(%rsp), %rdi and movq 8(%rsp), %rdi?
leaq ("load effective address") never touches memory — it just computes an address, which is exactly how C's & operator compiles. movq with the same operand actually dereferences that address and loads its contents.
