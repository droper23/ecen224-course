Arithmetic, Jumps & Conditionals

Move instructions get data where it needs to be, but a real program has to compute and make decisions. This module covers the arithmetic instructions, the condition-code register that every comparison and branch reads from, and how a C if statement collapses into a compare and a conditional jump.

CS:APP reference: Chapter 3.6.  |  Tested on: Game 2 and the Final.

Learning objectives

  • Use the two-operand and one-operand arithmetic instructions, remembering AT&T's source/destination order
  • Explain what CF, ZF, SF, and OF each mean, and which instructions set them
  • Distinguish cmpq and testq from ordinary arithmetic instructions
  • Map the jX / setX condition suffixes to the condition-code combinations they test
  • Trace how a C if/ternary compiles to compare-and-branch, and when the compiler uses a conditional move instead

1. Arithmetic instructions

Two-operand arithmetic instructions follow the same Src, Dest order as movq — and the same warning applies even more here, since subtraction is not commutative:

InstructionComputation
addq Src,DestDest = Dest + Src
subq Src,DestDest = Dest - Src
imulq Src,DestDest = Dest * Src
salq Src,Dest (= shlq)Dest = Dest << Src
sarq Src,DestDest = Dest >> Src (arithmetic — sign-extending)
shrq Src,DestDest = Dest >> Src (logical — zero-filling)
xorq Src,DestDest = Dest ^ Src
andq Src,DestDest = Dest & Src
orq Src,DestDest = Dest \| Src

Note that Dest = Dest - Src, not the other way around — subq %rax, %rbx computes %rbx -= %rax. There's also no separate signed/unsigned version of these instructions: the same bits mean different things depending on how you interpret them, exactly like the two's-complement representation itself.

One-operand instructions modify their single operand in place:

InstructionComputation
incq DestDest = Dest + 1
decq DestDest = Dest - 1
negq DestDest = -Dest
notq DestDest = ~Dest

All of these exist in b/w/l/q sizes just like mov. A representative compiled function shows several of these instructions — including leaq pulling double duty as cheap arithmetic, from the previous module — working together: 

long arith(long x, long y, long z) {
  long t1 = x + y;
  long t2 = z + t1;
  long t3 = x + 4;
  long t4 = y * 48;
  long t5 = t3 + t4;
  long rval = t2 * t5;
  return rval;
}
arith:
  leaq    (%rdi,%rsi), %rax    # t1 = x+y
  addq    %rdx, %rax            # t2 = z+t1
  leaq    (%rsi,%rsi,2), %rdx  # 3*y
  salq    $4, %rdx               # t4 = 3y << 4 = 48y
  leaq    4(%rdi,%rdx), %rcx    # t5 = (x+4) + t4
  imulq   %rcx, %rax            # rval = t2 * t5
  ret

Notice t3 (x+4) never gets its own instruction — the compiler folds it directly into the displacement of the leaq that computes t5. This is normal: once you're reading compiled assembly, a one-to-one line count with the source is the exception, not the rule.

2. Condition codes: CF, ZF, SF, OF

Alongside the 16 general-purpose registers, the CPU keeps four single-bit condition code registers that record facts about the most recent arithmetic result:

FlagNameMeaning
CFCarry FlagSet on unsigned overflow (a carry out of the most significant bit)
ZFZero FlagSet if the result was exactly 0
SFSign FlagSet if the result was negative (as signed)
OFOverflow FlagSet on signed (two's-complement) overflow

These are set implicitly, as a side effect, by most arithmetic instructions. For addq Src, Dest computing t = a + b:

  • CF set if there's a carry out of the top bit (unsigned overflow)
  • ZF set if t == 0
  • SF set if t < 0 as a signed value
  • OF set if the signed addition overflowed: (a<0 == b<0) && (t<0 != a<0) — the two operands had the same sign but the result's sign flipped
leaq is the exception. Because leaq is address computation, not "real" arithmetic, it never touches the condition codes — even though it internally adds and multiplies numbers. If you see a comparison immediately after a leaq, it must be testing something computed earlier, not the leaq result.

3. Setting condition codes explicitly: cmp and test

Sometimes you want the condition codes without keeping the arithmetic result around at all — that's what comparisons compile to. 

cmpq Src2, Src1    # computes Src1 - Src2, sets flags, discards the result

cmpq b, a behaves like computing a - b, but the difference is thrown away — only CF/ZF/SF/OF are updated. ZF set means a == b; SF set (roughly) means a < b as signed; CF set means a < b as unsigned. 

testq Src2, Src1   # computes Src1 & Src2, sets flags, discards the result

testq b, a behaves like a & b, again without storing anything. One operand is frequently a bitmask, and the most common idiom is testq %rax, %rax — ANDing a register with itself, which sets ZF exactly when the register is zero. That's how compiled code implements if (x) and if (!x) checks and null-pointer tests without wasting an instruction on a comparison against an explicit $0.

4. Reading condition codes: setX and jX

Once the flags are set, two instruction families read them back: setX turns a condition into a 0/1 byte, and jX turns a condition into a branch.

Suffix (X)Condition testedMeaning
eZFEqual / Zero
ne~ZFNot equal / Not zero
sSFNegative
ns~SFNonnegative
g~(SF^OF) & ~ZFGreater (signed)
ge~(SF^OF)Greater or equal (signed)
lSF^OFLess (signed)
le(SF^OF) \| ZFLess or equal (signed)
a~CF & ~ZFAbove (unsigned)
bCFBelow (unsigned)

Every row applies to both setX (e.g. sete, setg) and jX (e.g. je, jg), plus the unconditional jmp. Notice the signed comparisons (g/l) check SF^OF rather than SF alone — that XOR is what corrects for the case where the subtraction itself overflowed, which would otherwise flip the sign bit's meaning.

setX instructions only ever write the low byte of a register, leaving the rest of it untouched — so compiled code almost always follows a setX with a movzbl to zero out the garbage that might be sitting in the upper bytes: 

int gt(long x, long y) {
  return x > y;
}
gt:
  cmpq    %rsi, %rdi   # computes (x - y), sets flags -- note reversed order!
  setg    %al           # %al = 1 if x > y else 0
  movzbl  %al, %eax     # zero-extend into the rest of %eax
  ret

That reversed order is worth internalizing: cmpq %rsi, %rdi computes %rdi - %rsi, i.e. x - y, because AT&T syntax reads cmpq Src2, Src1 and the comparison is Src1 relative to Src2.

After cmpq %rbx, %rax, the ZF is 0 and the SF is 1 with no overflow (OF = 0). What does that tell you about %rax and %rbx (as signed values)?
cmpq %rbx, %rax computes %rax - %rbx and sets flags without storing the result. ZF=0 rules out equality. With no overflow, SF directly reflects the true sign of the difference: SF=1 means the result was negative, so %rax - %rbx < 0, i.e. %rax < %rbx.

5. How an if-statement compiles

Put compare and conditional jump together and you get the standard translation of a C if/else: 

long absdiff(long x, long y) {
  long result;
  if (x > y)
    result = x - y;
  else
    result = y - x;
  return result;
}
absdiff:
  cmpq    %rsi, %rdi   # compare x : y
  jle     .L4            # if x <= y, jump to the else branch
  movq    %rdi, %rax     # (then branch) result = x
  subq    %rsi, %rax     #               result -= y
  jmp     .L5             # skip over the else branch
.L4:                        # else: x <= y
  movq    %rsi, %rax     # result = y
  subq    %rdi, %rax     # result -= x
.L5:
  ret

Reading this is easiest if you mentally invert the test: the compiler jumps past the "then" branch whenever the opposite of the C condition holds. if (x > y) becomes "if NOT(x > y), i.e. if x <= y, skip to the else block" — hence jle, not jg. Writing that out as legal (if ugly) C with goto makes the correspondence explicit: 

long absdiff_j(long x, long y) {
  long result;
  int ntest = (x <= y);   // NOT of (x > y)
  if (ntest) goto L2;
  result = x - y;
  goto L3;
L2:
  result = y - x;
L3:
  return result;
}

The same pattern extends directly to the C ternary operator, since ?: is just an if/else that produces a value: 

val = Test ? True_Expr : False_Expr;

// equivalent goto form:
ntest = !Test;
if (ntest) goto L2;
val = True_Expr;
goto L3;
L2:
val = False_Expr;
L3:
A compiled if-statement begins with cmpq %rsi, %rdi followed by jge .L2. What C condition guards the "then" block that comes right after the jump instruction?
The code immediately after a conditional jump is always the "skip past the else" path: jge jumps to .L2 (the else branch) whenever x >= y, which means it falls through to the code right after the jump only when the opposite holds — x < y. That fallthrough code is therefore the "then" block for if (x < y).

6. Conditional moves: avoiding the branch entirely

Branches are expensive on modern pipelined CPUs: mispredicting which way a branch goes forces the processor to throw away speculative work and restart. For simple, side-effect-free ternaries, GCC prefers an instruction family that computes both outcomes and then picks one, with no branch at all: 

# semantics: if (Test) Dest <- Src   (else do nothing)
cmovle Src, Dest
absdiff:
  movq    %rdi, %rax    # result = x
  subq    %rsi, %rax    # result = x - y
  movq    %rsi, %rdx    # eval = y
  subq    %rdi, %rdx    # eval = y - x
  cmpq    %rsi, %rdi    # compare x : y, set flags
  cmovle  %rdx, %rax    # if x <= y, result = eval
  ret

Both x - y and y - x get computed unconditionally, and the cmovle just decides which one ends up in %rax. That's exactly why conditional moves are only a safe optimization when the compiler can prove both branches are cheap and side-effect-free:

  • Expensive computations — val = Test(x) ? Hard1(x) : Hard2(x); would do all the work of both Hard1 and Hard2 every time, even though only one result is ever used.
  • Risky computations — val = p ? *p : 0; exists specifically to guard against dereferencing a null p. Compiling it with a conditional move would dereference p unconditionally, crashing exactly the case the ternary was written to avoid.
  • Side effects — val = x > 0 ? x *= 7 : x += 3; can't use a conditional move because x would be mutated by the "true" expression even when the "false" branch is the one that's logically supposed to run.
Which of these C ternaries is safe for the compiler to implement with a conditional move (cmovX)?
x - y and y - x are both cheap, side-effect-free expressions safe to compute unconditionally — this is the absdiff example. The pointer dereference risks crashing on a NULL p if evaluated unconditionally, and the compound-assignment version has side effects (mutating x) that must not happen on the branch that "loses."
