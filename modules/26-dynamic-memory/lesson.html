Dynamic Memory Allocation

A local variable disappears the moment its function returns, and a global's size is fixed at compile time. Neither works for a data structure whose size you don't know until the program is running. malloc and free let you carve out and give back memory on demand, from a region called the heap — but unlike everything else you've allocated so far, the heap comes with no automatic cleanup and no safety net.

CS:APP reference: Chapter 9.9.  |  Tested on: This material comes after Game 2 and is tested only on the comprehensive Final.

Learning objectives

  • Explain what malloc, free, calloc, and realloc actually do
  • Describe the heap as a region of a process's virtual address space, managed by the allocator
  • Identify memory leaks, double-frees, use-after-free, and heap buffer overflows in code
  • Explain why every successful malloc must be matched by exactly one free
  • Describe, at a conceptual level, how an allocator might track which blocks of the heap are free

1. Why dynamic allocation exists

Programmers use dynamic memory allocators — malloc in C — to acquire memory at run time, for exactly the case static and automatic storage can't handle: a data structure whose size isn't known until the program is running (a linked list that grows, an array sized by user input, a buffer sized by a file's actual length). The allocator manages a region of the process's virtual address space called the heap, which sits above the program's static data segments and grows upward as more space is requested.

Allocators come in two flavors. An explicit allocator requires the application to request space and to give it back itself — this is malloc/free in C. An implicit allocator lets the application request space but never requires it to free anything explicitly; the system figures out on its own when memory is no longer reachable and reclaims it automatically. This is garbage collection, used by languages like Python, Java, and Lisp. C gives you none of that safety net — the allocator only ever gives memory back when you call free yourself.

2. The malloc package

#include <stdlib.h>

void *malloc(size_t size);
void  free(void *p);
void *calloc(size_t nmemb, size_t size);
void *realloc(void *p, size_t size);
  • malloc(size) returns a pointer to a new block of at least size bytes, aligned to a 16-byte boundary on x86-64. The contents are uninitialized — garbage left over from whatever used that memory before. If size == 0, it returns NULL. On failure, it also returns NULL and sets errno — a return value every call must be checked for.
  • free(p) returns the block pointed to by p back to the heap, making that space available for future allocations. p must be a pointer that came directly from a previous malloc/calloc/realloc call — not the middle of a block, and not an already-freed pointer.
  • calloc(nmemb, size) allocates space for nmemb elements of size bytes each and, unlike malloc, zero-initializes the entire block before returning it.
  • realloc(p, size) resizes a previously allocated block to size bytes, preserving its existing contents (truncated if shrinking). It may return the same pointer, or it may allocate a new block elsewhere and copy the old contents over, freeing the original — you must always use realloc's return value, never assume p is still valid.
void foo(int n) {
    int i, *p;

    /* Allocate a block of n ints */
    p = (int *) malloc(n * sizeof(int));
    if (p == NULL) {
        perror("malloc");
        exit(0);
    }

    /* Initialize allocated block */
    for (i = 0; i < n; i++)
        p[i] = i;

    /* ... use p ... */

    /* Return p to the heap */
    free((void *) p);
}

Internally, the allocator maintains the heap as a collection of variable-sized blocks, each either allocated (in use by the application) or free (available to satisfy a future request). Every call to malloc must respond immediately with some free block large enough to satisfy it — it can't buffer or reorder requests, can't move blocks once they're handed out (no compaction), and can only use heap memory itself to track its own bookkeeping.

3. How an allocator tracks free space (conceptually)

A useful mental model: the allocator keeps some kind of free list — a record of which regions of the heap are currently unused and how large each one is. When a malloc request comes in, the allocator searches that free list for a block big enough, splits off just the amount needed (keeping the leftover as a smaller free block), and hands back a pointer to the usable portion. When free is called, the allocator marks that block free again and, ideally, merges ("coalesces") it with any free blocks immediately next to it, so the heap doesn't fragment into many small, unusable gaps.

There are different levels of sophistication for organizing this bookkeeping. An implicit free list embeds a small header in every block (allocated or free) recording its size and status, so the allocator can walk the whole heap block by block to find free space — simple, but slow to search. An explicit free list instead links only the free blocks together directly (storing "next free block" pointers inside the free blocks themselves), so the allocator only ever has to scan free space, not allocated space, making searches much faster. You don't need to implement either for this course — just understand that "the allocator knows what's free" requires the allocator to actively track it using some structure like this, stored inside the heap itself.

4. Why you must free everything you malloc

Because C's allocator is explicit, nothing gets reclaimed automatically. Every block your program mallocs stays reserved — unusable by anything else — until your program explicitly frees it or exits. A program that keeps allocating without ever freeing what it no longer needs consumes more and more memory over its lifetime, which for a long-running program (a server, a daemon) can eventually exhaust available memory entirely.

The four classic heap bugs:
  • Memory leak: losing the last pointer to an allocated block without freeing it first. The block becomes permanently unreachable and unreleasable — the block in foo() below is a leak the moment the function returns.
  • Double free: calling free twice on the same pointer. The second call corrupts the allocator's internal bookkeeping, because that memory may already have been handed back out to a different malloc call.
  • Use-after-free: reading or writing through a pointer after the block it points to has been freed. The memory may already belong to something else, so this silently corrupts unrelated data.
  • Buffer overflow into heap metadata: writing past the end of an allocated block (e.g. writing n+1 elements into an n-element array) can corrupt the allocator's own header for the next block, causing crashes or corruption far away from the actual bug.
void foo(void) {
    int *p = malloc(128);
    return;   /* p's block is now garbage: no pointer to it remains, and it was never freed */
}
A function calls malloc, stores the result in a local pointer, does some work, and returns without ever calling free on that pointer. What's the bug?
Once the function returns, the only pointer to that block is gone, but the block itself is still marked allocated in the heap. It's now permanently unusable "garbage" — exactly the kind of leak that garbage-collected languages clean up automatically and C does not.

5. Garbage collection: the implicit alternative

Languages like Python, Java, and Lisp use garbage collection: the runtime automatically reclaims heap blocks once it determines nothing can reach them anymore, without the programmer ever calling anything like free. The classic approach, mark-and-sweep, treats memory as a directed graph: every heap block is a node, every pointer is an edge, and root nodes are the pointers living outside the heap — in registers, on the stack, or in global variables. A block is reachable if there's a path of pointers from some root to it; anything unreachable is garbage. The collector periodically walks from the roots, marking every block it can reach, then sweeps through the whole heap freeing every unmarked block.

This requires the collector to be able to reliably tell pointers apart from ordinary data (and for pointers to always point to the start of a block) — which is straightforward in a managed language but hard to guarantee in C, where a pointer can be cast to an integer and back. "Conservative" garbage collectors exist for C and C++, but in general they can't collect everything with certainty, which is part of why C code is expected to manage the heap explicitly instead.

In mark-and-sweep garbage collection, what makes a heap block eligible to be freed?
Mark-and-sweep treats the heap as a graph reachable from a set of roots outside the heap. Anything the mark phase can't reach by following pointers is, by definition, garbage the program can never use again — so the sweep phase reclaims it.
