Control & Data Flow

A function call is really three separate jobs happening at once: control has to jump to the callee and find its way back, arguments and a return value have to move somewhere both caller and callee agree on, and memory has to be carved out for the call and reclaimed afterward. In C this is invisible. In assembly, all three mechanisms are right there on the page — the stack, a handful of argument registers, and two instructions: call and ret.

CS:APP reference: Chapter 3.7.  |  Tested on: Game 2 and the Final.

Learning objectives

  • Explain the three responsibilities every procedure call must handle: passing control, passing data, and managing memory
  • Trace exactly what call and ret do to %rip and the stack
  • Name which registers carry the first six integer/pointer arguments, and where argument 7 and beyond go
  • Distinguish caller-saved from callee-saved registers, and explain why the convention exists
  • Draw the layout of a stack frame during a function call
  • Explain how recursion falls out of the call/return/stack discipline with no special-casing

1. Three jobs, one mechanism

Consider a caller P that calls Q(x), which in turn indexes into a local array before returning: 

P(...) {
  ...
  y = Q(x);
  print(y);
  ...
}

int Q(int i) {
  int t = 3 * i;
  int v[10];
  ...
  return v[t];
}

For that one call to work, three things have to happen, and every one of them is visible in the generated assembly:

  • Passing control — execution has to jump to the first instruction of Q, and when Q finishes it has to jump back to exactly the instruction in P right after the call.
  • Passing data — P has to hand x to Q, and Q has to hand its result back.
  • Memory management — Q needs space for its own local variables (like v and t) that appears when Q is entered and disappears when it returns.

x86-64 code only pays for a mechanism when it actually needs it — a leaf function with no locals and few arguments might use almost none of this machinery. But when it's needed, it's always built out of the same two ingredients: the stack and a fixed set of argument registers.

2. The stack: %rsp and push/pop

The stack is just a region of memory managed with stack discipline — last in, first out. Register %rsp always holds the address of the current stack "top." Unlike the number line in your head, the x86-64 stack grows toward lower addresses: pushing something onto the stack decreases %rsp. 

pushq Src
  1. Decrement %rsp by 8
  2. Write the operand at the address now in %rsp

popq Dest
  1. Read the operand at the address in %rsp
  2. Increment %rsp by 8
  3. Store the value into Dest (must be a register)

Every pushq/popq moves exactly 8 bytes (a quadword) on x86-64, which is why you'll see the stack pointer move in multiples of 8 (or 16, to keep it aligned) throughout this unit.

3. call and ret: passing control

Take a minimal example: multstore calls mult2.

long mult2(long a, long b) {
   long s = a * b;
   return s;
}

void multstore(long x, long y, long *dest) {
   long t = mult2(x, y);
   *dest = t;
}
0000000000400550 <mult2>:
400550:  mov    %rdi,%rax   # a
400553:  imul   %rsi,%rax   # a * b
400557:  retq               # return

0000000000400540 <multstore>:
400540:  push   %rbx        # save %rbx
400541:  mov    %rdx,%rbx   # save dest
400544:  callq  400550 <mult2>   # mult2(x,y)
400549:  mov    %rax,(%rbx) # *dest = t
40054c:  pop    %rbx        # restore %rbx
40054d:  retq               # return

call label does two things: it pushes the address of the instruction immediately after the call onto the stack (the return address), then jumps %rip to label. ret reverses it: pop that saved address off the stack and jump %rip there.

Walking the example above at 400544: callq 400550 <mult2>:

  • Before the call, %rip points at the callq instruction itself.
  • Executing it pushes 0x400549 (the address of the mov right after the call) onto the stack and sets %rip = 0x400550, the start of mult2.
  • mult2 runs its two instructions with no idea who called it or why — it only knows its arguments arrived in registers.
  • When mult2 hits retq, it pops 0x400549 back off the stack into %rip, and execution resumes right where multstore left off.

Notice that call/ret never touch any general-purpose register to remember the return address — it's parked on the stack, which is exactly what lets nested and recursive calls stack up correctly (more on that in Section 6).

Right after callq 400550 <mult2> executes at address 400544, and the next instruction in multstore is at 400549, what has changed?
call always pushes the return address (the instruction right after itself) before jumping, so the stack shrinks by 8 bytes and %rip lands at the callee's first instruction — here, mult2 at 400550.

4. Passing data: registers first, stack for the rest

x86-64 passes the first six integer/pointer arguments in fixed registers, in this order:

Argument123456
Register%rdi%rsi%rdx%rcx%r8%r9

Argument 7 and beyond go on the stack, in the caller's "argument build" area, in order. The return value comes back in %rax. In mult2 above, a arrives in %rdi and b in %rsi because multstore already had x and y sitting in those exact registers — no data even had to move before the call.

This register convention is why so much x86-64 code you'll read in this course never touches the stack at all for a simple, few-argument function: the registers are the calling convention, and the stack is only recruited when there's more data than registers, or space needed than registers can hold.

5. Stack frames

A stack frame is the region of stack memory that belongs to one in-progress function call. Reading from the top of the frame down to the bottom, a frame can contain:

  • An argument-build area, for arguments 7+ to whatever function this function is about to call
  • Local variables, for anything the compiler couldn't fit in registers
  • Saved register values, for any callee-saved registers this function needs to reuse
  • Optionally, the caller's old %rbp, if the frame pointer convention is used
  • The return address, pushed by call — technically the bottom of this frame, shared with the previous one

%rsp always marks the current top of stack; some code also keeps %rbp pointing at a fixed spot within the current frame (the "frame pointer") so local variables can be addressed with a constant offset even as %rsp moves around during the function body. Not all compiled code bothers with a frame pointer — when it's omitted, everything is addressed relative to %rsp instead.

Frame space is allocated when a procedure is entered and freed when it returns:

call_incr:
  subq    $16, %rsp        # allocate 16 bytes of frame
  movq    $15213, 8(%rsp)  # local variable v1
  movl    $3000, %esi      # 2nd arg to incr
  leaq    8(%rsp), %rdi    # 1st arg to incr: &v1
  call    incr
  addq    8(%rsp), %rax    # v1 + incr's return value
  addq    $16, %rsp        # deallocate the frame
  ret

leaq here is doing address arithmetic, not a memory access — it computes %rsp + 8 and loads that address into %rdi, which is exactly how C's &v1 gets compiled.

6. Caller-saved vs. callee-saved registers

Registers are a shared, limited resource: both a caller and a callee might want to use the same one for their own purposes across a call. x86-64 resolves this with a convention that splits the general-purpose registers into two camps:

ClassRegistersRule
Caller-saved%rax %rdi %rsi %rdx %rcx %r8 %r9 %r10 %r11A callee is free to overwrite these. If the caller needs a value in one of them to survive the call, the caller must save it first.
Callee-saved%rbx %rbp %r12 %r13 %r14 %r15A callee that wants to use one of these must save its incoming value and restore it before returning. The caller can trust these survive a call untouched.

%rax is also special as the return-value register — caller-saved, since the callee is expected to overwrite it on purpose. Back in the multstore example, the push %rbx / pop %rbx pair exists purely to honor this rule: multstore wants to keep dest in the callee-saved %rbx across the call to mult2, so it saves %rbx's old value on entry and restores it before returning, protecting whoever called multstore.

A function wants to keep a value alive in a register across a call to another function, without saving it itself. Which kind of register should it use?
Callee-saved registers are the callee's responsibility to preserve, so the caller can rely on their values surviving a call for free. A caller-saved register might be clobbered by the callee, so the caller would have to save and restore it itself — defeating the point.

7. Recursion: nothing special

Recursion often feels mysterious in a high-level language, but at the assembly level it's not a separate feature at all — it's the exact same call/stack-frame mechanism, just aimed at the same function. Each active call gets its own private frame, so each recursive invocation's locals and saved registers can't collide with any other invocation's. 

/* Recursive popcount: count 1-bits in x */
long pcount_r(unsigned long x) {
  if (x == 0)
    return 0;
  else
    return (x & 1) + pcount_r(x >> 1);
}
pcount_r:
  movl    $0, %eax        # return value = 0
  testq   %rdi, %rdi       # x == 0?
  je      .L6              # if so, done
  pushq   %rbx             # save caller's %rbx (callee-saved)
  movq    %rdi, %rbx
  andl    $1, %ebx         # %rbx = x & 1
  shrq    %rdi             # %rdi = x >> 1
  call    pcount_r         # recursive call
  addq    %rbx, %rax       # result = (x&1) + pcount_r(x>>1)
  popq    %rbx             # restore this frame's %rbx
.L6:
  ret

Each nested call to pcount_r pushes its own return address and its own saved copy of %rbx before recursing further, so the value of x & 1 computed at depth 3 can never be stomped on by the call at depth 4 — it's sitting in a different stack slot. When the base case (x == 0) finally returns, the calls unwind in exactly the reverse order they were made, each one popping its own saved %rbx and adding its own bit back in. Because the stack is strictly last-in-first-out and every call is matched with exactly one return, this works cleanly no matter how deep the recursion goes (until the 8 MB stack itself runs out) — and it even works for mutual recursion, where P calls Q which calls P again.

Why doesn't a deeply recursive function's local variables get overwritten by its own recursive calls?
The stack discipline gives every call — recursive or not — a private frame for the duration of that call. There's no special-case machinery for recursion; it's the same call/frame/return mechanism used for any function call, just pointed at itself.
