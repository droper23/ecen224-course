Linking

gcc -o prog main.c sum.c looks like one step, but it's really three: a compiler turns each source file into machine code, and then a separate program — the linker — stitches those pieces together with any libraries you use into one executable. This module opens up that last step: what a linker actually does, why splitting a program into files works at all, and how to read the errors it produces when it can't finish the job.

CS:APP reference: Chapter 7.2–7.4.  |  Tested on: Game 1 and the Final.

Learning objectives

  • Trace the compilation pipeline from source files to a single executable
  • Explain what an object file contains and what a symbol is
  • State the two jobs a linker does: symbol resolution and relocation
  • Distinguish static from dynamic linking and say why each exists
  • Diagnose "undefined reference" and "multiple definition" linker errors from the strong/weak symbol rules

1. The compilation pipeline

When you run gcc -o prog main.c sum.c, gcc is acting as a compiler driver: it invokes several separate programs in sequence, and only the last of them is technically "the linker." 

main.c ---translators (cpp, cc1, as)---> main.o
sum.c  ---translators (cpp, cc1, as)---> sum.o
                                            \
                                             +--> linker (ld) --> prog

Each source file is translated independently into a relocatable object file (.o) — independently enough that gcc never needs to see sum.c while it's compiling main.c. All it needs is to know that a function called sum exists somewhere, via its declaration. The linker is the step that comes after all the individual .o files exist, and its job is to combine them — along with any libraries — into one fully linked executable that contains the code and data for every function used, regardless of which source file defined it.

2. Why linkers exist

Splitting a program into separately compiled files, and then relinking them, buys you two things that a single monolithic source file can't give you:

  • Modularity. A program can be organized as a collection of smaller, more understandable files instead of one giant mass, and you can build reusable libraries of common functions once — the standard C library and the math library are exactly this — and link against them from any program that needs them.
  • Efficiency. Separate compilation means that changing one source file only requires recompiling that file and relinking — not recompiling everything. And with libraries, the executable only needs to end up containing the code for the functions it actually uses, rather than shipping every function in the library, every time.

3. What a linker actually does

A linker performs two distinct steps, and most linker errors come from failures in one or the other of them.

Step 1 — Symbol resolution. A program defines and references symbols: global variables and functions. A definition like int sum(int *a, int n) { ... } creates the symbol sum; a call to sum(array, 2) elsewhere references it. When the assembler builds an object file, it records every symbol the file defines in that file's symbol table — an array of entries, each with a name, a size, and a location. During symbol resolution, the linker's job is to match every symbol reference across all the object files to exactly one symbol definition. While main.c is compiled, the compiler has no idea where sum's code will end up (or even that it exists, beyond the declaration) — resolving that is entirely the linker's job.

Step 2 — Relocation. Each object file was compiled as if it started at address 0, independent of every other file. The linker merges all the separate code and data sections into single sections, assigns every symbol a final absolute address in the executable, and then walks back through the code and data patching every reference to those symbols so they point at the real, final address instead of the placeholder each file was compiled with.

4. Object files and the ELF format

There are three kinds of object file you'll encounter, all sharing one file format on Linux:

  • Relocatable object file (.o) — code and data in a form that can be combined with other .o files to build an executable. Each one comes from exactly one source file.
  • Executable object file (a.out) — code and data ready to be loaded directly into memory and run.
  • Shared object file (.so) — a special relocatable object file that can be loaded and linked dynamically, at load time or even at run time (Windows calls the equivalent a DLL).

All three are stored in ELF (Executable and Linkable Format), the one unified binary format Linux and Unix systems use for all of them. An ELF file's most important pieces:

SectionContains
.textThe compiled machine code
.rodataRead-only data: string literals, jump tables, etc.
.dataInitialized global variables
.bssUninitialized global variables — has a section header but takes up no space in the file itself ("Block Started by Symbol")
.symtabThe symbol table — procedure and static variable names, section names and locations
.rel.text / .rel.dataRelocation info: addresses of instructions/data that still need to be patched, and how to patch them
.debugSymbolic debugging info, present when compiled with gcc -g

5. Symbol resolution when a definition is missing

A declaration like void foo(); promises the linker a definition exists somewhere. If nothing ever defines foo, symbol resolution fails and the linker — not the compiler — reports the error, because the compiler was perfectly happy with the promise: 

$ gcc -c file1.c
$ gcc file1.o -o main
/usr/bin/ld: file1.o: in function `main':
file1.c:(.text+0xe): undefined reference to `foo'
collect2: error: ld returned 1 exit status

This is why "undefined reference to X" always means the same thing: some file referenced symbol X, and no object file or library being linked defines it. The usual fixes are: you forgot to add the .c file (or its compiled .o) to the link command, you forgot -l for a library, or you genuinely never wrote the function.

6. Strong and weak symbols, and multiple definitions

The other classic linker error is the opposite problem: too many definitions. To resolve it, every global symbol is classified as strong or weak:

  • Strong: functions, and global variables that are initialized (int foo = 5;)
  • Weak: global variables that are only declared/uninitialized at file scope (int foo;)

The linker resolves duplicate symbol names with three rules, in order:

  1. Multiple strong symbols with the same name are not allowed. Each one can only be defined once anywhere in the program; violating this is a link-time error.
  2. Given one strong symbol and one or more weak symbols with the same name, the strong symbol wins. Every reference to the weak symbol resolves to the strong definition instead.
  3. Given multiple weak symbols with the same name and no strong one, the linker picks one arbitrarily. (gcc -fno-common turns this case into an error instead, which is usually what you actually want.)
Why rule 2 is dangerous, not just permissive: if file1.c has double x; (weak) and file2.c has int x = 7; (strong), the linker silently merges them into one symbol at the strong symbol's size. Writes to x from the file that thinks it's a double can then overwrite whatever variable happens to sit right after it in memory — a real, silent bug with no warning at link time.
file1.c has int x; and file2.c has int x = 7;. What happens at link time?
int x; with no initializer is a weak symbol; int x = 7; is strong. Rule 2 says a strong symbol always wins over weak ones with the same name, so every reference to x across both files ends up pointing at the same initialized integer — no error, but both files now genuinely share one variable.

7. Declarations, definitions, and extern

A definition causes storage to be set aside (int sp;, double val[MAXVAL];); a declaration reserves no storage — it only promises the linker that a definition exists somewhere else. Whenever a global variable is used in a file that doesn't define it, that file needs an extern declaration for it: 

/* file: stack.c -- this is the definition */
int sp = 0;
double val[MAXVAL];

/* file: main.c -- this is a declaration, not a definition */
extern int sp;

There must be exactly one definition of a given external variable across the whole program, but as many extern declarations of it as you like. In practice, this is exactly what header files are for: a header holds the shared declarations (and #defines) that every .c file that uses a variable or function #includes, while exactly one .c file holds the actual definition.

The static keyword does the opposite of extern at file scope: it limits a global variable or function's visibility to the file it's declared in, so no other file can reference it, even with an extern declaration. Applied to a local variable inside a function, static means something different but related: the variable's storage persists across calls instead of being reallocated each time, so it keeps its value from one call to the next. 

void update(void)
{
    static int count = 0;  // initialized once, ever -- not on every call
    count++;                // but this increment sticks between calls
}

8. Static vs. dynamic linking

Everything above describes static linking: all the code a program needs, including any library functions it calls, is copied into the final executable at link time. That executable is then self-contained, but every program that uses, say, the standard I/O library carries its own copy of that code, and updating the library means relinking every program that uses it.

Dynamic linking instead links against a shared object (.so) file that stays separate from the executable, and gets loaded and linked in at load time or run time instead of at compile time. Multiple running programs can share one copy of the library code in memory, executables are smaller, and the library can be updated (e.g. a security patch) without recompiling every program that depends on it — the next time each program runs, it picks up the new shared object automatically.

Which of the linker's two jobs is responsible for turning a symbol's placeholder address into its real, final address in the executable?
Symbol resolution matches each reference to exactly one definition. Relocation is the separate step that then merges sections from every object file, assigns final absolute addresses, and patches every reference to point at them.
