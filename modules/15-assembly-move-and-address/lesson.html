Move & Address (movq, leaq)

Every C statement you've written eventually becomes a sequence of moves between registers and memory, plus address arithmetic to figure out where memory. This module covers the mov instruction family, the full x86-64 addressing-mode syntax, and the oddball instruction that never touches memory at all: leaq.

CS:APP reference: Chapter 3.4–3.5.  |  First lecture after Game 1.  |  Tested on: Game 2 and the Final.

Learning objectives

  • Choose the correct mov suffix (b/w/l/q) for a given operand size, and use movz/movs to widen a value correctly
  • Identify the three AT&T-syntax operand types — immediate, register, memory — in a real instruction
  • Parse the general addressing-mode syntax D(base,index,scale) and compute the effective address by hand
  • Explain what leaq actually does, and why it's different from every other instruction that mentions memory
  • Recognize why compilers emit leaq for pointer arithmetic and for cheap multiplications like x*12

1. AT&T syntax and the register file, briefly

This course uses AT&T syntax (the GCC/CS:APP default), not Intel syntax. Two rules fall out of that immediately: registers are prefixed with %, immediate constants are prefixed with $, and every two-operand instruction reads source, destination — the opposite order from how you'd read it in Intel syntax or in a C assignment. movq %rax, %rbx means "copy %rax into %rbx," not the reverse.

x86-64 gives you sixteen 64-bit general-purpose registers (%rax–%rdx, %rsi, %rdi, %rbp, %rsp, %r8–%r15). Each one also has smaller aliases for its low-order bytes, which is how the mov suffix and the register name have to agree:

WidthBytesExample (the %rax family)
Quad word8%rax
Double word4%eax
Word2%ax
Byte1%al

%rsi/%rdi and the numbered registers %r8–%r15 follow the same pattern with a d/w/b or numeric suffix (e.g. %esi, %r8d, %r8b).

2. Operand types: immediate, register, memory

Every operand in x86-64 assembly is one of exactly three kinds:

  • Immediate — a constant, written with a $ prefix: $0x400, $-533. Encoded directly into the instruction bytes.
  • Register — one of the sixteen integer registers: %rax, %r13. (%rsp is reserved for the stack pointer and shouldn't be used as a general-purpose scratch register.)
  • Memory — a reference to 1/2/4/8 consecutive bytes at a computed address, written in parentheses: (%rax) is the simplest case, meaning "the memory at the address stored in %rax" — exactly what pointer dereferencing (*p) compiles to.

The general move instruction is movq Src, Dest. Critically, you cannot move memory directly to memory — at least one operand must be a register. Moving a value from one address to another always takes two instructions, staged through a register: 

movq (%rax), %rdx     # load: temp = *p1   (illegal to fold into one instr)
movq %rdx, (%rcx)      # store: *p2 = temp
InstructionC analog
movq $0x4, %raxtemp = 0x4;
movq $-147, (%rax)*p = -147;
movq %rax, %rdxtemp2 = temp1;
movq %rax, (%rdx)*p = temp;
movq (%rax), %rdxtemp = *p;

A classic worked example is pointer swap, which uses only loads, a register move, and stores: 

void swap(long *xp, long *yp) {
  long t0 = *xp;
  long t1 = *yp;
  *xp = t1;
  *yp = t0;
}
swap:
  movq    (%rdi), %rax   # t0 = *xp
  movq    (%rsi), %rdx   # t1 = *yp
  movq    %rdx, (%rdi)   # *xp = t1
  movq    %rax, (%rsi)   # *yp = t0
  ret

Notice the arguments xp and yp arrive in %rdi and %rsi — that's the x86-64 calling convention, covered in a later module. For now, just read each line: dereference %rdi into %rax, dereference %rsi into %rdx, then store each temporary back through the other pointer.

In the instruction movq $-147, (%rax), what are the two operand types (source, destination)?
The $ prefix on -147 marks it as an immediate constant. (%rax) is a memory reference — the address stored in %rax, dereferenced. So this stores the constant -147 into the memory location that %rax points to.

3. The mov family: matching suffix to size

There is no single "move" instruction — there's a family, and the suffix tells the CPU (and you, reading the assembly) how many bytes to move. The destination register must match that width exactly:

SuffixSizeName
b1 bytebyte
w2 bytesword
l4 bytesdouble word (long, in x86 terms)
q8 bytesquad word
movl %eax, (%rsp)            # move 4 bytes
movw (%rax), %dx              # move 2 bytes
movb $0xFF, %bl                # move 1 byte
movb (%rsp,%rdx,4), %dl       # move one byte from (%rsp+%rdx*4) to %dl
movq (%rdx), %rax             # move 8 bytes

Moving a smaller value into a larger register needs to decide what goes in the extra bytes, so two more instruction families handle that explicitly:

  • movzb/w(w,l,q) — zero-extend: pad the upper bits with 0s. movzbq $0x8A, %rax produces 0x000000000000008A.
  • movsb/w(w,l,q) — sign-extend: replicate the sign bit into the upper bits, preserving the value as a signed number. movsbq $0x8A, %rax produces 0xFFFFFFFFFFFFFF8A (since 0x8A is negative as a signed byte).

A quirk worth remembering: a plain movl into a 32-bit register (e.g. %eax) automatically zeroes the upper 32 bits of the full 64-bit register as a side effect — but a movw or movb leaves the untouched upper bytes exactly as they were. movw $-1, %ax sets %ax to 0xFFFF but leaves the high 48 bits of %rax alone.

Instructions that don't exist — common exam bait:
  • movl %eax, (%rsp) is fine, but movl %rax, (%rsp) is not — the suffix (l, 4 bytes) must match the register width (%rax is 8 bytes).
  • movb $0xF, (%ebx) is illegal — a 32-bit register can't be used as a 64-bit address in x86-64; addressing registers must be full 64-bit.
  • movw (%rax), 4(%rsp) is illegal — both operands are memory references, and at most one operand may be memory.
  • movl %eax, $0x123 is illegal — an immediate can never be a destination.
You need to load a signed 16-bit value from memory into %rax, preserving its sign as a 64-bit signed value. Which instruction does that?
movw is a suffix/register-size mismatch (w is 2 bytes, %rax is 8). movzwq would zero-extend, which is wrong for a signed value — a negative 16-bit number would turn into a huge positive 64-bit number. movswq sign-extends the word into the quad word, which is exactly what preserving a signed value requires.

4. Full addressing-mode syntax

(%rax) was the simplest possible memory operand. The general form lets you express almost any array or struct access in a single operand: 

D(base, index, scale)      Mem[ D + Reg[base] + scale * Reg[index] ]
  • D — a constant displacement (encoded in 1, 2, or 4 bytes)
  • base — any of the 16 integer registers
  • index — any register except %rsp
  • scale — must be 1, 2, 4, or 8 (matching the size in bytes of char, short, int/float, and long/double/pointer respectively — that's not a coincidence, it's what makes array indexing free)

Every piece is optional, which gives several common special-case forms:

FormComputes
(b)Mem[Reg[b]]
D(b)Mem[D + Reg[b]]
(b,i)Mem[Reg[b] + Reg[i]]
D(b,i)Mem[D + Reg[b] + Reg[i]]
(b,i,S)Mem[Reg[b] + S*Reg[i]]
D(,i,S)Mem[D + S*Reg[i]]
D(b,i,S)Mem[D + Reg[b] + S*Reg[i]]

Given %rdx = 0xf000 and %rcx = 0x100, here's how the arithmetic plays out:

ExpressionD + Reg[b] + S·Reg[i]Address
0x8(%rdx)0x8 + 0xf0000xf008
(%rdx,%rcx)0xf000 + 0x1000xf100
(%rdx,%rcx,4)0xf000 + 4·0x1000xf400
0x80(,%rcx,2)0x80 + 2·0x1000x280
Given %rax = 0x2000 and %rdx = 0x3, what address does 0x4(%rax,%rdx,8) compute?
D + Reg[base] + scale·Reg[index] = 0x4 + 0x2000 + 8·0x3. In decimal, 8×3 = 24 = 0x18, so the sum is 0x2000 + 0x18 + 0x4 = 0x201c. Convert the scale multiplication to decimal first, then back to hex, to avoid the common slip of multiplying hex digits directly.

5. leaq: computing an address without touching memory

leaq Src, Dest stands for load effective address. Syntactically its source operand looks exactly like a memory operand — it uses the same D(base,index,scale) syntax — but semantically it is completely different from every other instruction that uses that syntax: leaq never reads memory at all. It just evaluates the address arithmetic and writes the resulting number into the destination register. Compare: 

movq (%rax), %rdx    # dereference: %rdx = *(long*)%rax
leaq (%rax), %rdx     # copy the address itself: %rdx = %rax

Compilers reach for leaq in two situations:

  • Generating a pointer, e.g. compiling p = &x[i];. Because leaq computes an address but doesn't dereference it, it's the natural translation of the & operator combined with array/struct offset math.
  • Cheap integer arithmetic of the form x + k*y, where k is 1, 2, 4, or 8. Since the CPU's address-computation hardware already computes exactly that expression, the compiler can hijack leaq as a fast add-and-multiply that has nothing to do with memory at all.

The canonical exam example is compiling multiplication by a constant. GCC turns x*12 into a shift and an add-via-leaq, because leaq and a shift are both cheaper than a general multiply: 

long m12(long x) {
  return x * 12;
}
                                 # x*12  ==  (x + 2x) * 4
leaq (%rdi,%rdi,2), %rax   # t = x + x*2 = 3x
salq $2, %rax                # return t << 2 = 3x*4 = 12x

leaq also shows up wherever a struct field's memory address (not its value) is needed — that's the subject of the Structs & Unions module.

Watch for on exams: because leaq performs no actual memory access and no arithmetic operation in the ALU sense, it does not set any condition codes (ZF, SF, CF, OF) — unlike addq, subq, and friends, which you'll meet in the next module.
Why does GCC translate x*12 using leaq and salq instead of a single imulq?
General multiplication is one of the more expensive ALU operations. Because 12 = (1+2)*4, the compiler can compute 3x with one leaq (an address-computation instruction, not a "real" multiply) and then finish with a cheap left-shift by 2 — avoiding imulq entirely for a constant that factors into small scale/shift-friendly pieces.
