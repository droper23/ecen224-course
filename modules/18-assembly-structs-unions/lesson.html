Structs & Unions

The machine has no idea what a struct is. By the time your code runs, every field access has been flattened into a fixed numeric offset into a block of memory. This module covers how the compiler picks those offsets — including the padding it inserts that you never asked for — and how a union throws the whole "each field gets its own space" idea away on purpose.

CS:APP reference: Chapter 3.9.  |  Tested on: Game 2 and the Final.

Learning objectives

  • Explain why struct field access compiles to a fixed-offset memory reference, with no runtime lookup
  • Compute a struct's field offsets, size, and padding by hand from its declaration and alignment rules
  • Explain why alignment requirements exist, in terms of how memory hardware actually works
  • Compute the address of a field within an array of structs
  • Explain how a union's memory layout differs from a struct's, and identify legitimate uses for that overlap

1. A struct is just an offset table, resolved at compile time

A C struct is represented at the machine level as nothing more than a contiguous block of memory, big enough to hold all its fields. The compiler decides, once, how many bytes each field needs and at what offset from the start of the struct it lives — and every field access in your program becomes a memory reference at that fixed offset. Field order in memory always exactly matches declaration order, even in the (unusual) case where the compiler could have packed things more tightly by reordering them. 

struct rec {
  int a[4];        // offset 0,  16 bytes (4 ints * 4 bytes)
  size_t i;         // offset 16, 8 bytes
  struct rec *next; // offset 24, 8 bytes
};                   // total size: 32 bytes

The critical thing to internalize: once this compiles, the machine-level program has no concept of "struct rec" at all. r->i doesn't look up a field named i at runtime — it compiles to "read 8 bytes starting at address r + 16," where 16 was baked in by the compiler and the field name is gone.

2. Field access: fixed offsets and leaq

Accessing an array field inside a struct combines two things you already know: a fixed struct-field offset, and array-element addressing (Module 15's D(base,index,scale) syntax). 

int *get_ap(struct rec *r, size_t idx) {
  return &(r->a[idx]);
}
# r in %rdi, idx in %rsi
get_ap:
  leaq  (%rdi,%rsi,4), %rax   # r + 4*idx  -- field a starts at offset 0, so no displacement needed
  ret

Because a starts at offset 0 within the struct, computing &r->a[idx] needs no separate displacement — it's exactly the addressing-mode scale trick from Module 15, with leaq doing the address math without ever dereferencing memory (which is exactly right here, since we're returning a pointer, not a value).

Following the next pointer to walk a linked list is just repeated fixed-offset loads: 

void set_val(struct rec *r, int val) {
  while (r) {
    long ind = r->i;
    r->a[ind] = val;
    r = r->next;
  }
}
.L11:                            # loop:
  movq    16(%rdi), %rax         #   ind = M[r+16]      (field i)
  movl    %esi, (%rdi,%rax,4)    #   M[r+4*ind] = val    (field a[ind])
  movq    24(%rdi), %rdi         #   r = M[r+24]         (field next)
  testq   %rdi, %rdi             #   test r
  jne     .L11                    #   if r != 0, loop

Every field reference here — 16(%rdi) for i, 24(%rdi) for next — is a plain displacement-addressed memory operand. There's no instruction anywhere that "knows" it's touching a struct.

3. Alignment: why fields don't always sit back-to-back

If the compiler just packed every field flush against the previous one, you'd get the smallest possible struct — but you'd also get fields whose addresses don't line up with how memory hardware actually reads data. x86-64 (and most architectures) reads memory in aligned chunks — typically 4 or 8 bytes at a time. A multi-byte value that straddles a chunk boundary can cost an extra memory access to read or write, and if it straddles a virtual memory page boundary, handling it gets considerably trickier. The fix is a rule: a value of size K bytes must start at an address that's a multiple of K.

Type sizeExamplesAlignment requirement
1 bytecharnone — any address
2 bytesshortaddress's lowest bit must be 0
4 bytesint, floataddress's lowest 2 bits must be 0
8 bytesdouble, long, any pointeraddress's lowest 3 bits must be 0
16 byteslong double (GCC/Linux)address's lowest 4 bits must be 0

To satisfy this for every field and keep fields in declaration order, the compiler inserts padding — unused filler bytes — wherever a field would otherwise land at a misaligned offset: 

struct S1 {
  char c;      // 1 byte,  needs no alignment
  int i[2];    // 4-byte elements, need 4-byte alignment
  double v;    // 8 bytes, needs 8-byte alignment
} *p;
offset:   0    1  2  3   4      8      12     16              24
field:    c  [pad-3 ][    i[0]    ][    i[1]    ][       v        ]
           1 byte     4 bytes(mult of 4)          8 bytes(mult of 8)

c takes 1 byte at offset 0. i needs to start at a multiple of 4, so 3 bytes of padding get inserted before it. i[0] and i[1] then sit back-to-back (offsets 4 and 8) since int doesn't need any gap between elements. v needs to start at a multiple of 8, and offset 16 already is one, so no more padding is needed there.

There's a second rule beyond individual field alignment: the overall struct's size must also be a multiple of K, where K is the size of its largest field — so that if you ever put this struct in an array, every element (not just the first) stays aligned. That can force padding at the very end, even after the last field: 

struct S2 {
  double v;    // offset 0
  int i[2];    // offset 8
  char c;      // offset 16
} *p;           // total size must be a multiple of 8
offset: 0        8         16   17                24
field:  [   v    ][  i[0]  ][ c ][   7 bytes pad    ]

v, i, and c only need 17 bytes total, but since K = 8 (from the double), the struct is padded out to 24 bytes.

Saving space: put large fields first. Since alignment padding is driven entirely by field order, reordering a struct's fields (when you control the declaration) so the largest types come first often eliminates padding almost entirely. struct S4 { char c; int i; char d; } needs 12 bytes (padding before i and after d), while struct S5 { int i; char c; char d; } — the same three fields, reordered — needs only 8.
struct T { short s; double d; char c; }; On x86-64, what is sizeof(struct T)?
s takes offset 0-1 (2 bytes, no alignment need beyond 2-byte). d needs 8-byte alignment, so it can't start until offset 8 — 6 bytes of padding go between s and d. d occupies offset 8-15. c takes offset 16 (1 byte). That's 17 bytes of real content, but the struct's total size must be a multiple of K=8 (the largest field, the double) — so it's padded out to 24 bytes total.

4. Arrays of structs

Once you know a struct's padded size, indexing into an array of them is just multiplying that size by the index — the same scale-and-offset addressing you've used throughout this unit, just with a struct's size standing in for a primitive type's size: 

struct S3 {
  short i;    // offset 0
  float v;    // offset 4  (needs 4-byte alignment, so 2 bytes padding after i)
  short j;    // offset 8
} b[10];       // sizeof(struct S3) padded to 12 (multiple of 4, the largest field)

short get_j(int idx) {
  return b[idx].j;
}
# %rdi = idx
  leaq    (%rdi,%rdi,2), %rax    # 3*idx  (since 12 = 4*3, this + a scale-4 access = *12)
  movzwl  b+8(,%rax,4), %eax     # load b[idx].j: address = b + 8 + 4*(3*idx) = b + 12*idx + 8

This is the same leaq-for-multiplication trick from Module 15 (12 isn't a legal addressing-mode scale, so the compiler factors it into a leaq-computed 3×idx combined with a scale of 4), landing on address b + 12·idx + 8 — the start of element idx, plus the fixed offset of field j within it.

struct P { int x; int y; } pts[100]; (no padding needed — both fields are 4-byte ints, struct size is 8). What address expression gives pts[i].y?
Each struct P is 8 bytes, so element i starts at pts + 8*i. Field y is the second int, at offset 4 within the struct, so pts[i].y lives at pts + 8*i + 4.

5. Unions: all members share the same memory

A struct gives every field its own space. A union does the opposite on purpose: every member is overlaid at the same starting address, and the union is only as large as its largest member — not the sum of all of them. 

union U1 {
  char c;      // offset 0, 1 byte
  int i[2];    // offset 0, 8 bytes
  double v;    // offset 0, 8 bytes
} *up;          // sizeof(union U1) == 8  (the size of its largest member)

struct S1 {      // for contrast: the equivalent struct
  char c;
  int i[2];
  double v;
} *sp;            // sizeof(struct S1) == 24, from Section 3 above

Where the struct version lays c, i, and v end-to-end across 24 bytes, the union version puts up->c, up->i, and up->v all starting at the exact same address, byte 0. Writing through one member and reading through another reads back whatever bit pattern is actually sitting in that shared memory, reinterpreted as the new member's type.

That's not usually what you want by accident — but it's exactly the tool for two legitimate jobs:

  • Reinterpreting bits without a cast. C won't let you treat a float's bits as an unsigned directly, but a union will: 
    typedef union {
  float f;
  unsigned u;
} bit_float_t;

float bit2float(unsigned u) {
  bit_float_t arg;
  arg.u = u;
  return arg.f;   // reads back the same 4 bytes, as a float
}
    This is precisely how you'd inspect the raw sign/exponent/fraction bits of an IEEE 754 float from Module 5, without the compiler trying to numerically convert the value for you.
  • Inspecting byte order. A union of a char[8], a short[4], an int[2], and a long[1] — all sharing the same 8 bytes — lets you write bytes through the char view and read the result through the wider views, which is exactly how you'd empirically confirm x86-64 is little-endian (the least significant byte lives at the lowest address) rather than taking it on faith.
The tradeoff: a union deliberately opts out of C's type safety — the compiler will not stop you from writing one member and reading a different, unrelated one. Use it when reinterpretation is exactly the point (bit tricks, tagged variants where only one field is ever valid at a time); reach for a struct whenever fields need to coexist.
union { int i; float f; } u; u.i = 0x40000000; What does u.f read back as?
i and f share the exact same 4 bytes of memory. Writing u.i doesn't convert anything — it just stores the bit pattern 0x40000000. Reading u.f reinterprets those same bits as IEEE 754 single precision: sign 0, exponent 10000000 (=128, bias 127, so E=1), fraction all zero, giving 1.0 * 2^1 = 2.0. This is legal, well-defined behavior in C, and exactly the "reinterpret the bits" use case unions are designed for.
